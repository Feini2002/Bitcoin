# 舆情分析模块 (fenxi) 设计与重构规划

## 1. 模块核心定位
本模块（第二页）的核心目标是**结合「事件」与「指标」，构建纯粹为金融交易与系统内其他“员工（Agent）”提供决策支撑的硬核情报看板**。
如果说第一页（事件一览）是“全天候信息雷达日报”，那么第二页（舆情分析）就是“世界新闻 + 金融真实数据”的**多重叠加验证器**。

## 2. 核心优化方向与避坑指南 (基于讨论共识)

### ① 与第一页“宏观温度”的绝对差异化
*   **痛点**：第一页顶部已经有了基于 F&G 和大类资产粗略波动的“信息温度”。如果第二页仅仅做情绪打分，会严重同质化。
*   **优化思路**：第二页顶部的 Gauge 与状态必须聚焦于**真实的资金面与风险偏好 (Risk-On / Risk-Off)**。需要脱离单纯的“新闻热度”，转而结合真实的金融硬指标（如：合约资金费率异动、爆仓分布、期权隐含波动率/VIX、美债收益率差等）。它反映的是“聪明钱在干什么”，而不是“散户在看什么”。

### ② 阻断“LLM分析LLM”导致的幻觉叠加 (抗失真机制)
*   **痛点**：如果只把第一页 LLM 总结出的快讯喂给第二页的 LLM 再次进行“深度逻辑分析”，由于没有增量事实，LLM 极易产生“回音室效应”，疯狂脑补出不真实的交易剧本（幻觉灾难）。
*   **优化思路**：
    *   **硬数据注入**：分析时必须强行注入此时此刻的市场真实切片（如特定标的的 1h/4h 涨跌、成交量异动、异动量级）。
    *   **定向二次搜索**：当需要验证某个第一页的叙事时，不是让 LLM 瞎猜，而是针对该叙事触发一次**极其狭窄、专注于金融标的定价验证的定向搜索**（专门搜彭博、WSJ 对该事件的定价分析）。
    *   **结论降级机制**：在 prompt 中严格要求，当无法用硬数据证实某个叙事的影响时，LLM 必须老实输出“仅见事件，未见资金跟随确认”，绝不顺着逻辑瞎编。

### ③ 绝对精准的催化剂时间轴 (禁止编造日期)
*   **痛点**：LLM 极其擅长编造虚假的倒计时、发榜时间或会议日期，一旦用于交易参考将带来极大风险。
*   **优化思路**：
    *   时间轴、宏观日历（如 CPI、非农、美联储决议、代币解锁）**绝对不能由 LLM 凭空生成**。
    *   必须依赖可靠的外部 API（如财经日历接口、硬编码时间表或可靠的第三方数据结构）提供准确的 `timestamp`。
    *   LLM 的权限被严格收敛：它**只允许对传入的确定性时间节点进行“影响面推演”和“事前关注点提炼”**，禁止其参与时间的计算与日期的输出。UI 层必须直接渲染确定的结构化时间。

### ④ 面向“系统员工”的结构化输出
*   本模块不只是给人看的新闻汇总，更是下游 Agent 的“前置环境上下文”。
*   **优化思路**：输出必须包含明确的、机器可读的枚举值/布尔值标识。例如：`macro_regime: "RISK_OFF"`, `verified_catalyst: false`, `data_divergence: true`。下游的“订单流员工”或“策略员工”能直接读取这些标识来调整策略阈值。

## 3. 后续落地 Next Steps
1.  **打通硬数据源**：在 Worker/前端层面准备好所需的财经日历接口、实时行情快照接口，以便与事件文本拼接。
2.  **重写 Prompt**：围绕“硬数据校验”、“防脑补约束”、“结论降级”编写新的二次验证与交叉分析提示词。
3.  **UI 映射调整**：对照现有的截图坑位，把前端的图表、卡片与新的高维数据结构对接，彻底剔除纯文本形式的无效占位。
