## 3. 现行数据流

舆情分析当前生成链路：

1. 前端 `js/pages/news.js` 读取 `DataEngine.fetchYuqingReportLatest("sentiment_analysis")`。
2. 手动二次分析时调用 `DataEngine.generateYuqingStructuredReport("sentiment_analysis")`。
3. Worker 进入 `createYuqingReport`，再进入 `buildSentimentAnalysisReport`。
4. `buildSentimentAnalysisReport` 读取最近一次 `daily_event`，读取事实池，拉取市场上下文，判断是否触发增量 ingest。
5. 当前仍通过旧 `buildReport` 复用 `dashboard/news/timeline/ai/trends` 的 LLM 编排，再组装成舆情分析页需要的 `report`。
6. 结果写入 `yuqing_reports`，前端按 `report.marketState`、`riskRadar`、`eventCalendar`、`aiIntel`、`trendRead`、`quality`、`sourceErrors` 渲染。

当前关键断点：

- `analysisCoverage` 已经按 8 个舆情模块存储，但仍通过 `fenxiLegacyModulesFromCoverage` 映射回旧的 `dashboard/news/timeline/ai/trends`。
- `cloudflare/yuqing/fenxi/index.js` 已是目录入口，但真实模块文件还没有按 8 个页面模块展开。
- `cloudflare/yuqing/fenxi/sentiment-logic.js` 只有早期纯函数，尚未形成完整的模块输入/输出契约。
- `catalystCalendar`、`techPremium` 以及部分搜索覆盖仍带 PLANNED，不能因为拆文件就去掉 PLANNED。

已完成但仍需保留为基础设施的部分：

- 舆情分析页设置抽屉、D1 持久化设置 key、`visibility` / `analysisCoverage` / `searchCoverage`、Worker 设置快照与设置接口已经纳入当前架构。
- 这部分对应 `cloudflare/yuqing/fenxi/DESIGN.md` 里的 Phase 0.5，后续无需再单独作为计划项重复执行，只需在拆模块时继续沿用这些 key 和开关语义。

## 4. 拆分总原则

推荐方法：先一次性拆出文件骨架和统一契约，再按风险分批迁真实逻辑。

不要一次性把所有真实逻辑全迁完。舆情分析关联了上游事件日报、事实池、市场 Worker、D1 设置、增量搜索、LLM 成本统计、报告库、前端渲染和下游 Agent 输入，一次性全迁容易让某些卡片显示正常，但报告结构、成本、错误降级或设置开关断裂。

拆分时保持这些约束：

- 主部署单元仍是 `cloudflare/yuqing/yuqing-worker.js`，先不拆成多个 Cloudflare Worker。
- `fenxi/` 下的每个模块文件只承接该模块的输入、prompt、normalize、fallback 和输出字段。
- 主 Worker 继续负责路由、D1、Cron、报告写库、成本汇总、全局错误收束。
- `fenxi/index.js` 作为 barrel，只导出模块、设置 schema 与聚合函数。
- 前端 `js/pages/news.js` 的模块 key 与 Worker `YUQING_FENXI_MODULES` 必须保持一致。
- `PLANNED` 只在对应能力端到端可用后删除；拆文件或接入壳子不等于完成。

## 5. 目标文件结构

建议最终让 `cloudflare/yuqing/fenxi/` 至少包含以下文件：

| 文件 | 目标职责 |
|------|----------|
| `index.js` | barrel 导出、模块 registry、settings/search scopes、健康检查可读 shell。 |
| `shared.js` | 舆情分析共用清洗函数、输入上下文规整、source/error/fallback 工具。 |
| `context.js` | 将 daily report、factRows、aiFacts、marketSnapshot、settings、incrementalSearch 组装成统一输入。 |
| `risk-regime.js` | 资金风险温度：风险偏好、评分、关键资产、市场状态摘要。 |
| `hard-data-matrix.js` | 硬数据校验矩阵：BTC、资金费率、OI、基差、强平、衍生品快照等结构化校验。 |
| `narrative-validation.js` | 叙事定价验证：只保留能被价格、资金或后续事实确认的事件。 |
| `catalyst-calendar.js` | 催化剂时间轴：只接受外部 API 或硬编码日历传入的可信 timestamp。 |
| `risk-thresholds.js` | 风险传导阈值：触发、确认、失效、降级分层。 |
| `agent-context.js` | 下游员工/Agent 可直接读取的枚举、状态和质量标识。 |
| `distortion-audit.js` | 抗失真审计：事实池、搜索、源覆盖、sourceErrors、降级理由。 |
| `tech-premium.js` | 科技叙事溢价复核：AI/工具/科技新闻如何进入资金面筛选。 |
| `report-builder.js` | 舆情分析 report 组装层；只组合各模块结果，不直接写路由或 D1。 |

如果实现时觉得文件过多，第一阶段也可以只建 `shared.js`、`context.js`、`risk-regime.js`、`hard-data-matrix.js`、`agent-context.js`、`distortion-audit.js`、`report-builder.js`，其余模块保留在 `sentiment-logic.js` 里等待后续迁移。

## 6. 分阶段计划

### 已完成前置：设置与模块注册框架

状态：已纳入现行架构，不再作为后续主线阶段重复执行。

已具备：

- `cloudflare/yuqing/fenxi/index.js` 中已有 8 个模块 key、`workerField`、`planned` 标记和搜索覆盖 key。
- Worker 已能读取舆情分析设置，并在报告与 grounding 中保存 `settingsSnapshot`。
- 前端已有 `visibility`、`analysisCoverage`、`searchCoverage` 的设置入口和默认回退。
- `analysisCoverage` 已能影响旧兼容编排映射，但仍不是完整模块化产出。

后续约束：

- 不改模块 key，除非同时改前端、Worker、历史报告 fallback 和验证脚本。
- `visibility` 只影响页面显示；`analysisCoverage` 影响分析纳入范围；`searchCoverage` 只控制增量搜索和未来定向搜索。
- 旧报告没有设置快照时，前端必须继续使用默认配置展示。

### 阶段 1：一次性拆骨架，不改行为

目标：让 `fenxi/` 目录具备和 `shijian/` 类似的模块形态，但外部响应字段尽量不变。

动作：

- 新建 `shared.js`、`context.js`、`report-builder.js` 与 8 个模块文件的空壳或最小导出。
- 沿用现有 `YUQING_FENXI_MODULES`、`YUQING_FENXI_SEARCH_SCOPES`、settings normalize；如果拆到清晰文件，仍必须由 `index.js` 汇总导出。
- 将 `marketStateFromLegacy`、`riskRadarFromInputs`、`opportunitiesFromInputs`、`calendarFromFacts`、`trendReadForSentiment` 从 `sentiment-logic.js` 逐步转接到对应模块，但第一步可保留原函数名再 export，降低主 Worker 改动。
- 在 `buildSentimentAnalysisReport` 内只把“组装 report”的部分改成调用 `fenxi/report-builder.js`，不改变 HTTP 路由、D1 写库、成本统计、sourceErrors 返回结构。
- 更新 `fenxiModuleShell()`，让 `GET /api/yuqing/health` 能读出更明确的 `fenxi` 拆分状态。

关联点：

- `cloudflare/yuqing/yuqing-worker.js` 的 import、`buildSentimentAnalysisReport`、`readFenxiDashboardSettings`、`fenxiLegacyModulesFromCoverage`。
- `cloudflare/yuqing/fenxi/index.js` 与新增模块文件。
- `scripts/verify-yuqing-reports.cjs` 如校验字段写死，需要同步补充。
- 不碰 `js/pages/news.js` UI，除非发现字段契约必须补充。

验收：

- 同样的 D1 最新 `sentiment_analysis` 报告仍能被前端渲染。
- 手动生成返回结构不变：`report.marketState`、`riskRadar`、`opportunityScanner`、`eventCalendar`、`aiIntel`、`trendRead`、`quality`、`sourceErrors` 保持可读。
- `PLANNED` 标记不因为拆文件而减少。

### 阶段 2：批量迁确定性模块

目标：先迁不依赖新增 LLM prompt 的确定性逻辑，降低主 Worker 复杂度。

优先模块：

- `riskRegime`：从 `legacy.dashboard`、market snapshot 和 source errors 生成风险状态。
- `hardDataMatrix`：从 `marketSnapshot.data` 中抽取 BTC、衍生品、强平、AI 快照、宏观代理等校验项。
- `agentContext`：输出 `macro_regime`、`verified_catalyst`、`data_divergence`、`market_snapshot_ok`、`incremental_search_used`、`llm_downgrade_required` 等下游可读状态。
- `distortionAudit`：收束上游日报引用、事实池数量、搜索覆盖、错误源、降级依据。

动作：

- 每个模块输出明确的对象或数组，不直接拼 HTML。
- 前端继续只读 report 字段，必要时只做字段兼容，不改视觉结构。
- 把市场快照缺口和 sourceErrors 统一归入审计模块，避免不同卡片各写一套错误逻辑。

验收：

- 关闭任一 `analysisCoverage` 开关，对应模块降级为空状态或关闭状态，不影响其他模块。
- 市场 Worker 不可用时，舆情报告仍能生成，但明确输出数据缺口与降级原因。

### 阶段 3：迁叙事验证与风险阈值

目标：把“事件是否能被资金跟随”与“风险触发/确认/失效”拆出，形成舆情页真正的二次研判核心。

模块：

- `narrative-validation.js`
- `risk-thresholds.js`

动作：

- `narrativeValidation` 只吃上游 `daily_event`、事实池、来源引用、市场确认信号，不再复用旧 `news/timeline` 的泛化字段作为唯一依据。
- `riskThresholds` 输出分层条件：触发、确认、失效；只给条件队列，不直接给交易方向。
- 如继续调用 LLM，prompt 放入模块文件，成本统计仍通过主 Worker 汇总。
- 搜索使用必须受 `searchCoverage` 控制，并写入 `incrementalSearch` 与 `sourceErrors`。

验收：

- 叙事验证缺少硬数据时，显示“待验证”而不是生成确定结论。
- 风险阈值没有足够数据时，只输出条件与缺口，不输出交易执行方向。

### 阶段 4：迁时间轴与科技溢价模块

目标：处理 PLANNED 较强的两块，避免过早宣称完成。

模块：

- `catalyst-calendar.js`
- `tech-premium.js`

动作：

- `catalystCalendar` 只接受可信 timestamp：外部日历 API、硬编码日历或事实池已有明确 UTC 时间；不允许 LLM 编造日期。
- 在没有可信 timestamp 前，保留 PLANNED 与“等待结构化财经日历”的 UI 状态。
- `techPremium` 只在 AI/科技新闻与资金偏好或资金流变化同向时提升权重。
- `techPremium` 接入搜索时必须记录来源覆盖、增量搜索是否启用、错误源和置信度。

验收：

- 没有可信时间源时，日历模块继续显示 PLANNED，不把事实池抓取时间误当事件时间。
- 科技叙事不能单独变成交易信号，只能进入资金面复核。

### 阶段 5：收束旧兼容层

目标：等 8 个模块都能独立产出后，逐步减少对旧 `buildReport` 的依赖。

动作：

- 逐步让 `buildSentimentAnalysisReport` 调用 `fenxi/report-builder.js` 和各模块专属 prompt。
- 保留 `daily_event` 的 `buildReport` 逻辑，不因舆情页拆分影响事件一览。
- `fenxiLegacyModulesFromCoverage` 仅保留为短期兼容；等新模块完整后再移除或降级为 fallback。
- 健康检查 `codeLayout.shell` 应能清晰显示 `shijian` 与 `fenxi` 当前状态。

验收：

- 舆情分析不再依赖旧 `dashboard/news/timeline/ai/trends` 映射来决定模块是否生成。
- 事件一览和舆情分析的模型通道、成本统计、报告库互不串扰。

## 8. 验证命令

文档变更本身只需人工核对内容。后续代码拆分按变更范围选择：

- 通用语法检查：`npm run lint`。
- Yuqing 报告契约：`npm run verify:yuqing`。
- Worker/API 路由或静态壳关联变更：`npm run verify:api`。
- 影响行情快照、衍生品或热力数据读取：`npm run verify:derivatives`，必要时再跑 `npm run verify:market-snapshot`。
- 跨前端、Worker、报告契约多区域变更：`npm run verify:all` 或 `npm run build`。
- UI 变更后，本地可跑 `npm run dev:local`，并检查 `#/news-analysis`；部署后检查 `https://bitcoin.feiniwork.com/index.html#/news-analysis`。

不要把网络实时数据成功当成稳定测试结论。行情源、Worker、Binance、Bybit、Gemini 与 Cloudflare 状态都可能随时间变化。

## 9. 部署与 D1 规则

默认不部署、不推送。

只有用户明确要求“部署 / 上线 / deploy”时才执行：

- 只改文档：通常不需要 Pages 或 Worker 部署。
- 改前端、静态资源、样式或 `index.html` 引用：部署前更新受影响资源 `?v=`，再执行 `npm run deploy:pages`。
- 改 `cloudflare/yuqing/yuqing-worker.js` 或 `cloudflare/yuqing/fenxi/*.js`：本地验证后，如用户要求部署，在 `cloudflare/` 下执行 Yuqing Worker 的 wrangler deploy。
- 同时改 Pages 与 Worker：先部署 Worker，再部署 Pages。
- 改 D1 schema、迁移 SQL 或远程表内容：默认不执行远程 D1；只有用户明确要求同步时再做。

阶段 1 到阶段 4 的计划默认不需要 D1 schema 变更。若某个模块后续需要新增持久字段，先写迁移计划，再单独执行。

## 10. PLANNED 保留规则

以下情况必须保留 PLANNED：

- 只有文件骨架，没有真实数据链路。
- 只有 LLM 文本，没有可校验结构化输入。
- 只有事实池抓取时间，没有事件发生的可信 timestamp。
- 只有 AI/科技新闻热度，没有资金面或价格确认。
- 只在 Worker 中生成了字段，但前端、报告库、设置开关、错误降级还没有一致可用。

允许删除 PLANNED 的条件：

- 该模块的数据来源、生成逻辑、D1 写入、前端展示、设置开关、错误降级和验证脚本都已连通。
- 对应报告字段在最新报告、历史报告和 report item 中都可稳定读取。
- 用户明确同意进入完成态，或当前任务明确要求完成该模块端到端。
