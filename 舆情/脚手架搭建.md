# 舆情与事件模块 · 脚手架与现行说明

与 **双层日报子页面**、`yuqing` Worker、`yuqing` D1 及 Cron 对齐。**未端到端接通的能力**：仍须保留站内 **PLANNED** 占位，勿随意删除。

## 一、与其它 Worker 的边界

| 域名（默认） | 代码入口 | 职责 |
|--------------|----------|------|
| `yuqing.feiniwork.com` | `cloudflare/yuqing-worker.js` + `yuqing-facts.js` | 舆情两页：**事实池、日报/二次研判、`yuqing_reports`、`/api/yuqing/reports/*`** |
| `btc.feiniwork.com` | `cloudflare/binance-klines-worker.js` | **K 线 / 衍生品等行情 D1**；舆情二次分析时由 Yuqing Worker **HTTP 拉取**市场上下文 |

前端通过 `js/data-engine.js` 的 **`yuqingApiBase()`** 与 **`apiBase()`** 分别指向两套服务（可在页面注入 `BIT_YUQING_API_BASE` / `BIT_DATA_API_BASE` 覆盖）。

## 二、两条子页面（主路径 = 云端，不是 mock）

| 路由 | 名称 | 页面脚本 | Worker 报表 `kind` |
|------|------|----------|---------------------|
| `#/news` | 事件一览 | `js/pages/events.js`（`pageYuqingEvents`） | `daily_event` |
| `#/news-analysis` | 舆情分析 | `js/pages/news.js` | `sentiment_analysis` |

**数据流（现行）**

- 两页首屏与历史列表以 **`GET /api/yuqing/reports/latest|history|item`** 为主（封装在 `DataEngine.fetchYuqingReport*`）。
- **`GET /api/yuqing/latest` / `items` / `history`** 等事实池接口仍保留，用于排障或其它场景，**不是**双子页默认首屏数据源。
- 生成写库：**`POST /api/yuqing/reports/generate`**（body 带 `kind`）；兼容路径 **`POST /api/yuqing/report`**（舆情编排）。

**关于「mock」**

- **事件一览**：无整块离线假 `report`；无数据时展示空状态 + 引导「实时扫描」或报告库。
- **舆情分析**：内部用字符串 `"mock"` 仅表示 **未从 D1 载入成功时的 UI 状态**（chip 样式），**不是**一份完整假 JSON 日报。
- 开发时以 **Worker 落库字段** 与 **`GET …/reports/*` 响应** 为契约真源；旧独立单页见下「附录」。

**逻辑关系（闭环）**

- 事件一览侧重 **事实池 + 信息底座** 的结构化展示。
- 舆情分析读取 **最近一次 `daily_event`**（`grounding.basedOnDailyReportId` 等），叠加 **行情/衍生品快照** 与按需增量采集，产出 **二次研判**。
- Cron 设计意图：**先事件日报、后舆情分析**（具体 UTC 表达式见 `cloudflare/wrangler.yuqing.toml`）。**开发阶段**可在 Worker 内用常量 **临时跳过**定时 LLM 报告（见下文「定时与开发开关」）。

## 三、后端 · `yuqing` Worker（单一部署单元）

| 项 | 说明 |
|----|------|
| 主代码 | `cloudflare/yuqing-worker.js` |
| 事实池 / D1 辅助 | `cloudflare/yuqing-facts.js` |
| 配置与 Cron | `cloudflare/wrangler.yuqing.toml`（**独立**于 btc Worker） |
| D1 迁移 | `cloudflare/migrations/yuqing/0001_init.sql`、`0002_reports.sql` |
| 手工事实写入 | `POST /api/yuqing/ingest`，请求头 **`X-Yuqing-Cron-Secret`** = Secret **`CRON_SECRET`** |

### 定时与开发开关

- **Cron 表**仍在 `wrangler.yuqing.toml`；触发的是 **本 Worker** 的 `scheduled`。
- 若 `yuqing-worker.js` 顶部 **`YUQING_SKIP_SCHEDULED_LLM_REPORTS === true`**：`scheduled` **不再**跑会调用 LLM 的 `createYuqingReport`（事件日报 + 舆情二次）；**手动** `POST /api/yuqing/reports/generate`、事实池 ingest **不受影响**。
- **`GET /api/yuqing/health`** 字段 **`scheduledLlmCronSkipped`** 可在线上确认上述开关形态。

### 事件一览内 LLM 编排要点（已实现）

- **单次「实时扫描」**：浏览器 **一次** `POST …/reports/generate` → Worker **一次** `createYuqingReport` → **`buildDailyEventReport` → `buildReport`**，同一条响应内含温度计、今日头条+动态速览、趋势、AI 情报等后再写入 D1。
- **趋势研判（`daily_event`）**：`buildReport(..., trendsUseAiIntel: false)` 时，趋势 prompt **只综合**页面顺序上位居其上的三块：**dashboard JSON（与温度卡同源）+ 今日头条 + 动态速览**，**不把「AI 情报站」Markdown 喂给趋势模型**；舆情二次（`sentiment_analysis`）仍默认可 **full**（含 AI 情报等）综合趋势，与其页面职责一致。
- **默认 Gemini 模型**：以 `yuqing-worker.js` 中 **`YUQING_GEMINI_MODEL_DEFAULT`** 与 `wrangler.yuqing.toml` 的 **`YUQING_LLM_MODEL_*`** 为准（当前部署为轻量 flash 系 preview 名时，以线上 vars 为准）。

### 主要 HTTP 路由（摘要）

- `GET /api/yuqing/health`
- 事实池侧：`GET /api/yuqing/sources`、`latest`、`items`、`history`
- 报表侧：`GET /api/yuqing/reports/latest?kind=…`、`history`、`item`、`DELETE item`
- `POST /api/yuqing/reports/generate`、`POST /api/yuqing/report`、`POST /api/yuqing/llm/test`

### Secrets / 环境变量（常见）

- `FINNHUB_API_KEY`、`CRON_SECRET`
- `GEMINI_API_KEY` / `GOOGLE_API_KEY`，`YUQING_LLM_PROVIDER`，`YUQING_LLM_MODEL_*`
- 慎用：`YUQING_LLM_ALWAYS_SEARCH=1`（搜索配额）

## 附录：旧 ribao 单页与现行差异

- **`舆情/日报/ribao-cloudflare/`** 等旧 **独立 HTML** 实验稿 **不由** BitDesk 壳 `index.html` 渲染；**契约与 prompt 真源**以 **`cloudflare/yuqing-worker.js`** 为准。
- 旧稿中 **Markdown + `===SPLIT===`** 等流式拆分，与现行 Worker **单轮 JSON（宏观）+ 结构化落 `report`）** 不必逐字一致；若需对照「叙事习惯」，可参考该目录草稿，不必维护单独 Mock 手册。
- **趋势读数字段**：事件一览 `trendRead` 使用 **`cracking`**；舆情分析使用 **`fracturing`**（及 `checklist` 等），勿混用键名。
