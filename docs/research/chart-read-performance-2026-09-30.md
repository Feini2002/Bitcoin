# 行情切换与读取性能修复（2026-09-30）

## 范围与契约

- 用户当前要求先修复本地行情工作台切换周期、切页和刷新超时；迁移打包、README、commit/push 留待此项收口后继续。
- L2：共享数据读取与生产行情 Worker；维持采集频率、D1 schema、历史保留和分析来源规则。没有删历史、插值补洞或放宽来源核实。
- 依据现有四页工作台计划、`cloud-d1-desk-governance-2026-09-21.md` 与真实浏览器/数据库证据；分析仍仅使用 `/api/desk/*`。

## 已核验的问题

- 内置浏览器原 4h 全窗一次读取 16.403 秒，其中等待响应头约 15.685 秒；另一次读满 30 秒失败。并非绘制 6,000 根蜡烛本身耗时十几秒。
- 首次读取失败后，正常轮询尚未注册，旧 UI 禁用全部周期按钮，无法自行恢复。“主图停机”也容易被误解为云端或历史被删除。
- D1 实际返回过 `overloaded / requests queued for too long` 和 CPU reset。旧 4h 全窗扫描 24,961,983 行、SQL 6,048.7624 ms；20 根尾部扫描 578,055 行、SQL 1,082.7122 ms。
- 根因之一是规范数据选择有效版本时，对每个候选版本再比较全部版本；递归时间上界也可能退化为从固定上界反复扫描。仅查看 EXPLAIN 中出现索引不足以证明扫描量受控。
- 仅修读取 SQL 后仍有间歇性排队。生产日志捕获 `fred-real10y` 采集耗时 35,331 ms 并失败，同时行情等待 D1 约 34 秒。宏观历史修订的 successor 查询被优化器展开，重复寻找后继 receipt；1,500 个日期、连续三次快照的本地复现中，旧 SQL 单步耗时 3,410 ms。
- Worker 未捕获的组装异常跳过统一 CORS，浏览器会把实际后端失败显示为 `Failed to fetch`。

## 实现

- `dataset-store.mjs`：在选出的 observation key 上直接排序选出唯一 rowid，维持 closed 优先、有效接收时间、receipt 次序和 knownAt；合并递归 seek 上界。无需新增索引或迁移。
- 宏观写入先物化 successor 集合，限定 `@receipt` 键，再按输入日期驱动关联；避免重复计算。相同规模复现该步降至 2 ms；迟到修订和并发写入契约保持不变。规范历史修订判断也改为一次排序选版本。
- `scheduler.mjs`：仅对超过 2 秒的采集记录 dataset、耗时、成功状态，便于区别上游延迟与数据库阻塞，不记录请求头或凭据。
- `desk.mjs`：返回 Server-Timing，区分 desk、D1 往返、SQL 执行和实际行读取数。
- Worker：异常返回统一且不暴露内部细节的 503，并保留允许来源的 CORS。
- `data-engine.js`：同 URL 的在途请求合并；每个订阅者独立取消，最后一个离开才取消底层请求；12 秒单次截止，暂时错误最多重试一次，鉴权错误不重试。
- 主图：5 分钟内保留最多七个完整周期窗口；切回时必须用新尾部核对产品、historyRevision 和时间重叠才复用。历史修订、无重叠或显式同步均重新读完整窗口。网络失败不把缓存冒充新数据。
- 周期切换取消旧主图、子图读取，防止旧周期蜡烛被贴上新标签；失败保留可操作的周期按钮和重读入口，并在可见页面退避恢复，离页取消。

## 第二轮：读取调度、共享历史与失败退避

用户继续要求优化读取策略。本轮修改前端共享读取层、行情页及多周期子图，沿用第一轮 Worker；不修改采集节奏、保留量、schema 或来源判断。

核对发现：

- 子图自身有缓存，但离页销毁后未复用共享数据层已读过的完整窗口；上级结构周期也会重复读完整历史。
- 多个子图和上级结构会同时发请求，快速切换单个子图时，旧请求只忽略结果而未及时取消。隐藏/关闭面板也可能继续等待。
- 常规主图尾部读取失败后仍每秒尝试，首次失败恢复机制未覆盖该分支。
- 旧周期历史重读的 finally 可以在新周期已启动重读后，清掉新周期的 inFlight 状态。

实施策略：

- 单浏览器同时最多两个 desk 传输，子图/上级结构最多占一个；主图和当前页优先。相同请求仍共享，子图请求被主图接管时提升优先级。排队超过 12 秒报繁忙，取消或过期的排队请求不再送到服务端。
- 子图和上级结构复用共享完整窗口，但先读取当前尾部核对时间重叠、产品和历史版本；修订必须重读，删除的历史棒仍按范围替换。没有把缓存标成新采集。
- 单个子图切周期、关闭面板、离页或隐藏时取消相应子图请求。正常轮询仍为 1 秒；失败后按 2、4、8、16、30 秒退避，成功恢复正常节奏；400/401/403/404 停止自动重复请求，重新进入可见页面或手动读取可重试。
- 旧周期重读只允许释放自身仍拥有的状态，防止迟到完成破坏新请求。

验证与限制：

- `verify-desk-read.cjs` 新增主图预留通道、后台串行、排队取消/截止、共享请求优先级提升、轮询退避与旧周期完成竞态检查。
- `verify:cost-ui` 新增共享窗口尾部校验、历史删除后的替换、单子图切换取消和关闭面板取消；桌面 1440 与手机 390 验收通过。

- 2026-09-29 18:47 UTC 本地真实读取：首次 4h 1,369 ms、全部子图 3,877 ms；切页返回主图 365 ms、全部子图 1,182 ms，新增完整历史请求 0；切换 15m / 5m / 4h 为 828 / 917 / 391 ms，无页面脚本错误。

## 外部核验（2026-09-30）

- [Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/)：单库串行处理查询，队列过载会返回 overloaded；优化每次查询比拉长客户端等待更直接。适用当前 D1 Worker binding。
- [D1 Query API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/)：SQL 执行时间与 rows_read 是数据库侧证据，不能和浏览器端到端延迟混淆。
- [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)：SEARCH 只说明访问部分行，不证明在多层循环下总访问数很小；计划格式可能变动。
- [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)：使用明确错误边界、可观察性和有界操作。Wrangler 本仓库锁定 4.85.0，未升级依赖。
- [Pages Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)：第二轮发布前核对构建目录与 Wrangler 直接上传方式；沿用仓库现有部署脚本，仅上传 `dist/pages/` 白名单产物。
