### 2.3 一个容易误读的字段

`sync_status.last_ok = 1` **不等于本次上游抓取成功**。`syncKlinesOne` 在上游失败但有存量数据时，若 `isKlineTailStaleForRead` 判定 D1 尾部仍算新鲜，会写入 `ok: true, inserted: 0, skippedBecause: "d1_tail_fresh_upstream_unavailable"`。因此 1h/4h/1d 的 `last_ok=1` 需要结合 `last_count=0` 与数据时间一起读，不能单独当作健康证明。

    40|### 2.4 本机对照测试的局限（重要）

本机测试币安、Bybit、OKX、`data.binance.vision` 均返回 200，但**不能据此得出「本机直连可用」**：

- 本机运行 FlClash（`FlClash Meta Tunnel` 适配器 `Up`），默认路由 `0.0.0.0/0` 指向 `198.18.0.2`（TUN 虚拟网关）。
- `fapi.binance.com` 被解析为 `198.18.0.x` 虚拟地址。
- 出口 IP 为 `155.254.108.7`（Singapore, AS38136 Akari Networks）。
- 加 `--noproxy "*"` 重测仍为 200，但 TUN 在网络层接管流量，该参数**不能绕过 TUN**。

结论：本机 200 只能说明「经由当前代理线路可访问币安」，不能证明裸连可达，也不能作为方案可行性的依据。

## 3. 归因

**事实层面：**

- 拒绝发生在边缘/CDN 层，不在币安业务逻辑：错误页由 CloudFront 生成，`httpStatus=403`，`binanceCode=null`。
- 与 API Key、签名、请求参数无关；`extra_json` 中 `binanceBanUntilMs` 是历史值，不是本次原因。
- 换域名无效：5 个 fapi 备用域同时 403，说明按来源特征（IP 段）拦截。
- 换 placement 无效：`remote-NRT` 已在东京附近，仍全 403。

**推断层面（未获币安确认）：**

- 币安官方限制基于**源 IP** 而非 API Key（见来源 S1）；Cloudflare 出口是共享且跨机房轮换的 IP 段（见来源 S5/S6 的实践描述）。两者叠加的结果是：CF 出口 IP 段被币安边缘策略拒绝，同一个 CF 段上的所有用户一起受影响。
- Bybit 同样部署在 CloudFront 之后，因此它**不能作为币安的出口兜底**：币安被封时它大概率一起被封。现有 `fetchKlinesWithFailover` 的 binance → bybit → okx 链条在这一前提下存在设计缺口。

**责任归属：** 不是本仓库代码缺陷，也不是配置错误；属于「CF 共享出口 + 交易所侧 IP/地域策略」的组合限制。社区记录显示这类封锁**没有有效申诉渠道**（见来源 S3）。

## 4. 社区同类做法

以下为外部案例，**未经本仓库验证**，仅作候选。

**样本强度说明（2026-09-19 复核）**：这些是个别博客与个人仓库，其中 `LuuOW/binance-proxy` 为 0 star、0 fork，**不能据此断言「最主流」**。可以确认的是**模式**——把出口交给一个可控的固定 IP——在多处独立记录中反复出现；但它在全部方案中的占比没有数据支撑。原文「最主流」的表述过强，已修正。

### 4.1 Worker 保留 + 出口交给固定 IP（多案例，样本有限）

思路：Worker 保留业务逻辑与签名，只把网络请求交给一台有固定出口 IP 的小机器转发。

- **EC2 形态**：Cloudflare Worker VPC → cloudflared Tunnel → AWS EC2（t4g.nano，东京）Rust 代理 → 币安。安全组仅允许出站到币安；签名仍在 Worker，代理不持有密钥（来源 S4）。
- **Fly.io 形态**：[binance-proxy](https://github.com/LuuOW/binance-proxy) 用 Fly 小机器 + Bright Data 固定住宅 IP，Worker 通过 `BINANCE_PROXY_URL` / `BINANCE_PROXY_SECRET` 调用（来源 S5）。注意该仓库 0 star，属个人实作记录。
- **普通 VPS/VPS+反代形态**：一台机房机（可 Docker）把请求整体转发到币安，前面挂 Nginx/Caddy 或直接 IP:端口（来源 S13）。作者记录这是在其「Cloudflare 全 IP 段被封」结论后**唯一可行**的路。
- **共同注意点**：必须剥除 `Fly-*` / `X-Forwarded-*` 等转发头，否则币安 CloudFront 会识别并 403（来源 S5）。
- **共同前提**：若走币安 API Key，需把该固定 IP 加入 Key 的白名单；币安对「IP 不在白名单」也返回 403（错误码 `-2015`），与地域封锁的 403 从外观上难以区分（来源 S14）。

### 4.2 采集逻辑整体搬到固定 IP 主机

用 VPS/EC2 承担 WebSocket 常连与抓取，Cloudflare 只做 cron 调度、UI 与 API 门面。理由：CF Workers 对出站 CONNECT 隧道支持不完整，且出站 DO WebSocket 不能用服务端休眠模型（来源 S7、仓库卷 14 §3）。

### 4.3 换掉边缘平台

有方案建议改用容器平台（如 Northflank）以获得持久连接与固定出口（来源 S8）。对当前问题属过度反应：瓶颈只在出口 IP，不在算力。

### 4.4 失败案例（反面证据）

[lijiachang/cloudflare-worker-binance-api-proxy](https://github.com/lijiachang/cloudflare-worker-binance-api-proxy) 是一个纯 Worker 代理尝试，仓库 README 直接以 `Error 😂` 结尾并附上币安拒绝原文 `Service unavailable from a restricted location`。说明**纯 CF 方案行不通**（来源 S9）。

[S13 作者](https://www.logiconsole.com/bypass-binance-location-restriction/) 的实验更完整：先用 `cf.resolveOverride` 把请求强制改道到台湾机房的 CF 出口（绕过「CF 按请求来源判断地域」），**仍然失败**，最终结论是「币安貌似把 Cloudflare 所有 IP 段都封了」，只好改用机房转发。这说明**在 CF 内部换 region 无法解决**，与仓库「换 placement 无效」实测一致。

**一个存疑点**：社区讨论（来源 S15）提到「可以把 `.com` 换成 `.us` 恢复调用」，但 `binance.us` 是独立的美国合规实体，**不是绕过手段**；S13 的作者是**美国用户**，其被封主因是属地合规限制，与本仓库「非受限地区 IP 被共享 CF 段牵连」的情形不完全相同。该路径不适用于本仓库，需另行核验后再议。

### 4.5 与 Access 相关的伪 403

Cloudflare 官方文档 issue #31885：当 Access 应用目标是 **Worker destination** 时，Access 会**静默拒绝 WebSocket 升级请求并返回 403**，普通 HTTP 不受影响（来源 S10）。该 403 无 `cf-mitigated` 头、响应体为空，容易与币安 403 混淆。本仓库 Worker 正在使用 Access，排查 WebSocket 问题时需先排除此项。

### 4.6 官方能力现状

- **Workers VPC**：beta 阶段对所有 Workers 计划免费，可经 Cloudflare Tunnel 私密接入自有网络（来源 S6、S11）。
- **Dedicated Egress IPs**：属 Zero Trust **Enterprise 附加项**，当前套餐不可用（来源 S12）。

## 5. 与本仓库的对应

- 现有预留：`cloudflare/wrangler.toml` 中 `BINANCE_FAPI_ORIGIN = ""`，注释写明「仅当 Cloudflare 直连 fapi 被 451 时使用」；`parseCustomFapiOrigin` 与 `fetchKlinesFromBinance` / `fetchAggTradesFromBinance` 已支持该自定义源。即 §4.1 路线**不需要改业务逻辑**，只需外部主机 + 配置。
- 条件分支：`NEW-027`（采集运行环境与持续性实验）已把该问题定性为运行环境与授权问题，要求验证合法可达路径、不得用代理或别所绕过、不得以历史 403 认定今天失效。
- 现有兜底缺陷：如 §3 推断成立，`bybit`/`okx` 兜底在币安同被封时不可靠，且规则要求不得静默以他所数据冒充币安。
- 现有本地采集：`scripts/collect-market-local.cjs` 可复用，但依赖本机与代理，只能作过渡。

## 6. 建议方向（待决策，未实施）

优先级大致为：

1. **自建固定 IP 反代 + 填 `BINANCE_FAPI_ORIGIN`**：改动最小、保持币安来源；代价是常在线设备与运维承诺。
2. **历史数据走 `data.binance.vision` 公开归档**：免费、带校验和、无需 Key，可补历史；**不能解决实时**。
3. **接受部分数据长期滞后并显式标注过期**：零成本，但需前端强制区分「数据缺失」与「数据过期」。

不建议：用其他交易所数据静默顶替币安；购买商业代理绕过地域限制（与仓库规则冲突，需单独授权）；频繁换域名重试。

## 7. 限制与未验证项

- 全部线上结论来自 2026-09-19 两次采样，属**时点快照**；403 状态可能随时间变化，不能当作长期结论。
- 币安侧拒绝的**具体规则未获官方确认**（地域策略 / WAF / IP 段封禁三者未区分）。
- `data.binance.vision` 从 **CF 出口**能否访问未验证（Worker 无通用代理端点，本机测试被 TUN 污染）。
- 5m 数据在 09:15→09:25 之间有推进，但**写入来源未确认**，无法判定是哪个兜底在生效。
- 社区方案的免费额度、条款与可用性按各自官方说明执行，采用前需重新核验。
