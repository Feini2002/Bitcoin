## 2. 产品应该回答什么

默认服务六类研究任务，而不是让用户依次读完所有栏目：

| 任务 | 合格输出 | 不合格替代 |
|---|---|---|
| U01 看当前变化 | 与上次可比窗口相比的重要新变化、来源与局限 | 每次固定生成一篇背景综述 |
| U02 核对一个判断 | 支持证据、反证、时间与方法，能回到原定位 | 给更多专业名词或高置信度数字 |
| U03 排除资讯噪音 | 合并转载、区分根来源、突出实质更新 | 热门新闻越多越好 |
| U04 知道下一检查点 | 官方排期、可观察条件、证据不足时说明等待什么 | 用文章发布时间伪造催化剂日历 |
| U05 恢复研究现场 | 固定run/绝对窗口/方法/来源及诚实恢复等级 | 打开最新K线冒充旧报告现场 |
| U06 复盘过去观点 | 原问题、条件是否发生、结果与误读来源 | 只保存成功预测或事后改写解释 |

暂时无需判断、没有重大变化、需要等待数据与证据不足都是正常结果。系统不以买卖建议数量、Agent数量、报告字数或提醒次数衡量价值。用户仍作金融判断，系统负责减少重复核数、重建上下文与受到噪音干扰的劳动。

时间尺度采用可配置任务窗口，现有5m/24h/3d/7d只是设计参考，不能当用户已经确认只做某种周期。秒级执行、账户风险和自动下单不是本次主线；高频数据只有在对应研究问题成立时才有理由增加。

## 3. 最终产品结构

### 3.1 四个默认工作区

**市场变化**：价格/波动、主动成交、杠杆与可见强平分family展示；强调相对上次的变化、来源一致性和缺口。不再把多个相关指标加成一个无校准市场分。

**重要事件**：文章→事件→主张→版本，转载归并、根来源、时间精度、传闻/否认/更正、官方催化剂。AI与GitHub资讯保留独立可选频道，不默认进入BTC主简报或模型输入。

**条件判断**：事实、解释、成立条件、反证、下一检查、暂不判断。期权/ETF/宏观模块未启用时不出现“已确认”叙述；不为了填卡片生成机会。需要概率时使用独立可结算forecast实验，不把数据质量百分数当概率。

**观点复盘**：研究现场、用户笔记、观点修订、原条件与结果、后来的反证和数据修订。它与交易账户日志不同，不要求资金管理或订单执行。

### 3.2 对现有对象的决定

| 对象 | 决定 | 原因及边界 |
|---|---|---|
| 原生JS、Pages、现有Worker适配 | 初期保留 | 没有性能或维护证据支持先整站迁移 |
| Lightweight Charts4.1.3 | 先保留底座，重做研究状态与页面组织 | 工作区价值来自联动和证据，不来自默认升级版本 |
| 真实aggTrade足迹与已测试方向映射 | 保留并补语义/质量 | 不是从零建设采集器；价格/数量信息仍需完善 |
| 固定score/confidence/机会优先值 | 在新研究输出中退出或明确legacy规则 | 不是统计概率，当前分支不足以支持精确金融含义 |
| 两套snapshot路径 | 统一capture责任与输入身份 | 不再让报告在同一run混取多个latest |
| Gemini REST/流式调用 | 保留provider适配，重做输入/预算/验证/历史 | 现有能力有价值，无证据证明必须换SDK |
| 全球日报、AI情报、GitHub工具 | 按任务重组；非BTC默认退出主链 | 降噪先减少无关输入，不只在最后提示模型简短 |
| 5个员工、会议室与执行原型 | 保留demo边界，不按角色逐一“转正” | 角色名不等于真实研究任务或来源独立性 |
| 期权、ETF、ALFRED、事件研究 | 纳入明确条件的新能力设计 | 不宣称已存在，不一次性作为第一版前置 |
| 多代理/在线分析库/独立服务 | 条件试验 | 以独立信息、恢复、计算和维护证据决定 |

这是比旧报告更主动的业务与分析重设计，但仍要求每项改动有可观察收益。既不为了迁就旧方案保留固定分数，也不为了全面升级删除可靠的原生代码。

## 4. 主架构决定：统一研究域，部署逐步选择

推荐路线B的**职责结构**：市场采集/展示可继续现状，新增统一研究域负责来源政策、输入捕获、方法、事件、报告与复盘；按任务需要才使用批计算或专用服务。初期部署完全可以仍在已有Cloudflare边界内，不等于必须新增常驻Python或数据库。

对比路线A“只改局部文案/提示词”：能快速修正误导，但不足以解决双输入、历史与跨页面身份问题。因此R0可以是A式补丁，目标状态不止于A。

对比路线C“全面后端/前端迁移”：可能适合长期数据密集或团队维护，但当前没有生产容量、查询延迟、真实费用和运维人力证据支撑立即投入。先形成稳定研究契约和测量，再允许外置某个已证明瓶颈。

不要求所有能力运行在Cloudflare；也不把“Python有现成库”自动转成新常驻服务。一个批事件研究可以按任务运行，持续盘口采集才需长期生命周期。现有独立snapshot是否部署未知，实施时选择唯一capture owner而不是再造第三份。[R03｜仓库事实报告§1.3，L28-36](../inputs/repository_facts.md) [R05｜仓库事实报告§2，L53-58](../inputs/repository_facts.md)

## 5. 核心数据与模型链

```text
现有行情/新增获准来源
  → 原始语义与版本/质量
  → 统一capture（市场截止 + 知识截止 + 采样跨度）
  → 不可变bundle与方法清单
  → 确定性状态、变化、分歧
  → 任务相关事件/反证（可选、按权利）
  → 模板或受约束综合
  → 数值/引用/时间/权限验证
  → 不可变final report
  → 研究现场 / 观点 / 预警 / 后续评价
```

程序负责数字、来源、时间、单位、权限、预算和状态；模型负责受约束的解释、复杂材料抽取及有明确问题的补充研究；用户决定值得追问什么和是否接受某项研究假设。多代理只在独立子问题与同预算对照有收益时使用，不按“首席＋四员工”固定一轮讨论。

Google Search Grounding的结果与普通生成、独立获准来源不同，不能默认把它当长期可复用事实池。方案把可归档研究和受专门规则约束的交互回答隔离，具体适用合同和现有用途仍须核对，不据此认定旧系统已经违规。[S024｜Gemini API附加条款](https://ai.google.dev/gemini-api/terms)

## 6. 首个业务交付不等待所有数据工程

**R0**：修正固定概率外观、缺失填50和未启用能力文案，降低BTC默认无关信息。它可以在小范围本地改动后独立验收。

**R1**：从当前可用市场输入产出一次“什么变化、哪些分歧、下一步查什么”的简报，能够打开证据、固定窗口、保留历史；预算未配置时模板可用。无需先建全节点、采购多年L2、接齐ETF或部署向量库。

**R2**：事件归并、官方日历、研究现场与观点记录逐项增加；每个专题能单独验收，不用等全部宏观数据。

**当前切片规则：**收集增量可与首份简报并行，也可不启用；不是所有R2都必须等所有R1任务。首交使用根目录F任务/profile，完整WP仅作细节映射。需要先读的不是30表DDL，而是一个用户问题与其实际输入。

**R3**：前瞻评价、条件预警、事件研究和受条件约束的新期权/ETF能力。无增量的方法或来源应退役，不因已经写了文档而强行上线。

所有阶段都需要与现有治理配合，但治理不是吞没业务交付的无期限前置工程。真实构建/认证/数据边界问题必须处理；与本次能力无关的全仓重排不进入主线。

## 8. 怎么判断这不是新一轮工具清单

每个进入主线的能力都有明确用户问题、输入/输出、来源时间、计算/缺失规则、模块owner、API或存储对象、前端/缓存/导出/模型/历史关联、正常与异常状态、验收、迁移与回退。任务包按实际模块落点，而非只有“增强证据链”“优化prompt”的口号。

候选工具不自动成为依赖。datasketch只在近重复候选必要时；Trafilatura/RSSHub只对明确获准来源；DuckDB只对实际批计算需求；vollib只为期权独立数值校验；promptfoo只为评估组织成本；TradingAgents/FinGPT主要借鉴任务与研究方法，默认不搬入其交易/训练平台。

已知软件许可证、数据用途、模型服务和商业费用分别核对；未明确授权的代码/数据不能因网上可见而复制或再分发。文档研究不是运行验证；性能、模型质量和用户收益必须通过卷11/13的实际试验形成证据。

## 9. 用户价值验收的最低形态

同一份市场数据下，新系统不能比简单模板多出无依据数字；同一个事件集合下，重复/无关信息减少的同时不能把重要更正删掉；同一次研究跨页面应保持窗口/版本一致；同一个旧观点能找到原条件和结果，而不是只看到今天重写的解释。

程序测试能发现FNG缺失、混源、清算价格类型、未来修订、假引用和预算越界。真实样本评价能说明模型相对模板的增量及费用。用户任务对照能说明定位和核对是否更省力；没有测量时不给提升百分比。

校准只针对预声明、可结算的问题；风险/数据质量标签不用概率外观。所谓“有行动意义”包括不判断、等待核实和停止使用坏数据，不强迫每次给交易动作。

## 10. 明确完成状态

本套设计完成的是研究、独立评价、产品/方法/API/工作流规格、迁移与任务拆分，以及文档自身可检查材料。没有完成实际仓库改造、真实模型评估、生产部署或未来有效性证明。条件能力也有设计，但默认未启用，不构成必须实施的用户需求。

后续开发者不需要再从空白构思整套系统，但需要把方案绑定真实源码和配置，并通过列明的实验判断未知。若某项现有实现已经满足合同，直接复用；若某个外部假设不成立，按相应任务缩小/退出，而不是为了执行文档强行增加复杂度。

**最终目标是：每次打开系统，用户更容易看到真正变化、知道哪些结论值得相信、哪些仍不确定，并能回头检验自己的判断。技术选择服务于这个目标，而不是目标本身。**
