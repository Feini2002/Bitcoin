# CASE01｜订阅阅读器怎样成为收集底座

资料核验：2026-09-16。这里分析已公开的产品/方法，不声称实际使用过产品，也不复制其商业实现。


## 已公开的做法
Miniflux的API可管理订阅和条目并暴露检查状态，FreshRSS通过阅读器兼容接口提供同步；RSSHub则把来源适配成feed。直接证据在文末，未实际部署。

## 可吸收的机制
将“取得条目”和“研究该条目”分成两个阶段。订阅服务只负责来源、取得时间、更新和失败，研究服务再决定事件、相关性和证据。人工阅读状态可以帮助分配注意力，但不能让一条文章被标已读后所有相关更正都消失。

## 为什么不能整套照搬
传统阅读器优化的是个人阅读体验，可能按同URL更新内容，不保证满足历史证据版本；研究系统必须在摄取边界保存允许的版本和抓取时间。同步API能导出文章不代表原站授权所有用途，也不保证历史完整。

## 可迁移小实验
选一个官方发布feed和一个许可允许的分析源，导出标题、链接、正文/元数据范围、更新时间和失败信息。模拟同URL更正、304、删除和源停更，观察是否保留旧版本和更正关系。若只能拿到不可追溯的最新摘要，限为阅读入口，不用作审计底座。

## 对当前仓库的意义
这是一条可独立交付的情报收集试点，能与分析简报并行，不要求先换掉现有事实池；若现有模块已经提供同等功能，只借字段和运行指标。
