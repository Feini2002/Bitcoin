## 1. 仓库总纲与当前状态摘要

### 1.1 仓库自述的用途

README 将项目称为面向个人期货交易台的静态 Web 控制台，围绕看盘、研判、复盘与自动化报告组织导航。技术主体是原生 HTML/CSS/JavaScript、Cloudflare Pages、Workers 和 D1。

用户本次明确的目标是：系统分析有实际价值，减少噪音，能够辅助判断；允许网页端研究现有架构、分析方向、提示词和工作流是否需要改变。该目标是用户输入，不是本轮对系统效果已经成立的结论。

### 1.2 已确认的组成

- 浏览器中有行情工作台、足迹/订单流、强平雷达、衍生品、事件日报、舆情分析和设置的接入代码。
- 市场侧同时存在采集、聚合、技术指标、规则派生摘要；分析侧存在事实池、搜索、云端模型、结构化与 Markdown 内容、报告存储和历史。
- 页面导航还保留多员工、会议室、交易执行和复盘相关原型或规划，详见第 9 节。
- 图表入口已使用 Lightweight Charts 4.1.3。package.json 有 Playwright、Vite 等开发依赖；本轮未确认 React、CCXT、DuckDB、AI SDK、promptfoo 已作为当前依赖使用。
- 构建命令执行本地验证并生成 dist/pages/，发布范围由 config/pages-assets.json 指定。

### 1.3 状态不等于部署结果

本地 btc 和 yuqing Worker 配置已启用 workers.dev、Cron 和自定义域相关配置；README 与运行手册仍保留历史暂停说明。文件治理与业务治理记录说明有其他任务并发调整并统一发布。本文未访问 Cloudflare 控制面，因此远程 Cron、路由、当前版本与数据库实际状态未知。

本轮 Git 差异摘要为 65 个已跟踪文件变化，另有未跟踪文件；这一数字不含所有新增文件，且不表示本轮作者修改了这些文件。本文没有执行 commit/push。

上一版包含架构推荐、优先级、实验安排和给网页端的方案约束。本版删除这些内容，保留已核验事实和问题回答，补充当前提示词、规则输出、既有规划与近期变化。本文不判断应采用局部改造还是整体重构，也不替网页端决定保留或淘汰哪些模块。

## 3. 能力 A：版本化证据与历史重现

### A1. 当前权威计算在哪里？

**代码事实：按能力分布，没有全系统单一计算入口。** 浏览器有图表指标、足迹及衍生品展示计算；Worker 有聚合和摘要；独立快照程序有自己的分析逻辑，并复用图表结构模块。现有测试覆盖部分计算和输出契约，但不能证明所有页面、快照和报告对所有输入完全相同。

### A2. 是否已经保存版本与证据？

**部分已有。** 市场快照包含 `snapshotVersion`、`generatedAt`、`dataFreshness`、`sourceFingerprint`；总快照包含四页和五类员工输入。独立快照表按 run/scope 保存 payload 和版本，报告也保存来源引用、grounding、市场上下文和正文。

**但这些字段不等于完整重放保证：**

- 图表指纹主要拼接周期和最新时间；订单流等指纹也主要使用最新时间或行数。因此较早的输入行被修订而最新时间不变时，指纹可能不变。证据：`marketSnapshotProgram.mjs:594`、`:646`、`:698`。
- 原始 K 线表按品种、周期、时间覆盖写入，没有数据修订版本。证据：`cloudflare/schema.sql:3`、`binance-klines-worker.js:742`。
- 快照存的是输出及部分上下文，不能直接推定所有计算需要的原始输入都已保存。
- 独立快照的 run 查询目前返回运行记录及快照索引；其公开 latest 接口不等于“按任意历史 run 恢复全部输入与页面”的完整界面。

### A3. 哪些历史可以重建？

| 对象 | 当前代码规定的保留范围 | 能证明什么，不能证明什么 |
|---|---|---|
| K 线 | 每品种、周期最多 6000 根 | 可从保留 OHLCV 复算相应指标；不能反推原始逐笔，也不保证实际已有 6000 根 |
| 足迹 | 最多 8640 根 5m 基础桶，理论上约 30 天 | 有价格档买卖量可重聚合部分周期；不能完整还原原始事件序列 |
| 强平、衍生品 | 代码保留约 30 天 | 是聚合或指标历史，不是全市场完整逐事件档案 |
| 稳定币 | 约 90 天 | 是低权重背景，不是完整链上研究库 |
| 独立市场快照 | 清理 30 天之外数据，并将运行数量控制在最近 500 条 | 如果运行频率高，实际覆盖可能短于 30 天 |
| 舆情报告和事实池 | 默认清理阈值为 7 天；历史 API 请求范围上限另设为 30 天 | API 接受 30 天不能把已清理记录恢复出来；不适合直接承诺长期研究档案 |

证据：`binance-klines-worker.js:44`、`:54`、`:70`、`:77`、`:150`；`market-snapshot-worker.mjs:180` 起；`yuqing-worker.js:80`、`:835`、`:3336`。

另外，`cloudflare/schema.sql:2` 仍写“2000 根”，而执行常量和回归是 6000 根。这是明确的文档与实现差异，本轮未修改。后续报告应以执行代码为准，避免沿用旧注释。

### A4. 来源修订和来源切换如何处理？

**已有现实的追溯缺口。** K 线可由 Binance 回退到 Bybit/OKX，获取结果带 source，但 K 线持久表与写入语句没有逐条 venue/source 字段。系统能表达某次读取或同步状态，不代表能从当前 K 线表可靠重建每根旧 K 线的交易所来源。

这不是在断言已发生错误交易或错误报告；它说明“长期保留单所历史”和“当时数据来源可追溯”尚不能据此成立。

衍生品的 `funding_binance`、`oi_binance` 指标槽也可接收 Bybit 回退值，但这一表有来源元数据。指标键的名称与实际来源在回退情况下不完全一致。证据：`binance-klines-worker.js:2984`—`:3017`。本轮未逐一验证所有消费者的来源标注。

### A5. 存储和查询成本是否需要迁库？

**未知。** 本轮没有取得生产 D1 大小、扫描行数、写入量、查询分位延迟和账单。源码中“免费额度足够”的旧说明不能替代测量。本轮未开展 DuckDB 与 D1 的对比实验。

## 4. 能力 B：订单流与衍生品

### B1. 足迹到底来自什么？

**来自聚合成交。** 前端代码以 `m=false` 计入主动买量，以成交 ID 等构造去重标识；D1 保存 5m 价格档买卖量、最后成交 ID 和同步状态。已有回归验证买卖量、聚合与恢复。

其实现属于基于 Binance aggTrade 的足迹；不是仅根据 K 线涨跌方向估算买卖量。是否存在真实丢包、历史缺口以及最新上游聚合规则影响，仍需样本核验。

### B2. 清算方向和金额是否正确？

**方向存在按来源区分的实现和通过的固定样本测试。** Binance SELL 映射多头强平；Bybit allLiquidation 的 Sell 映射空头强平。

**归一化字段事实：**归一化对象均输出 price、qty、notional，未在这些对象中保存明确的 priceType。Binance 使用 `ap/p` 和 `z/l/q` 的回退取值，Bybit 使用 `p×v`。本轮没有验证这些价格和数量语义在桶、页面、快照与报告中的全部传递情况。

本轮没有独立重查交易所协议，因此不宣布所有金额计算错误；可直接成立的代码结论是：不同来源字段归并后，价格类型信息不在该对象中显式保留。已有方向测试通过也不能替代价格语义测试。

### B3. 期权与合约规格是否已经具备？

当前核心指标清单没有 Deribit IV、Greeks、期权曲面。针对运行 JS 的检索未找到 Deribit 请求链；schema 中有 `derivative_option_surface`，只能说明保留了结构，不能证明正在采集。

统一的、带生效区间的 instrument 主数据服务也未在本轮查到。不能把 BTCUSDT 的字符串标识直接解释为已经保存全部合约规格。

### B4. 历史、维护责任和新增交易所价值？

- 足迹、强平等历史范围见 A3；实际远程完整度未知。
- 已有采集和恢复实现，新增 Cryptofeed 不是解决“没有采集器”的必要动作。
- 新交易所是否增加独立信息、谁承担持续采集、允许多少费用，是使用目标与运维决策，代码不能代答。
- Binance、Bybit、Deribit 数据的展示、保存、外部推理和分发权利，本轮不做法律结论，也不默认新采购或新授权。

## 6. 能力 D：LLM 报告与回归评估

### D1. 已有适配器缺什么，是否需要换 SDK？

**已有可复用部分：**云端 Gemini REST/流式调用、模型配置、超时、搜索接入、用量与费用估算、来源引用、结构化报告和失败状态。旧本机 CLI 执行入口已由并发治理退役；本轮云端专用回归通过。

本轮未做不同 SDK 的兼容性、维护成本或性能对比；本文不作 SDK 选型结论。

### D2. 报告是否冻结输入？

**保存了结果上下文，但不能认定严格冻结了全部输入。** 报告表保存 `source_refs_json`、`grounding_json`、`market_snapshot_json` 和 `report_json`。市场上下文从多个端点并行读取，生成期间还可能补充事实池与搜索结果；未见该入口以一个统一历史 cutoff 对所有来源实施时点读取。

可以说“报告有留存上下文”，不能说“同一 run 完整固定了当时所有证据和每次模型输入”。本轮未取得完整的生产模型请求记录。

### D3. 重试是否覆盖历史？

报告 ID 默认包含时间和随机后缀，通常形成新报告；日报流式生成会复用同一 ID 更新预览与最终结果。存储采用 INSERT OR REPLACE，因此同 ID 可覆盖。

结论是“支持生成中的同报告更新”，不是“每次重试都覆盖所有旧历史”，也不是“天然不可变审计库”。报告默认 7 天清理；本文未确认存在独立的长期归档。

证据：`yuqing-worker.js:754`、`:789`、`:3160`、`:3791` 附近；`cloudflare/migrations/yuqing/0002_reports.sql`。

### D4. 是否已有模板、预算与评估？

- 已有 fallback dashboard、事实池降级、超时和成本估算；这些不等于经过统一评估的模板基线。
- 存在大量结构、函数与云端流程回归；其中部分是源码字符串断言，不能用于证明模型主张真实。
- 本轮没有运行真实模型，也没有确认端到端“每项关键数字与引用均受支持”的评估集。
- 成本追踪不等于硬费用上限；本轮没有证明每类报告都具有经用户选定的总费用预算。测试中固定价格断言也不能证明当前官方价格仍相同。

### D5. 哪些字段能外发、失败应如何处理？

现有代码实际组织市场上下文、事实和搜索进入云端模型，但代码不能证明数据许可允许任何用途。新增商业数据的用途权利本轮未知。当前云端失败流程有 error 状态留存，已有离线测试覆盖该路径；本文没有给出新的失败处理政策。

## 8. 当前分析内容、提示词与工作流事实

### 8.1 事件日报的范围

cloudflare/yuqing/shijian/index.js 导出信息温度、今日头条、动态速览、AI 情报、GitHub 工具雷达和趋势线索模块。对应前端为 js/pages/events.js，路由是 news；它并非只聚焦比特币的单主题新闻流。

- 信息温度提示词要求覆盖比特币、纳指、标普500、英伟达和黄金；24h 表示短线冲击，3d 表示短线延续，7d 表示背景趋势，以 3d 为主轴。
- 温度提示词禁止直接给出买卖、加减仓指令。这是现有 prompt 的要求，不是对网页端新方案范围的额外限制。
- temperature.js 中程序分数读取 FNG；缺失或非有限值回退为 50。文字分析与这一程序分数不是同一个计算过程。
- 趋势线索 prompt 的角色是全球日报“收束主编＋外部校准员”，输入来自已完成的上游模块，要求围绕具体事件开展 3—6 次定向搜索并提供补充来源。
- 提示词要求使用 Google Search，不等于本轮已经核验生产每次调用的搜索次数和引用支持度。

证据：cloudflare/yuqing/shijian/temperature.js:3、:65 起；trend-clues.js:235 起；shijian/index.js。

### 8.2 舆情二次分析的范围

分析入口读取最新事件日报、近期事实池与市场上下文，并依据日报年龄、事实数量、市场错误与设置决定是否补充事实/搜索。结果包含市场状态、风险雷达、机会条件等；路由为 news-analysis，主要页面文件为 js/pages/news.js。

模块配置包括资金风险温度、硬数据校验矩阵、叙事定价验证、风险传导阈值、Agent 结构化输出、抗失真审计；精准催化剂时间轴和科技叙事溢价复核被标为 planned。搜索配置中的叙事定价验证搜索、宏观事件搜索也标为 planned。

这些配置标签表达模块设计状态；非 planned 不等于已证实分析有效，planned 也不等于没有任何辅助函数。例如代码中存在从事实池提取日历条目的函数，但精准催化剂模块仍标为 planned。
