# 比特币金融分析系统：能力、数据与架构演进研究报告

**检索与核验日期：2026-09-16（Asia/Singapore）**  
**性质：公开资料研究与条件性改造建议；不是代码审计、运行验证、投资建议或上线方案执行记录。**

> 核心判断：先把系统变成“数据可回放、指标可复算、报告可追证”的研究工具，再决定是否更换技术。若确有持续逐笔、订单簿和历史回放需求，首选保留 Cloudflare 展示及控制层、增加一个独立数据计算服务的渐进式混合架构；若实际只需要分钟级行情与日频研究，保守演进已经足够。

## 1. 执行摘要

### 1.1 最值得引入的能力

| 优先事项 | 实际研究价值 | 初步决定 |
|---|---|---|
| 原始数据留存、数据集版本和统一时间口径 | 解释“这个指标当时为什么是这个数”，防止修订后的数据污染历史结论 | 推荐采用，先于增加指标 |
| 单交易所逐笔与订单簿的可靠恢复、回放、缺口标记 | 让足迹、CVD、盘口研究有可信基础，不把漂亮图形当成证据 | 推荐采用方法；采集器通过实验选型 |
| 宏观与 ETF 数据的当时可见性管理 | 区分“事后知道”与“报告生成时已经知道” | 推荐采用 |
| 确定性计算 + 受约束 LLM 解释 + 证据包 | 降低编造数字、混用时间窗口、来源不可核验的风险 | 推荐采用；不默认多代理 |
| Parquet 原始/标准化文件 + DuckDB 批量分析 | 在个人维护成本下建立可复算研究底座 | 推荐采用为混合路线的首个分析存储方案，先小样本验证 |
| 图表、事件、研究笔记与报告证据联动 | 缩短从观察异常到定位原因的操作路径 | 值得试验，不为换图表而换图表 |

这些不是对现有系统缺陷的确认。它们是依据背景及公开技术边界给出的**优先核查、优先补齐的能力清单**。

### 1.2 建议保留的基础

优先保留能正常工作的 HTML/CSS/JavaScript 前端、Cloudflare Pages、Workers API、已有来源适配和指标定义；D1 可继续承载配置、笔记、报告索引、任务状态、数据清单和适量聚合结果。是否已有性能问题、数据耦合或服务边界错误，需要代码与运行数据证明，不能从项目年限推出。

D1 不是“不可用”，但它有具体边界：当前官方单库上限为免费 500 MB、付费 10 GB，查询最长 30 秒，单数据库查询处理存在串行约束。这些限制支持把高频原始事件与复杂历史扫描单独评估，而不是支持直接删除 D1。[S01]

### 1.3 暂不值得投入

暂不引入完整自动交易平台、无人监管的交易代理、Kafka/Kubernetes 等重型集群、全量交易所覆盖、未经许可的社媒抓取，也不把“机构级全市场订单簿历史”列为免费的必备项。ClickHouse、全节点、复杂期权曲面、多代理协作都应有明确研究问题和实验结果之后再增加。

### 1.4 本次核验中最影响决策的发现

- **历史与实时不是同一种可获得性。** Binance 公开历史现货数据自 2025-01-01 起采用微秒时间戳；其 USDⓈ-M 持仓统计接口只提供最近一个月。不能因为今天能查到，就认为以后能补回所有历史。[S05][S06]
- **可见清算不是全量清算。** Binance 相关推送说明存在按交易对、每 1000 ms 仅推送最新一条清算快照的限制。图表应标注“观测到的清算”，不能写成全市场实际总量。[S07]
- **旧许可证印象不可依赖。** Cryptofeed 当前主分支是 AGPL 并附加署名要求；vectorbt 当前许可证包含 Commons Clause；Coin Metrics Community 数据为 CC BY-NC 4.0。[S11][S32][S24]
- **数据商业条款会直接改变 LLM 架构。** Tardis 当前条款区分内部量化研究、LLM 相关用途、外部服务商披露和衍生数据再分发；购买数据不等于可以直接传入任意云端模型。[S15]
- **Cloudflare 不是不能接 WebSocket，但出站连接不能使用 Durable Objects 的 WebSocket 休眠机制。** 因而不可把面向浏览器的低成本休眠模型直接套到交易所长连接采集上。[S02]

## 2. 研究范围与证据边界

### 2.1 三类信息严格区分

| 分类 | 本报告能确认的内容 |
|---|---|
| 用户提供的已知事实 | BTC 分析；涉及图表、指标、足迹、订单流、宏观、舆情、云端 LLM；HTML/CSS/JS 和 Pages/Workers/D1；Binance、Deribit、FRED、Yahoo；项目暂停 |
| 基于背景的条件性推断 | 可能需要持续采集、历史回放、跨来源时间对齐；高频数据可能不适合继续全部放 D1；混合路线可能比整体迁移更便于个人维护 |
| 必须查仓库或实验才能确认 | 实际依赖版本、是否真实逐笔/足迹、是否持久化原始数据、数据规模、错误率、当前费用、代码质量、LLM 工具权限、是否有前视偏差、适配器可复用程度 |

**没有查看用户实际仓库，没有安装或执行候选项目，没有运行回测或性能测试，没有连接交易账户，没有触发真实采集任务，也没有变更生产系统。**

**X 的检索命中过索引条目，但相关帖子正文访问失败，没有把索引摘要当成已读原文。** 本次另外成功读取了 X 官方 API 定价文档，这是“官方文档访问”，不是“已经访问 X 舆情正文”。没有访问私密 Discord、Telegram 群组或付费研究终端。部分搜索结果实际落到网站首页而非目标文章，未用于证明文章细节。

### 2.3 证据强弱与维护核验的限制

**强证据**是当前官方协议、许可证原文、实际发布说明、作者论文。**中等证据**是仓库文档明确描述的能力，但尚未运行。**弱证据**是社区评价、未经复现的性能宣传或推测。

长名单中的维护状态分为：

- **R：**读取了发布或变更记录，可指出实质变化；不代表测试由本研究运行通过。
- **D：**当前仓库/文档可核验，但未完成最近实质提交、全部测试和贡献者分布审计；不能称其已停止维护，也不能无条件称其活跃可靠。
- **S：**官方服务或协议文档可访问；没有实际 SLA、吞吐和可用性测试。

本次没有取得全量 commit、issue、PR 响应时间和贡献者统计。对重点候选只给出可观察的维护迹象和集中度风险，不伪造“bus factor=几人”。发布页的 Latest、LTS、主分支版本、桌面应用版本与后端版本分别处理。下文版本属于**检索时所见的发布/源码状态**，不是升级指令。

### 2.4 法律与授权边界

本报告做工程采购层面的授权识别，不代替法律意见。每个方案至少拆成四个问题：**代码能怎样用；原始数据能怎样保存和展示；数据能否传给云端模型；衍生报告能否商业再分发。** 代码 MIT/Apache 不会自动解除交易所、新闻、社媒或数据商的限制。默认分支许可证与拟锁定版本可能不同，实际选型要重新检查所用版本及依赖。

## 3. 行业方案地图：先按研究能力分层

### 3.1 不是一套“万能交易框架”，而是七层可替换能力

| 层次 | 必须承担的责任 | 候选方向 | 不应混进去的责任 |
|---|---|---|---|
| 来源层 | 接口能力、授权、时延、原始口径 | 原生交易所、FRED/ALFRED、发行人、链上节点、数据商 | 把商业指标包装成原始事实 |
| 采集/回补层 | 长连接恢复、分页、限流、去重、断点和缺口 | 原生适配、CCXT、Cryptofeed、Tardis | 直接生成投资结论 |
| 标准化/质量层 | instrument、单位、时间、序列、版本 | 自有轻量契约，必要时 Pandera | 无痕修正或填平缺口 |
| 存储层 | 原始留存、分析文件、元数据、热点结果 | R2/Parquet、DuckDB、D1；必要时 ClickHouse | 用一个数据库承接全部不同负载 |
| 确定性研究层 | 指标、因子、事件研究、验证和复现 | SQL、Polars、TA-Lib、受控回测工具 | 让 LLM 自行算核心金融数字 |
| API/产品层 | 统一视图、查询缓存、联动和证据追踪 | Workers、现有 JS、图表组件、研究笔记 | 无限制地向浏览器暴露原始数据 |
| 报告/自动化层 | 固定数据窗口、证据包、结构化报告、重试 | AI SDK + 有界工作流 | 默认扩展为自主交易系统 |

### 3.2 必須区分四类数据

| 类型 | 示例 | 对产品和研究的影响 |
|---|---|---|
| 原始公开观测 | 交易所可见成交、区块交易、官方宏观发布 | 仍有接口覆盖、时间、权利与修订问题；“公开”不是“无条件再分发” |
| 可复算指标 | 固定规则 CVD、实现波动率、基差、链上部分统计 | 必须保存输入、算法版本、单位和窗口 |
| 估计指标 | 交易所/矿工实体流入流出、去内部转账的链上流量 | 依赖标签、聚类、启发式和更新；不是节点原生字段 |
| 商业或许可受限数据 | 完整历史 L2、部分期权历史、专有实体标签、付费新闻 | 要把权利、覆盖与费用纳入架构，不仅比较 API 易用程度 |

Glassnode 的 PiT 方法说明明确讨论了实体识别、后续信息和修正导致的历史变化，支持把链上估计指标与原始链上事实分层保存。[S25]

### 3.3 数据能力的最小可信定义

“支持 CVD”至少意味着有可解释的主动买卖方向、明确累计起点和缺口处理；“支持足迹”至少意味着逐笔或经说明的聚合成交、价格桶和数量单位；“支持订单簿”至少意味着快照与增量的序列恢复；“支持宏观回测”至少意味着发布时点与历史版本。

因此，“有一个字段/图形”并不等于“具有相应研究能力”。本报告优先推荐能让这四类定义成立的组件组合。

## 5. 重点候选深度分析（15 个主对象）

接入负担使用相对等级，不给无依据工期：**低**指单个只读接口或局部组件；**中**包括标准化、缺口处理和回放验证；**高**包括持续服务、多个运行环境、复杂迁移或授权谈判。同一项目的实际工作量仍取决于仓库现状。

### 5.1 CCXT：适合减少多交易所重复适配，不适合抹平微观结构差异

**问题与价值。** 多交易所的市场列表、OHLCV、交易、资金费率等接口适配适合复用 CCXT，而不是逐项手写。它支持 JavaScript/TypeScript 和 Python，契合现有技术背景。发布记录中可以看到与资金费率、清算字段相关的修正，说明“统一接口仍需持续校正交易所口径”，并不代表语义永远一致。[S08][S09]

**取舍与接法。** 首选在独立 Node 进程中试验 1—2 个公共接口。把 CCXT 返回值转换为自己的契约，同时保留原始字段和适配器版本。对订单簿序列恢复、交易所特有清算采样、期权细节，不让统一抽象覆盖原始协议。不能假设整个 Node 包未经处理就能在 Workers 中运行；是否存在包体、网络、运行时或方法支持问题需要构建和样本测试。

**授权、数据和维护。** 代码 MIT；上游数据限流、历史范围和再分发权利仍按交易所逐一管理。库本身不会带来免费全历史数据。发布页可见持续修正和多位贡献者，但本次未量化贡献集中度或运行其测试。频繁更新带来维护价值，也要求锁版本和回归样本，不能每天自动追最新版。

**结论。** **值得试验，中等负担；能力判断把握较高，现有仓库适配把握中等。** 多所需求明确时优先于重复手写普通 REST；只有 Binance、Deribit 且原有适配可靠时，不必为了统一而迁移。替代方案是原生轻适配；实验重点是数据一致性，不是接口数量。

### 5.2 Cryptofeed：实时标准化能力强，但许可和架构变更不允许“直接接上”

**问题与价值。** 适合持续接收多交易所实时事件并统一交给处理器；可借鉴交易所适配、异步消费、测试样本及后端分离。它不应被当作新的 REST 万能层，也不能替代历史数据采购和正确性验证。[S10]

**当前状态的关键区别。** CHANGES 标明 2.5.0 在 2026-08-08 有 Python/工具链及兼容性更新；主分支 3.0 记录涉及新的异步核心及删除 REST 等变化，但未据此确认 3.0 已正式发布。当前主分支许可证是 AGPL-3.0 或后续版本并带附加署名要求，不应沿用旧的宽松许可认知。[S11][S12]

**接法与边界。** 作为独立 Python 服务更自然，通过文件或 HTTP 输出给现有系统，不把 Python 采集器塞进前端或直接替代 Workers。AGPL 风险并不会仅靠“单独容器”自动消失，仍须按修改、交互和分发方式审查。数据条款继续由各交易所决定。

**结论。** **值得试验，但当前不列入默认采用组合。接入/长期负担中高。** 许可证事实把握高；具体版本稳定性和每个交易所兼容性未实测。可见核心维护者角色较集中，本次未量化完整分布。替代是原生小适配或 CCXT；若仅接一两个市场，新增 Python 运维和版本迁移可能不划算。

### 5.3 Binance 原生协议与公开归档：最合适的第一条验证链，不是完整微观结构数据库

**可以复用。** 公开归档适合历史 trades/aggTrades/klines 回补，原生 WebSocket 文档适合作为协议真值。现货公开归档从 2025-01-01 改为微秒，应按文件/接口来源显式记录时间单位，不靠位数猜测。[S05]

**必须实现而不能省略。** 本地盘口需要缓冲增量、请求快照、按更新 ID 衔接、发现断档后丢弃旧簿并重建；数量为零的档位要删除。初始快照深度和推送频率限制决定了你恢复的是“接口可见盘口”，不是完整订单生命史。`aggTrade` 也不是无条件的一笔独立成交；要保留聚合方式，避免把它与原生 trade 重复累计。[S04]

**数据边界。** USDⓈ-M OI 统计历史只有最近一个月；清算流存在每交易对每 1000 ms 最新一条快照限制。停机期间不能以当前接口自然补齐所有这些数据，也不能把已收集清算量命名为总清算量。合约口径或 UM/CM 字段变更需在锁定的接口契约中检查。[S06][S07]

**接法、权利与判断。** 原生只读接口 + 归档文件解析器 + 本地复算，是低依赖、中等正确性工程负担的方案。公开可下载不等于商业展示、转售、发给模型均获授权；本次未确认归档仓库所有脚本的明确代码许可，不建议整段复制未知授权脚本。**推荐采用为首个数据基准，外部协议事实把握高；地域可达、限流实况和实际历史文件覆盖待实验。** 替代是授权历史商；不要一开始扩到所有交易所。

### 5.4 Tardis：能购买“过去没有自行采集的历史”，但用途限制可能比技术更关键

**适合的问题。** 做历史 L2 回放、跨交易所对照或过去事件研究时，Tardis 比今天才开始的自采更直接。可复用 SDK 的标准化、异步迭代与回放接口。官方数据说明强调采集本地时间的作用，事件排序不能只依赖交易所消息时间。[S13][S14]

**代码与运行环境。** Node SDK 为 MPL-2.0。检索时主分支 manifest 见 18.2.1，声明 Node >=24.19、npm >=11.17；这是该分支环境声明，不是要求现系统立即升级，也不是已确认稳定发行版。更适合独立 Node 运行环境，不能假定 Workers 兼容。[S16][S17]

**费用与历史范围。** 当前 Academic/Solo 主要提供 CSV，Professional/Business 才包含原始回放 API 等能力。历史范围受套餐和计费周期约束，不能假设买一个月就解锁全部年份。检索页面中“全永续”Solo 为 700 美元/月、Professional 为 1,000 美元/月；这不是 BTC 单市场最低报价，也不包括税费或个别订单变化。对个人系统，数据费可能比计算费更值得先验证。[S18][S19]

**授权是硬关口。** 服务条款不是 SDK 许可证：内部使用、符合定义且满足条件的较低频衍生输出、第三方披露、AI/LLM 用途分别受限。条款 9.5 对通用 AI/LLM 相关训练、验证、评估等用途及向外部服务商披露数据提出额外限制，Coinbase 数据还有单独限制。具体云端推理是否获准需要按用途确认，不能把“不训练模型”当成自动许可。因此在没有明确许可前，不把 Tardis 数据或其派生指标输入云端 LLM，也不据此推出公开付费足迹服务。[S15]

**结论。** **值得试验，限于先核权利、再验覆盖；未授权 LLM 接入暂不采用。** 历史服务能力属于文档证据，完整率和恢复行为未实测，供应商 SLA 与团队集中度未审计。替代是原生归档、自采未来历史，或另行询价的授权供应商。不要为试验先订全交易所包。

### 5.5 Deribit：期权研究的起点是完整快照契约，不是增加一个 IV 数字

**价值。** 适合组织期限、行权价、看涨/看跌、买卖报价、标记价格、指数价格、持仓量和隐含波动率的观测，为期限结构、偏斜、基差及流动性研究服务。原生接口比泛化接口更有利于保留衍生品字段。[S20]

**重要口径。** 官方 `get_order_book` 对 OI 单位有区分：永续及反向期货可按美元表达，期权和线性期货按基础币表达。不能把“open_interest”作为无单位通用列直接相加。合约乘数、计价/结算币、到期时间和数据时间必须一起保存。[S20]

**接入策略。** 先做固定频率、带批次 ID 的期权链快照，而非立即构建高频全曲面。保存每个 instrument 的采样时间，避免把分批抓到的多个截面当成同一瞬间。对无双边报价、过宽价差、零买价、异常 mark 设置质量标记；由确定性程序选择和计算，LLM 只解释。

**未确认项与结论。** 本次未充分核验各 WS raw/聚合频道的认证边界、当前实际限流、完整期权历史及再分发条款；不能宣称免费多年全链历史已具备。官方协议持续可读，但服务稳定性和维护团队分布不在本次可核范围。**推荐采用原生快照契约，曲面和高频流值得试验；中等接入负担、长期数据完整性维护中高。** 替代是授权历史供应商或减少到固定期限/行权价样本。

### 5.6 DuckDB + Parquet/R2：首选的“可复算研究底座”，不是万能在线数据库

**解决什么。** 把不可变原始/标准化文件作为事实底座，DuckDB 负责批量 SQL、窗口运算、分组研究和报告输入计算；D1 不再承担所有事件扫描。官方文档支持读写 Parquet 和通过 S3 兼容方式访问 R2。[S21][S22]

**为什么比直接上大数据库更合适。** 这是架构推断：初期以单人、少量分析任务为假设，文件层便于迁移和重算，计算进程容易隔离。Polars 可处理复杂变换，但不要同一指标同时维护 SQL、Polars、前端 JS 三份实现。

**边界。** DuckDB 嵌入式文件的并发模型不能理解为通用多进程共享写入服务器；官方也有新的远程/目录方案，具体模式要区分。本方案明确采用“一个受控写入/生成进程 + 不可变文件 + 只读分析”，不依赖未验证的多写者能力。实时浏览器推送通过预计算聚合/API 完成，不直接扫描全部原始对象。[S23]

**维护、授权、成本。** DuckDB MIT、Polars MIT；数据权利不变。DuckDB 发布页见 v1.5.5，可见修复和持续发布；本次未运行相关测试和 R2 端到端性能测试。R2 是计费服务，文件大小、请求次数、缓存和扫描范围影响成本，不能只计算 GB 单价。[S60][S03]

**结论。** **推荐采用为混合路线的分析起点；中等首次接入、相对较低常态运维。** 方案适配把握中高，实际查询延迟未知。若持续并发查询或数据新鲜度目标无法达到，再比较 ClickHouse/QuestDB；不是遇到一次慢查询就迁库。

### 5.7 ClickHouse：为已证明的连续写入与并发分析买复杂度

**价值。** 当大量增量写入、多个工作区并发、长区间聚合查询成为常态时，可作为在线研究结果与事件分析数据库。它应替换已被测量为瓶颈的查询路径，而非替换原始文件留存。[S61]

**关键风险。** `ReplacingMergeTree` 的后台合并不能视为写入后即时唯一约束。采集至少一次投递时，需要明确事件键与版本，查询按场景使用去重策略；不能让重复成交污染 CVD，再期待后台合并自动“恢复真值”。[S62]

**实质比较。** DuckDB 优先满足单进程批量研究；ClickHouse 更值得用于持续服务化分析；QuestDB 可作为金融时序/as-of 查询的对照；TimescaleDB 对已有 Postgres 经验和业务关系查询更有吸引力。后两项具体性能没有实测，不采用官方自报 benchmark 作优劣结论。

**维护与许可。** ClickHouse Apache-2.0；检索发布页的 Latest stable 为 26.6.7.18，同时存在 26.8.4.11-lts，不能把最大版本号等同推荐版本。QuestDB 开源核心 Apache-2.0；TimescaleDB 必须按 Apache 与 `tsl` 目录分别核许可。[S63][S64][S65]

**结论。** **值得试验，当前不默认部署；接入/常态运维高于 DuckDB 路线。** 数据库能力把握较高，是否值得本系统承担运维把握有限。新增备份、容量、分区、版本升级和查询监控有真实成本；未证明延迟/并发收益前应停止投入。

### 5.8 Lightweight Charts：可以直接复用的显示层，但不会提供研究可信度

**价值。** 适合 BTC K 线、价格、成交量、技术指标及研究结果叠加。JS 前端可局部接入，不要求整个站点重写。它与 TradingView 的其他商业图表产品不是同一许可和能力包，也不附送行情。[S26]

**哪些不应假定。** 足迹价格桶、盘口热力图、CVD 的原始数据与计算逻辑仍需自建或选择组件；自定义渲染不是“开箱已有正确足迹”。图形层只消费统一查询 API，不能自己直接连交易所并计算另一份指标。

**维护/许可。** 检索发布页见 5.2.1，包含十字线标记等修正；代码 Apache-2.0，README 要求相应 NOTICE/TradingView 署名链接。可见厂商维护背景，但本次没有量化贡献集中度、浏览器回归或性能上限。[S26][S27]

**结论。** **推荐采用或保留；局部接入低、定制足迹中高。** 前提是现有图表确有缺失或已有该组件需要保守升级。替代为 KLineCharts；选择标准应是同一研究任务的准确性与操作次数，不是截图风格。

### 5.9 KLineCharts：绘图与指标操作值得对照，但不应再造一套数据层

**价值。** 中文官方文档和面向 K 线的交互适合国内个人开发者验证绘图、指标配置和标注工作流。若现有组件中绘图工具维护困难，它是具有实际相关性的替代。[S28][S54]

**维护与接入。** 本次发布页可见稳定版 10.0.3 及覆盖物层级修正；不能混用此前 beta 的 API 认知。代码 Apache-2.0，适合浏览器局部依赖。完整贡献者分布、锁定版本测试状况和在现有 CSS/事件体系下的兼容性未核。[S28][S29]

**取舍。** 不同时长期维护两套金融图表以追求功能大全。以相同 OHLCV、同一缺口样本、同一十字线时间同步和同一足迹价格桶做对照，比较缩放、标注保存、长数据更新、移动端行为及自定义图层难度。

**结论。** **值得试验；中等迁移负担，数据许可仍由上游决定，组件不提供免费历史。** 若用户完成研究任务没有更快，或需要为它重做全部数据模型，应保留现有图表。替代包括继续使用已有组件和仅修复交互。

### 5.10 mempool：补齐链上语境，不能直接获得实体资金流真值

**价值。** 适合给 BTC 研究补充区块、手续费、拥堵、矿工相关观测的上下文；优先消费允许用途内的 API 或借鉴视图，避免起步就维护完整浏览器栈。[S30]

**做不到什么。** 全节点能提供链上交易事实，但“交易所流入”“矿工卖出”“大户在抛售”通常还需要地址标签、实体归属和行为推断。把可见链上转移等同经济买卖，会使报告看似专业却不可证。[S25]

**授权与替代。** mempool 当前许可为 AGPL-3.0 并明确不授予商标权；代码、托管 API 与品牌使用是三个不同问题。Esplora 本仓库许可是 MIT，不能与索引器 electrs 等依赖混为一谈。Bitcoin Core 可在更长期的原始链上研究中独立评估。[S31][S66]

**维护/负担/结论。** mempool 发布页见 3.3.1，之前版本有后端/API及前端工具链更新，可见多位贡献者；本研究未运行节点或索引。**值得试验：API 接入中低，自建完整服务高。** 若没有需要自行复算的具体链上研究，使用适当授权的 API 比复制全套系统更合适；若公开 API 无授权或无稳定保障，则降级显示，不伪造实时性。

### 5.11 Coin Metrics Community：适合方法探索，不可直接成为收费产品数据底座

**价值。** 提供链上和市场数据的社区子集，适合先验证某项指标是否有解释力、与本地计算是否一致，也能作为契约设计参考。公开仓库/接口不能被理解为全部商业指标均免费。[S24][S67]

**授权与覆盖。** 官方 Community 页面明确 CC BY-NC 4.0。API、仓库下载和数据集子集的具体可用范围需按资产/指标查目录，不能把某一类接口的 30 天限制推广到全部数据，也不能假设所有 BTC 指标都从创世完整提供。代码或下载工具的许可不会移除 NC 限制。

**接法与维护。** JS 通过 HTTP 拉取、独立计算进程导入均可；保存字段、单位、来源版本、观测时间和抓取时间。属于持续数据服务而非一个可凭发布版本判断维护状态的包；本次没有验证实际日更完整率、限流、服务承诺或维护团队集中度。

**结论。** **值得试验，限于符合授权的非商业研究；接入低，覆盖/许可管理中等。** 商业化之前需要取得对应权利、换来源或自行复算可复算部分。替代不是“另找一个偷偷转发同一数据的免费 API”。

### 5.12 FRED/ALFRED：应成为宏观研究的默认时点性规范

**价值。** FRED 当前值适合今天的宏观描述；ALFRED 的 vintage/实时区间机制适合回到历史当时可获得的数据。官方说明指出默认实时区间面向现在，历史研究应主动指定区间或版本。[S33]

**接法。** 每个序列保存频率、单位、季调标记、观察日期、版本日期、实际获得时间和来源。观察月份不是数据发布时间，修订日期也不一定能提供足够精确的日内可见时间。只有日期而无可信发布时间时，在日内事件研究中保守处理并明确不确定性。

**数据权利与成本。** 官方 API 接入不等于所有序列均可自由再分发，第三方提供的序列仍有自己的限制。缺少版本覆盖的序列不能由最新版逆推“当年最初公布值”。本次未审计每一条拟使用序列，也没有将某个未知免费调用上限写成保证。[S34]

**维护与结论。** 官方长期方法文档是强证据，但没有实际 API 连通/额度测试；维护团队集中度不适用软件项目式评分。**推荐采用，低中接入、中等时间口径治理负担，方法适配把握高。** 替代为原始发布机构的历史发布档案；不能退回仅用 yfinance 最终值做所谓实时宏观回测。

### 5.13 OpenBB：最值得拆解的是 provider 思路，不是整体替换已有系统

**价值。** 它将金融数据适配、标准化模型和 API 组织成平台，可用于减少部分跨资产适配重复工作。值得复用的是特定 provider 和数据对象边界；需先确认实际使用的来源支持什么接口，而不是把项目“支持很多数据源”的宣传理解为每个来源稳定可用。[S35]

**运行环境与范围。** 开源后端 Open Data Platform、Desktop 与企业 Workspace 不是同一个交付物。本次发布页见后端 4.7.0 和 Desktop 1.0.2，不能把桌面最新标签当成所有后端 provider 已更新。Python 服务可向 Workers 提供小型 API，但会引入新的依赖和故障路径。[S36]

**许可与数据。** AGPL-3.0；Workspace、外部数据商、provider 的 API key 和商业使用权都要分别审查。仓库开源并不提供 Yahoo、新闻或交易所数据的再授权。完整搬入平台还可能与现有标准化、任务系统重复。

**结论。** **值得试验一个确有价值的 provider；整体替换暂不采用。** 单 provider 中等负担，整个平台高。可见组织化发布，但维护质量仍分 provider，本次未量化贡献集中度或运行其全部测试。替代是直接来源 API；只有确实节省持续适配工作，才保留这一层。

### 5.14 vectorbt：帮助快速研究，但不能用快回测替代有效验证

**价值。** 适合固定数据集上的因子探索、参数对照、事件条件分组和向量化实验。对于当前分析系统，目标是检验解释是否稳健，而不是默认接自动执行。[S37]

**当前许可和维护。** 检索时许可证是 Apache-2.0 加 Commons Clause，不能称其为无条件可商用的纯 Apache 库。1.1.0 发布包含 Python/pandas/NumPy 兼容和相关实现更新，说明不能凭旧版本记忆认定停更。可见核心作者角色突出，但未量化维护集中度，也未运行新旧实现一致性测试。[S32][S38]

**必须另外承担的工作。** 保存试验次数与参数搜索范围；训练/测试按时间分离；只在训练集拟合标准化与状态模型；评估标签窗口重叠、手续费、点差、滑点和资金费用。框架的快速遍历会放大反复试到好结果的风险。PBO/DSR 论文提供针对选择偏差、多重试验的分析方法，但不能替代真正样本外数据与合理实验设计。[S39][S40]

**结论。** **值得试验，仅在用途许可明确后；研究实现中等、验证维护中高。** 若只需要事件前后收益和条件统计，DuckDB/Polars + 简单明确的计算已经足够。NautilusTrader 借鉴事件回放，Freqtrade 借鉴 lookahead/recursive 检查，不引入其完整交易平台。[S41][S42]

### 5.15 Vercel AI SDK + 有界工作流：优先约束证据，再考虑代理复杂度

**价值与接法。** 用现有 JS/TS 技术组织模型适配、流式输出、工具参数和结构化结果，比先引入多语言代理平台更直接。AI SDK 为 Apache-2.0；本次发布页见 ai@7.0.101。Cloudflare 有官方 AI SDK 集成资料，但文档示例与 SDK 大版本之间仍需配对验证，不能把示例视为已在此仓库运行。[S43][S44][S45]

**普通程序应完成。** 数据拉取白名单、单位转换、指标、时间窗口、聚合、数值校验、授权检查、重试、成本限额、证据 ID 解析。LLM 负责解释异常、整合互相矛盾的证据、提出待验证假设、整理报告。它不应生成或修正权威数值，更不应为了补全叙述擅自扩大时间窗口。

**工作流。** 建议单个有界流程：“冻结数据截止点 → 生成确定性证据包 → 检查可披露权限 → 调用模型 → 校验结构和数值引用 → 保存报告/拒绝发布”。Workflows 提供持久步骤，Queues 可解耦缓冲，但其至少一次投递要求幂等处理；不能把 `waitUntil` 当作完整长任务引擎。[S46][S47]

**替代与维护。** 当研究主体已转为 Python，PydanticAI 值得试验；只有真实存在人工中断、多分支状态、可恢复协作，才考虑 LangGraph。Langfuse 可用于追踪和评估，但核心 MIT 与 ee/云服务应分开审查，自建观察栈会增加维护成本。厂商/社区持续维护不等于具体模型输出可信，版本升级必须重放自己的报告测试集。[S48][S49][S50]

**结论。** **推荐采用类型化、带证据、有预算的单工作流；SDK 可用现有等价实现替代，多代理暂不采用。** 代码接入低中，评估体系中等。模型服务条款、推理费用和输入数据许可另审；本次未比较实际模型价格/延迟，不能给出每篇报告的真实成本。

## 6. 面向本系统的三条架构路线

以下是条件性设计，不是对现有实现的诊断。选路线的输入应该是数据粒度、历史规模、查询并发、新鲜度目标和维护预算，而不是项目年龄。

### 6.1 路线 A：保守演进——以 Cloudflare 为主

```text
来源 REST / 授权文件 / 现有可靠采集
        ↓
Workers 定时入口 / 必要的 Workflows
        ↓
校验与标准化 → D1 元数据/适量聚合 + R2 原始批次
        ↓
Workers 查询与缓存 → 现有 JS 图表
        ↓
冻结快照 → 确定性指标 → 有证据报告
```

适用前提：以分钟、小时、日频为主，报告批次数可控，长时间连续逐笔/深度回放不是核心需求。收益是保留最多代码、账号和部署习惯，避免维护一台长期运行的服务。

风险是试图把重型历史计算、持续交易所长连接和大量原始事件写入都塞入边缘层。D1 单库限制、Workflows 步骤资源/保留期、出站 WebSocket 不能休眠都需要核对。[S01][S02][S46]

**迁出触发条件：**代表性任务稳定超出实际资源边界；可靠连续采集依赖不适合的执行生命周期；历史扫描成为可重复的瓶颈。没有这些证据，不必为了“金融平台架构”新增后端。

### 6.2 路线 B：渐进式混合架构——有高频需求时的首选

```text
Binance / Deribit / 其他获准来源
        ↓
一个独立 Node 或 Python 数据服务
  ├─连接与恢复、序列检查、历史回补
  ├─原始批次 → R2
  ├─标准化 Parquet → R2 / 本地受控缓存
  └─DuckDB 分析 → 聚合结果 / 证据包
                         ↓
Cloudflare Workers API / 缓存 / 任务入口
  ├─D1：配置、manifest、任务、报告索引、笔记
  ├─R2：获准保存的原始文件、快照、报告正文
  └─现有 JS：图表、工作区、证据追踪
                         ↓
有界报告工作流 → 结构与数值校验 → 报告历史
```

**首选原因是可撤回，不是技术更新。** 可以先接一个独立数据源，用稳定 API 或文件契约向旧系统提供结果；功能对照通过后才逐步切换。控制面、展示面不必陪着数据计算一起迁移。

独立服务初期只选择 Node 或 Python 一种主要运行环境：现有 JS 复用优先时选 Node；研究计算和依赖明显偏 Python 时选 Python。不要为每个候选另建服务。原始文件是恢复基础；本地分析缓存丢失后应能重建。

**主要成本：**新增主机或容器、磁盘、备份、采集健康监控、部署和安全边界；跨服务契约与故障处理。收益是否抵得过这些成本由第 9 节实验判断，不以“架构更标准”为依据。

**适用前提：**逐笔/CVD/盘口/期权历史确实重要；数据授权允许所需保存和处理；有人承担长期进程维护。否则路线 A 更合适。

### 6.3 路线 C：较大重构——传统后端主导，前端与边缘层可保留

```text
来源 → 持续采集进程 → 标准化/质量 → 对象存储 + 分析数据库
                                  ↓
                        后端 API / 调度 / 研究计算
                                  ↓
                      前端工作区 / 报告 / 受控分发
```

该路线可以从单体后端加独立任务进程开始，不等于必须微服务化。关系元数据可在真实需求下考虑 Postgres；在线分析库在测量后选择 ClickHouse、QuestDB 或其他方案。Cloudflare 仍可保留 CDN、前端托管或入口防护，不必全盘退出。

**适用条件：**数据服务已经承担系统主要工作；团队能够运维；需要统一后端资源/网络策略；现有数据和业务耦合确实阻碍安全演进；混合方式造成的长期重复复杂度大于迁移成本。

**不应触发它的理由：**文件看上去旧、代码量大、用了原生 JS、想使用某个新框架。

### 6.4 比较表与明确选择

| 维度 | A 保守演进 | B 混合架构 | C 较大重构 |
|---|---|---|---|
| 最合适的需求 | 分钟/日频看板、宏观报告 | 逐笔/盘口/回放 + 云端报告 | 数据密集、多用户、团队化研究 |
| 新增运维 | 低 | 中：一个主要数据服务 | 高：后端、数据库、任务及迁移 |
| 保留现有代码机会 | 最大 | 大 | 取决于当前耦合与接口设计 |
| 数据分析弹性 | 受平台与执行边界约束 | 高，计算可单独调整 | 高，但成本和职责也更多 |
| 主要迁移风险 | 未改变的数据错误继续存在 | 两条数据链结果漂移、契约破坏 | 同时改变数据/业务/前端难以归因 |
| 推荐顺序 | 低频场景首选 | 高频研究场景首选 | 获得明确证据后的选项 |

**本报告的条件性首选是 B，不是立即重构的决定。** 首先按路线 A 的方式盘点与补契约，再以一个独立数据服务验证 B 的必要性。若没有高频和历史回放价值，停止新增服务。

### 6.5 资源与费用：只给已核验单价，不假装已有系统账单

截至检索日，Cloudflare Workers 付费计划最低为 5 美元/月；R2 Standard 存储标价 0.015 美元/GB·月，Class A 为 4.50 美元/百万次、Class B 为 0.36 美元/百万次，互联网出站流量不另收 R2 egress 费，另有免费额度与计费规则。**这些不是整个系统成本。** 还需计算独立计算服务、其他请求与服务、数据订阅、模型、日志及维护投入。[S03][S59]

建议用实际样本估算：

```text
原始日数据量 ≈ 实测平均事件/秒 × 实测平均编码字节 × 86400
文件存储预算 = 原始层 + 标准层 + 衍生层 + 必要副本/保留期
月总成本 = 托管/CPU/磁盘 + 对象操作 + 数据授权 + 模型 + 监控备份
```

不能用交易所数量代替事件率，不能未经测量假设压缩比，也不要每个 tick 上传一个对象。批次大小应同时考虑恢复粒度、对象操作数、查询裁剪和文件过小问题。主机供应商与地区未确定，本文不编造一笔“每月几十元肯定够用”的报价。

## 7. 高价值能力组合：从原始数据到可复核结论

### 7.1 先固定六种数据契约

| 契约 | 建议最少字段/规则 | 防止的具体错误 |
|---|---|---|
| Instrument | venue、市场类型、原始代码、基础/报价/结算币、线性/反向、乘数、tick/lot、到期与生效区间 | 把 BTCUSDT 现货、永续、反向合约或期权混为一类 |
| 原始事件 | source、source_event_id/sequence、原始 payload、source_ts、received_at、schema_version、原文件定位 | 无法恢复来源语义或定位采集故障 |
| 标准化成交/盘口 | 价格、基础数量/合约数量、名义金额、主动方向、序列范围、质量标记 | 买卖方向颠倒、合约量与币量混加、漏包后继续画假盘口 |
| 低频观察与修订 | observation_date、published_at/known_precision、available_at、vintage、value、unit、revision_of | 把未来修订值放回过去，或把观察月份当发布时间 |
| 衍生指标 | method_id/version、参数、窗口、输入 dataset_id、数据覆盖、计算时间、单位 | 前后端结果不同却无法判断哪份正确 |
| 报告证据 | report_id、cutoff、dataset/version、evidence_id、来源链接、数值定位、许可标签、生成模型/模板版本 | 报告看似有引用，实际无法找到对应数字和时点 |

这些是建议的内部契约，不声称交易所直接提供所有字段。没有可信发布时间时填“未知/精度为日期”，不要把抓取时间伪装成发布时间。原始记录允许保留供应商字段差异，不为了统一而丢失信息。

**时间与数字原则。** 内部使用 UTC；保留原始时区和单位；展示毫秒不覆盖原始精度。纳秒和某些长 ID 可能超过 JS 安全整数范围，可用十进制字符串/BigInt 跨层传递；价格和数量按明确精度处理。微秒时间戳不能与毫秒接口直接拼接。[S04][S05]

### 7.2 组合一：可信订单流工作区

```text
Binance 原生 trades/depth
 → 序列恢复与原始留存
 → 标准化成交/盘口
 → 确定性足迹、CVD、价差/深度指标
 → 联动图表 + 质量条 + 异常事件
 → 固定窗口解释报告
```

**足迹定义。** 每个价格桶分别聚合主动买量和主动卖量。明确桶宽、锚点、窗口、原始成交还是聚合成交、数量单位和日/session 划分。Binance 中 buyer-is-maker 为真对应买方挂单、卖方主动；原生与聚合成交不能重复算。[S04]

**CVD 定义。** 用已明确主动方向的成交量累计差值；每个市场单独计算，并显示累计起点与缺口。跨交易所合成时先统一名义单位和来源覆盖，名字必须体现“所选市场观测 CVD”，而非“比特币全市场真实资金流”。价格/稳定币换算是显式方法，不默认 USDT 与 USD 永远可无损互换。

**盘口和清算。** 盘口缺序列就标记不可用并恢复，不靠插值“补盘口”。订单簿数量减少可能由撤单或成交等原因造成，不能直接命名为卖压成交。清算是单独的可见事件序列，不能替代全部成交或真实持仓损失。[S04][S07]

**产品验收重点。** 图表某个异常柱能回到对应成交批次；切换聚合窗口不会改变同一范围的总量；重放相同数据得到相同结果；缺口不会悄悄消失。

### 7.3 组合二：衍生品压力与期权结构研究

最小组合是 **资金费率 + 基差 + OI + 可见清算 + 期权快照**，但不建议立即压缩成一个不透明“多空分”。

资金费率区分预测与已结算、费率与结算间隔；跨所比较应先转成明确的可比口径。基差区分永续、交割合约和现货基准，年化算法及剩余到期时间写入方法版本。OI 是存量，不把 `ΔOI × 价格` 直接说成净新增资金；线性、反向及期权单位先转换再讨论。[S06][S20]

期权先显示可信报价截面、期限结构与观测覆盖，再研究固定 delta 偏斜、曲面拟合或定价模型。合成曲面必须公开样本筛选、报价时间分散程度、插值与外推。缺少可成交双边报价时，不能将 mark IV 当作同等可信的可交易价格。

一个有意义的报告问题是：“本次价格变化是否伴随杠杆、期限结构或流动性的同步变化？”而不是“这些数据证明下一小时必涨”。后者需要额外预测验证，本报告没有做出此类效果声明。

### 7.4 组合三：链上、ETF、稳定币与宏观证据面板

**链上层次。** 区块/手续费等原始统计先行；自有可复算指标要说明链状态、价格序列和处理规则；交易所和矿工实体流量额外保存标签版本与置信度。PiT 思路适合借鉴，但不能假设商业标签历史永远不变。[S25]

**ETF 管道。** 发行人披露的份额、资产、持仓与日期可作为交叉核验基础，Farside 等汇总仅作第二来源。份额变化乘 NAV 可作为有假设的估算方法，但 AUM 变化还包含价格与其他影响，不能直接称作净申购。发行人数据字段存在并不等于所有发行人都有完全相同的日内披露口径。[S68]

本次抓取 Farside 页面时，2026-09-15 行出现个别基金为“-”而合计为 0.0 的状态。**这是很具体的解析陷阱：不能把页面的 0.0 合计直接解释成已完整确认的零流入。** 应保留各成分到齐状态及抓取时间，之后版本也不能覆盖当时所见快照。[S69]

**稳定币。** 参考 peggedassets 适配思路，先明确原生发行、跨链映射、锁定/赎回和供应变化口径，防止跨链资产重复累计。供应增加不是 BTC 买盘的同义词；商业展示或移植代码前核验对应仓库与 API 的授权，本次未确认该仓库完整许可。[S70]

**宏观与跨资产。** 用 FRED/ALFRED 管理政策利率、美元/利率相关序列及发布版本；跨资产按共同可观察时点对齐。股票休市时，不把沿用的旧收盘价当作周末新价格。Yahoo/yfinance 可作研究辅助，但未经稳定性和权利核验不作生产唯一源。[S33][S34][S53]

### 7.5 组合四：舆情先做“事件与来源”，不要先做一个情绪分数

推荐从央行/监管/交易所/ETF 发行人等原始发布的链接与许可允许的摘要，以及 GDELT 的新闻发现能力开始。GDELT 官方 DOC API 文档提供新闻检索与时间线思路；其服务的历史查询覆盖、实际召回、延迟需另测，开放索引不代表新闻全文可任意复制。[S71][S72]

每条事件保存 `event_time`、`published_at`、`first_seen_at`、来源域、原文链接、事件类型、是否修订、重复报道簇。先解决转载重复、来源层级与发布时间，再让模型分类主题/倾向并标注不确定性。新闻量变化可能是采集覆盖变化，不一定是市场关注度真实变化。

X 当前官方采用按量计费的 API 体系；本次没有接入账号，也不引用旧套餐价格。Reddit 现行 API 条款对商业使用、数据保留与模型训练等有独立要求，不能通过第三方开源爬虫绕过。[S73][S74]

**采用边界：**事件发现值得试验；未经授权的全量社媒存储、商业舆情转售、声称情绪模型有预测能力暂不采用。没有可靠召回与去重评估前，不推出“全网情绪指数”。

### 7.6 组合五：证据驱动的 LLM 报告

建议证据包与文字报告分开保存。一个概念结构如下，字段是设计示例，不是已实现 API：

```json
{
  "report_id": "...",
  "cutoff_utc": "...",
  "snapshot_id": "...",
  "window": {"start": "...", "end": "..."},
  "facts": [{
    "evidence_id": "E001",
    "metric": "venue_cvd",
    "value": "...",
    "unit": "BTC",
    "dataset_id": "...",
    "method_version": "...",
    "quality": "complete|partial|unavailable",
    "allowed_uses": ["internal_display"]
  }],
  "limitations": ["..."],
  "model_config_version": "..."
}
```

`allowed_uses` 只是内部政策标签，不会自行创造法律授权。来源允许保存，但不允许外部推理时，应在模型调用之前拦截；“只发计算后的数”也未必能解除衍生数据条款。[S15]

报告按“事实—解释—假设—反证—局限”组织。数值由证据键引用，校验器检查指标、单位、方向、时间窗口；语法正确的 JSON 仍可能事实错误。没有数据就输出缺失，不让模型找一个相近但不同时间的数补位。

检索和工具均设白名单及只读权限；外部文章/帖子内容当作不可信数据，不允许它们改变系统指令、请求秘密或触发交易。报告接口不拥有下单权限。LLM-as-judge 可协助检查可读性，但数字、覆盖和引用存在性必须由程序验证。

### 7.7 研究计算与复现：最低要求而非自动交易扩张

| 风险 | 最小防范机制 | 不足以证明什么 |
|---|---|---|
| 前视偏差 | 所有输入 `available_at <= cutoff`；ALFRED vintage；延迟到达处理 | 不能仅凭字段名判断数据当时已知 |
| 数据泄漏 | 训练集拟合缩放/阈值/状态模型；按时间切分；重叠标签隔离 | 一次随机拆分高分不代表未来有效 |
| 幸存者偏差 | 历史 instrument 清单、生效/到期区间；不只用今天仍活跃合约 | BTC 单资产也有合约存续选择偏差 |
| 过度试验 | 记录所有候选与搜索范围；锁定规则后再验证；参考 PBO/DSR | 一个漂亮夏普值不证明稳健 |
| 状态识别偷看未来 | 线上使用截至当时的过滤状态，不把全样本平滑结果当实时状态 | HMM/聚类标签不天然具有可交易意义 |
| 指标递归/预热 | 增长前缀重算、不同 warmup 对照、黄金样本 | 同名 RSI/EMA 不一定实现相同 |
| 不现实的收益模拟 | 手续费、点差、滑点、资金费用、交易时点与可用报价 | K 线收盘价信号不能默认同时成交 |
| 不可复现 | 数据版本、方法版本、参数、样本期、报告 cutoff、环境清单 | 仅保存 notebook 截图不够 |

PBO/DSR 与 Freqtrade 的偏差检查提供可借鉴的方法，不是自动给研究盖上“无偏”认证。事件研究先预声明事件集合、比较窗口与基准，相关性结论和因果解释分开。这里需要的是可信的研究验证，不是必须接入券商或交易所下单。[S39][S40][S41][S42]

### 7.8 基础工程：每项机制必须对应一个真实故障

| 机制 | 要防止的实际故障 | 最小实现与维护代价 |
|---|---|---|
| 唯一事件键 + 幂等任务键 | 重试/至少一次投递导致成交和报告重复 | 规则、唯一索引/账本、重复统计；不要只相信队列去重 |
| 序列检查与快照重建 | 网络断线后盘口继续沿用旧状态 | 采集器内状态机；每来源维护恢复样本 |
| 日期/分区 manifest | “有一个文件”被误认为整天完整 | 开始/结束、行数、校验和、缺口、完成状态；失败分区可重跑 |
| schema 与单位测试 | 上游字段变化、毫秒/微秒切换 | 锁版本样本和契约测试；未知字段保留，必要字段异常隔离 |
| 数据新鲜度/覆盖率 | 界面正常但数据实际停止 | 每来源 last-success、延迟、缺口数；不用泛化服务器在线率替代 |
| 有限重试、退避、失败隔离 | 上游限流后请求风暴或永远卡住 | 按来源预算、停止条件、死信/失败表 |
| 快照键缓存 | 不同 cutoff 的历史报告被同一缓存覆盖 | key 包含数据/方法版本、参数和时间；旧数据明确 stale |
| 冷启动与预计算 | 每次开图都重算全历史 | 预计算常用聚合，缓存可重建；先测瓶颈再增加常驻预热 |
| 恢复演练 | 备份存在但数据恢复不了 | 用小分区删除缓存重建、重放任务；无需一开始灾备集群 |
| 成本/权限限制 | LLM 递归工具循环、原始数据外泄 | 调用预算、超时、只读白名单、权限标签、秘密隔离 |

Queues 的至少一次交付和不保证全局顺序使幂等与序列处理成为应用职责；Workflows 自身保留期也不能替代报告长期归档。[S46][S47]

## 8. 分阶段路线图：按证据推进，不按技术数量推进

以下阶段不承诺周数。先确定每阶段的交付物和停止条件，再结合真实仓库估算工作量。

### 8.1 近期：建立可验证基线，不先迁库

| 工作 | 依赖 | 交付物 | 验收条件 | 停止/降级条件 |
|---|---|---|---|---|
| 现有能力与数据盘点 | 只读代码、配置、账单和数据样本 | 来源/指标/任务/权限/数据规模清单 | 每个界面数字能指向来源和计算位置 | 未知项明确挂牌，不用猜测补表 |
| 锁定一条 BTC 数据链 | 一个市场、一类成交与深度样本 | 原始样本、标准化契约、重放器与黄金结果 | 重跑稳定；重复与断档可识别 | 无原始数据则只验证未来采集，不伪造过去足迹 |
| 报告证据包 | 已确认的现有指标和快照 | 事实包、数值引用、报告版本历史 | 关键数字全部可定位；缺失会降级 | 数据权利不允许外部推理则不传模型 |
| 图表质量标记 | 来源延迟/缺口统计 | 新鲜度条、覆盖提示、证据入口 | 数据停止时不继续显示“实时” | 没有研究收益不换图表组件 |

### 8.2 中期：完成研究闭环，按实验选择新增服务

| 工作 | 依赖 | 交付物 | 验收条件 | 停止/降级条件 |
|---|---|---|---|---|
| 独立采集/分析服务 | 高频需求与实验 1、2 结果 | 一个主要运行环境、分区文件、查询契约 | 能独立恢复；前端不直接依赖供应商 | 保守路线已足够，则不增加长期服务 |
| 宏观/ETF 当时可见性 | 版本/发布时间来源 | vintage 管道、快照、as-of 查询 | 历史截止后数据不会进入过去报告 | 只有最新版时禁止宣传历史实时回测 |
| 衍生品研究面板 | instrument 与单位契约 | 资金费率/OI/基差/期权质量视图 | 单位统一、过期合约保留、缺失可解释 | 历史覆盖不足则缩小期限/市场范围 |
| 研究实验注册 | 确定性指标和固定数据集 | 参数/样本/验证记录、基线对照 | 所有试验可重放，样本外规则预先确定 | 无稳定增量价值则停止增加复杂因子 |
| 工作区与笔记 | 用户真实研究任务 | 联动图表、事件、证据、笔记 | 比旧流程更快定位问题；标注可恢复 | 仅视觉更好、操作更慢则回退 |

### 8.3 长期：只为已证明的收益增加复杂度

| 可选方向 | 前置证据 | 交付物与验收 | 停止条件 |
|---|---|---|---|
| ClickHouse/QuestDB | DuckDB 方案持续不满足实测并发/新鲜度 | 同一数据同一查询对照，正确性一致且延迟/成本有净收益 | 优化分区或缓存已解决问题 |
| 自建 Core/索引器 | 具体链上指标需要自行复算，托管来源不满足权利或覆盖 | 可恢复索引、重组处理、明确方法版本 | 无研究使用或维护负担压过收益 |
| 采购完整历史/标签数据 | 明确历史问题、覆盖样本与权利确认 | 数据验收、授权范围、预算与退出方案 | 无可接受商用/模型使用权或没有增量研究价值 |
| 更复杂期权模型 | 已有质量良好的期权快照和基线 | 固定报价筛选与样本外误差对照 | 主要误差来自脏数据而非模型 |
| 多代理或 Dagster 等编排 | 单流程存在真实的分支、恢复或人工审批难题 | 故障恢复/成本/完成率优于简单方案 | 只是增加角色和对话轮数，没有可测改善 |

## 9. 优先验证的五个小范围实验

**以下都是提议的实验，没有在本次研究中执行。** 成功标准是项目待采纳的验收要求，不是已经测得的结果；涉及付费数据、账号和采集的步骤需要另行授权。

### 实验 1：一条成交/盘口链能否正确回放

**输入：**一个 BTC 现货市场的有限、允许使用的成交与深度样本；相应快照；可取得的归档对照。优先用已存在的只读样本，没有样本时后续再获准采集。不得用 K 线合成“真实逐笔”。

**步骤：**保存原文；构建标准化记录与序列状态；计算固定窗口成交量、足迹、CVD；人为注入重复、乱序、缺口、断线和时间单位混淆；重新运行并对比结果。

**成功标准：**相同输入的结果一致；重复不增加总量；已知缺口全部被发现并暂停受影响指标；恢复后可回到有效状态；未破坏样本范围内的成交聚合与基准一致，差异能归因到明确口径。不要要求无法由接口保证的“每条市场事件全部收到”。

**失败处理：**不发布受影响足迹/CVD；拆分原始数据问题和适配器问题；保留来源限定标签；跨所扩张停止，先修单链。

### 实验 2：是否真的需要独立分析服务或 ClickHouse

**输入：**真实代表性只读数据副本、现有数据库索引信息、常用查询（如一天足迹、一段区间聚合、报告快照、多个面板并发），以及事先写下的响应时间/预算目标。

**步骤：**在允许的实验环境中对比现有 D1 路径、Parquet/DuckDB 路径；区分冷缓存、热缓存、重启恢复和并发；记录 p50/p95、失败、扫描量、峰值内存、对象请求及结果一致性。只有前两者确实不足，才添加 ClickHouse/QuestDB 对照。

**成功标准：**满足预先约定的交互和数据新鲜度目标，查询结果一致，成本/维护增加可解释；故障后能恢复，不依赖未持久化状态。不给所有系统套同一个毫秒阈值。

**失败处理：**先检查分区、小文件、索引、裁剪和缓存；混合方案没有净收益就保留路线 A；DuckDB 已满足要求就停止数据库扩张。

### 实验 3：宏观与 ETF 的历史时点是否污染研究

**输入：**少量有修订的宏观序列、可获得的 vintage、ETF 披露/抓取快照以及预设历史报告截止点。

**步骤：**分别按“今天最终值”和“当时可见值”生成同一指标/报告；逐条检查 `published_at/available_at` 与 cutoff；人为加入晚到、缺份额、汇总先于明细、缺失被填零的记录。

**成功标准：**任何截止后可见的记录均不进入当时研究；ETF 未到齐状态保持未知；修订能解释，并能重现两个版本之间的差异；缺少日内发布时间时报告不假装具备日内精度。

**失败处理：**停用受污染的历史因子或缩小到有可信版本的时期；保留“仅适用当前描述”的功能，不用最新值替代历史可见值。

### 实验 4：LLM 是否比模板提供可验证的增量价值

**输入：**同一组获准提供给模型的证据包，包括正常、缺失、过期、互相矛盾、单位冲突、受限数据以及含恶意指令的外部文本；确定性模板作为基线。

**步骤：**先用程序生成事实表；分别生成模板报告和有界 LLM 报告；自动核对每个数值引用、单位、窗口、来源与许可；人工检查解释质量；记录成本、延迟、重试和失败降级。禁止拿许可不明的商业数据做模型评测样本。

**成功标准：**关键数值没有未支持引用；缺失不被补造；受限字段不外发；外部文本不能改变权限；解释确有比模板更多的可用内容，并满足事先设定的费用/延迟上限。输出流畅不算单独通过条件。

**失败处理：**数值字段改成程序插入；缩小 LLM 工作范围；必要时退回确定性报告。多加代理不能替代修正输入和校验。

### 实验 5：图表更换是否改善研究，而非只改善截图

**输入：**同一份可信 OHLCV/足迹/缺口样本，当前图表与一个候选组件；固定任务，例如定位异常量柱、对照宏观事件、保存假设笔记、回到某份报告的窗口。

**步骤：**比较时间对齐、拖拽/缩放、覆盖物和标注保存、更新时稳定性、内存与任务步骤；用黄金样本确认桶和数值没有因渲染而变化。

**成功标准：**相同事实显示一致，关键任务更顺畅，状态能恢复，源码/授权维护成本可接受。是否更美观单独记录，不冒充分析价值。

**失败处理：**保留原图表，只引入证据入口、质量提示或单个自定义面板；不进行整站重写。

## 10. 待查仓库与运行环境问题清单

| 领域 | 必须核查的问题 | 会改变什么决策 |
|---|---|---|
| 依赖与结构 | 真实 lockfile、版本、前后端共享模块、原生/第三方图表、构建链？ | 能否局部复用与升级，是否需要新增运行环境 |
| 采集机制 | 由浏览器、Worker、定时器还是外部进程采集？页面关闭是否停采？ | 是否存在持续采集缺口；路线 A/B |
| 原始留存 | 保存原始逐笔和深度还是只有指标？最长历史和丢失区间？ | 足迹和回放是否具备事实基础 |
| 时间/单位 | 毫秒、微秒、日期、时区、合约单位在哪里转换？ | 是否已有静默污染；是否能合并不同数据源 |
| 订单簿/CVD | 快照衔接、断档恢复、主动方向、累积起点、价格桶？ | 微观结构功能是否真实可用 |
| 数据库 | D1 表、索引、库大小、日写入、扫描行数、查询延迟、锁等待？ | 是否真实需要文件层/独立分析库 |
| 数据修订 | FRED vintage、ETF 到齐状态、链上标签版本是否保留？ | 历史研究能否声称时点正确 |
| 指标实现 | 同一指标是否前端/Worker/LLM 各算一次？预热和缺失规则？ | 是否要统一计算中心与黄金样本 |
| 云任务 | 调度归属、任务生命周期、重试、幂等、超时、恢复点？ | Workflows/Queues 是否有具体必要性 |
| LLM 权限 | 能调用什么工具？是否能访问任意 URL/账户/秘密？是否有循环预算？ | 安全边界与报告链改造优先级 |
| LLM 证据 | 输入快照是否固定？数字是否由模型计算？报告可否重放？ | 类型化输出与证据包的接入方式 |
| API/缓存 | 缓存键是否包含参数、时点和数据版本？是否展示 stale？ | 前后窗口串数据、冷启动和加载问题 |
| 实际负载 | 高频市场数量、事件量、历史增长、并发、用户工作流？ | 数据库与采集范围，而非凭想象扩容 |
| 网络/部署 | 部署地区、来源合规可达性、长期连接和独立服务运维能力？ | 云平台边界、来源选择；不设计绕过访问限制 |

### 11.4 结论的把握与未完成验证

**把握较高：**公开协议和许可中已经明确的限制；数据/方法/报告分层的必要性；把未知当零、混淆时间与单位会破坏研究；不能从项目年龄推出重写。

**条件性把握：**混合架构比全量迁移更适合本项目、DuckDB 是当前首选分析引擎、某个图表组件会提升使用体验。这些建立在个人维护、少量市场、研究而非交易执行的假设上。

**尚未验证：**用户实际代码质量、现有性能、数据真实完整率、各候选运行效果、全部上游商业授权、模型成本与增量价值、独立服务地区可达性。文档阅读不是运行验证，报告中所有实验仍待执行。

## 最终决策归纳

**推荐采用：**统一契约、原始与版本留存、时点性管理、数据质量可视化、确定性指标、证据驱动单工作流；在高频需求成立时采用 Cloudflare + 单独数据服务 + Parquet/DuckDB 的演进方向。

**值得试验：**CCXT、受许可约束的 Cryptofeed/Tardis、Deribit 期权快照、KLineCharts、mempool API、Coin Metrics 非商业子集、OpenBB 单 provider、许可明确后的 vectorbt，以及达到负载触发条件后的 ClickHouse。

**仅借鉴思想：**aggr/flowsurface 的订单流工作区、NautilusTrader 的事件模型、Freqtrade 的偏差检查、Glassnode 的 PiT 方法、授权未明的稳定币适配代码组织。

**暂不采用：**为技术老化而整体重写；未获许可的数据复制/对外分发/LLM 输入；默认全市场高频库、完整自动交易平台、多代理堆叠与重型集群。

**最先应拿到的不是一套新架构，而是三份证据：一条能正确回放的数据链、一份没有未来信息的历史研究样本、一份所有关键判断都能追到数据和方法的报告。** 三者成立后，再扩大数据、界面与计算能力。
