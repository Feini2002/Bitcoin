# 比特币金融分析系统：证据核验与能力升级修订报告

**查询日期：2026 年 9 月 16 日。版本：实施前研究修订版。**  
**适用对象：系统负责人、仓库开发者及获得只读仓库权限的开发代理。**  
本报告可以独立使用，替代上一版作为后续讨论依据。它不是代码审计结果、性能测试报告、数据采购意见或实施授权。

## 1. 执行摘要

**首选不是迁移架构，而是用现有系统完成一条可核验的研究闭环；只有闭环需要的特定数据或计算超出现有路径的合理边界时，才增加专用服务。**

本轮最重要的纠偏，是降低部分分析能力的最低数据要求。Binance K 线包含总成交量和主动买入成交量，因此可以先验证柱级成交 Delta 与累计 Delta，不必为此先建设完整逐笔、盘口和高频数据库。价格分档足迹、柱内路径和盘口热力图则是另外三个问题，不能由普通 K 线还原。依据见[现货 WebSocket 协议的 Kline 字段](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/web-socket-streams.md)。

最终仅提出五项值得交给开发者讨论的能力：

| 编号 | 能力 | 主要价值 | 决策 |
|---|---|---|---|
| U1 | 可复算的数据与证据快照 | 解释同一指标为什么变化，让页面、导出、历史报告使用同一事实版本 | **优先考虑方法；不预设换存储** |
| U2 | 分层的市场行为与衍生品分析 | 区分成交主动性、杠杆变化、期限结构和数据覆盖，而非只给“多空分” | **先验证低成本版本；逐笔、L2、完整期权曲面逐层获证** |
| U3 | 当时可见的事件与因子研究 | 检验宏观、ETF、资金费率等条件与后续市场表现的关系，减少事后解释 | **选一个问题做实验，不同时建设全部研究模块** |
| U4 | 有证据约束、可回归评估的 LLM 报告 | 让关键数字、时间窗口、引用和不确定性可检查 | **优先考虑；复用现有调用层优先于更换 SDK** |
| U5 | 联动工作区与可解释预警 | 从异常图形追到事件、数据、笔记和报告，避免重复查找及重复告警 | **先做局部联动，不默认替换图表或整站** |

近期的讨论顺序是：先核对 U1，结合已有云端报告验证 U4；随后在 U2 与 U3 中选择一个真实研究问题。U5 随所选问题补齐必要交互。**这不是五项同时开工的清单。**

应保留能够满足需求的原生 JavaScript、Cloudflare 展示/API 层、现有来源适配、指标实现和任务机制。应暂缓完整交易平台、多代理堆叠、默认全交易所 L2 留存，以及没有查询负载证据的数据库集群。

这些建议改善的是研究过程的可信度和效率。它们没有证明能预测比特币价格，也不承诺准确率、收益、稳定性或工期。

## 2. 本轮纠偏发现与修正

### 2.1 对十四项风险的审查结论

| 检查项 | 实际发现 | 修正 |
|---|---|---|
| 1. 热门项目或首页依赖 | 无法从上一版证明当时只看首页；能确认的是候选偏完整平台，专用统计、交易日历和评估工具覆盖不足 | 补查 arch、exchange_calendars、Barter-Data、ruptures、专用 IV 库及 promptfoo |
| 2. 用 Star、提交时间证明成熟 | 未发现 Star 评分；但原有 R/D/S 主要表示查过什么资料，不足以表示维护健康 | 改为具体发布修正、可定位源码、环境变化与明确未知；不推算维护者“可靠分” |
| 3. 只有工具没有流程 | 上一版已有流程，不能说完全没有；问题是可试验对象过多，缺乏硬取舍 | 最终收敛到五项能力，组件成为替代选项 |
| 4. 功能存在等于场景适用 | 对 CVD、逐笔、足迹与 L2 的最低依赖区分不够细 | 补充柱级 Delta 最小方案，并分开成交链和盘口链的失效范围 |
| 5. 偏向换技术栈 | 上一版没有宣布必须重写，但混合架构的优先表述早于真实需求验证 | 改为局部演进作为起点；混合架构必须由数据、计算和维护证据触发 |
| 6. 职责重复框架 | 没有要求全部部署，但 CCXT/Cryptofeed、图表库、代理框架等并列试验过多 | 每个职责先保留现有实现，只选择一个有针对性的对照方案 |
| 7. 免费与商业边界 | 上一版多数已区分；仍缺 Coinbase 原生行情使用限制，以及 Tardis SDK 与其数据产品的分界 | 补充官方条款；不把开源 SDK 的使用自动归入数据商合同 |
| 8. 历史、时间与修订 | 这是上一版较充分的部分；仍缺“市场当时公开”与“本系统当时实际收到”的区别，以及交易日历与发布延迟 | 增加三种历史读取模式、发布精度、跨资产交易时段和 COT 延迟示例 |
| 9. 估计当观测 | 上一版已正确提醒链上标签推断；清算热力图的模型性质没有充分展开 | 明确区分成交、可见盘口、已发生清算流和潜在清算模型 |
| 10. 许可证与维护成本 | Cryptofeed、vectorbt、Coin Metrics 等重要警示复核后成立 | 保留；同时避免把 AGPL 说成禁止商业使用，或把 Commons Clause 泛化为禁止所有商业活动 |
| 11. 虚假精确性 | 未发现加权分、收益承诺或确定工期；旧版套餐报价不代表本项目最低可用报价 | 不沿用不对应 BTC 数据范围的套餐金额；成本改为输入条件与费用项 |
| 12. 阅读与运行混淆 | 上一版明确说明未运行，未发现反向证据 | 保留，并进一步区分文档阅读与局部源码阅读 |
| 13. 仓库情况当事实 | 上一版没有声称已读本仓库 | 保留条件表达，新增逐能力的仓库核验材料 |
| 14. 缺少反证和放弃理由 | 上一版已有停止条件；不足在于具体反证，例如 D1 读复制和低成本柱级分析 | 将反证直接放入架构选择与候选取舍，而不是只放结尾 |

### 2.2 四处明确调整

**第一，修正架构论证。** D1 官方文档既说明单实例串行处理，也说明读副本可以分担读取，并要求使用 Sessions API。不能由前者推导“全部读取都只能串行”或“必须迁库”。读复制也不会消除单库容量、写入和重型扫描的限制。见[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)及[读复制与 Sessions](https://developers.cloudflare.com/d1/best-practices/read-replication/)。

**第二，修正最小数据要求。** 成交 Delta 不等于资金净流入；足迹不等于盘口；计算 CVD 或成交足迹不必先具备 L2。盘口断档只应使依赖盘口的结果失效，不能机械地把仍完整的成交统计一起停掉。

**第三，收紧维护结论。** CCXT 可见的 v4.5.78 主要是构建修正；与本系统直接相关的 Bybit 清算方向、资金费率或 OI 历史修正，分布在其他相邻版本。以后应引用对应变更，不把“最新标签存在”写成所有功能可靠。见[CCXT 发布记录](https://github.com/ccxt/ccxt/releases)。

**第四，修复可追溯性。** 上一轮聊天正文有部分来源标记未正常显示，正文与附件组织也不完全相同。本版统一正文结构并附原始链接。上一版关于某次 Farside 页面出现缺失明细和零合计的日期性观察，不再作为独立证据：未保存当时完整快照，当前动态页面不能证明过去的页面状态。相同风险改为明确的合成测试案例，而不是继续引用未经归档的瞬时观察。

## 3. 已知背景、研究边界与证据说明

### 3.1 四种证据标签

| 标签 | 含义 | 本报告中的用法 |
|---|---|---|
| **已核验事实** | 有本轮读取的直接文档、源码、发布记录、条款或论文支持 | 某字段含义、某 API 限制、某许可证、某发布修正 |
| **合理推断** | 从事实推导的适配判断，并说明条件 | 单人低频研究可能不需要常驻行情服务 |
| **待验证假设** | 需要实际仓库或实验 | 当前适配是否丢字段、DuckDB 是否更省、联动是否更快 |
| **未知** | 尚无充分信息 | 实际完整率、维护响应速度、全部商用权利、生产账单 |

“推荐采用”是对方法或条件性方案的判断，不把后两类自动升级为事实。“未找到缺陷”不等于“没有缺陷”。

### 3.2 已知与未知

**用户提供的已知背景：**BTC 分析系统，涉及行情、指标、足迹、订单流、宏观、舆情、云端 LLM 报告；技术包括 HTML/CSS/JavaScript、Pages、Workers、D1；来源包括 Binance、Deribit、FRED、Yahoo；系统暂停；仓库治理另有工作处理。

**本仓库未知：**实际依赖、来源适配、存储内容、指标定义、任务恢复、报告输入、访问量、成本、授权、部署地区和性能。本轮没有读取它，因此不能认定任何能力缺失，也不能认定某项功能已经正确实现。

本轮完成了上一版全文核对、公开网页与协议读取、若干许可证和源码局部检查、发布说明及研究论文核验。没有安装软件、运行候选代码、调用交易账户、连接个人数据账号或操作生产系统。论文阅读不等于复现实验；测试目录存在也不等于测试通过。

### 3.3 检索范围与局限

采用中英文检索，补查重点是：最小数据粒度、多交易所语义、历史回补、期权认证边界、时点研究、专用统计库、工作区和报告评估。

直接核验来源包括交易所文档、Cloudflare、DuckDB、FRED/ALFRED、CFTC、数据提供方、发行人、开源仓库及作者论文。中文资料包括[KLineChart 官方文档](https://klinecharts.com/)及中文关键词检索；社区线索包括[Reddit 的订单簿研究讨论](https://www.reddit.com/r/algotrading/comments/10937x1/orderbook_based_indicators_and_strategies/)和[HN 的 DuckDB/Harlequin 使用讨论](https://news.ycombinator.com/item?id=37588526)。社区观点没有作为性能、获利或协议正确性的证明。

本轮没有取得可用于核验的 X 原帖；OKX 中英文协议页访问未成功，因此不声称完成其当前频道语义核验。部分 AI SDK 文档页访问失败，改读项目源码和发布记录。没有访问付费历史数据、登录后的供应商后台或私密社区。

没有完成所有候选的安全审计、贡献者集中度统计、PR 响应统计或全部测试审查。维护分类仅表示可见信号：**活跃演进、稳定维护有据、维护证据不足**；不能仅凭旧标签把项目列为停止维护。

## 4. 方案地图与候选项目表

### 4.1 按研究责任，而非品牌分层

| 层次 | 应承担的责任 | 不应混入的责任 |
|---|---|---|
| 来源与权利 | 数据定义、覆盖、认证、许可、修订 | 不由 SDK 许可证代替数据授权 |
| 采集与标准化 | 回补、实时衔接、去重、序列、单位、时间 | 不在此层生成不可追溯的“多空判断” |
| 事实与版本 | 原始或获准留存内容、快照、来源、质量 | 不把缓存当唯一事实存档 |
| 确定性研究 | 指标、事件、统计验证、实验记录 | 不依赖模型心算或临时改变窗口 |
| 产品交互 | 共同研究上下文、图表、笔记、导出、预警 | 不各自维护第二套指标定义 |
| 报告解释 | 引用事实、解释冲突、提出假设与局限 | 不把生成文本当新观测数据 |

这些是责任边界，不是六个必须分别部署的微服务。

| [Vercel AI SDK](https://github.com/vercel/ai) | 类型化工具与受控生成 | Apache-2.0；可定位工具输出序列化修正 | **现有调用层不足时采用** |
| [promptfoo](https://github.com/promptfoo/promptfoo) | 报告回归与自定义断言 | MIT；0.123.0 有发布证据；CLI 环境与外部调用需控制 | **离线评估候选，不是生产必驻服务** |
| [Cloudflare Workflows](https://developers.cloudflare.com/workflows/reference/limits/) / [Queues](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) | 跨步骤恢复或异步缓冲 | 托管服务；费用、幂等和状态保留分别处理 | **仅在现有任务机制不足时采用其一** |
| [GDELT DOC API](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/) | 新闻发现和事件索引 | 官方介绍可核；当前实际召回、延迟和全文权利未验证 | **只做元数据和去重试验** |

未进入本轮重点的完整平台不因此被判定质量差。OpenBB、vectorbt、NautilusTrader、Freqtrade、LangGraph、Langfuse、Dagster 等的职责与本轮最低方案并不一一对应，不再把它们并列排入近期任务。

## 5. 重点候选的深度比较

以下维护信息均为 **2026-09-16 查询所见**。版本用于定位证据，不是升级指令。默认分支的许可证和环境声明也不能替代最终锁定标签的核验。

### 5.1 Binance 原生协议与公开归档：最小行情能力的基准

**类型与事实。** 数据 API、WebSocket 协议和历史文件，不是全功能研究软件。官方 Kline 字段包含总基础币成交量 `v`、主动买入基础币量 `V` 和闭合状态 `x`；公开归档说明现货数据自 2025-01-01 起采用微秒时间戳。依据是[原始协议](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/web-socket-streams.md)与[归档 README](https://github.com/binance/binance-public-data)。

**具体复用。** 使用原始字段建立校验样本，优先验证闭合柱的 `Delta = 2 × V − v`。这来自“总量＝主动买量＋主动卖量”的代数关系，前提是两项属于同一市场、窗口、单位和统计覆盖。按固定起点累计，可得到柱末累计 Delta；没有柱内路径，也没有价格分档足迹。

**限制与反证。** 不同市场、普通成交与其他成交类别可能有不同覆盖；REST、实时与归档必须实际对照。合约 OI 统计的历史范围、清算流的采样限制，不能从“历史 K 线免费”类推。原生盘口需要自己的快照和增量恢复。见[OI 统计文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/market-data/rest-api/Open-Interest-Statistics)及[合约市场流](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/ws-streams/market)。

**维护、授权与运行。** 协议及归档说明可核，实际可达性和数据完整率未知。无需为公开行情配置交易权限，但数据留存、展示、外部模型输入和商用再分发仍需核定。归档辅助脚本的整体复制许可未核全，不据此复制。最小方案可以由现有 JS/API 层完成；持续深度采集另作实验。

**替代与判断。** CCXT 能降低多所接口成本，代价是统一对象可能不含所需原始字段。只有一个来源、少数接口时，原生适配更容易逐字段核对。**推荐采用基准方法，是否替换现有适配为待验证假设。**

### 5.2 CCXT：适配通用接口，不接管研究语义

**已核验事实。** [统一 API 规范](https://docs.ccxt.com/docs/base-spec)中的 OHLCV 是时间、开高低收、成交量六项，不应假定其中还保留 Binance 的主动买量。[发布记录](https://github.com/ccxt/ccxt/releases)包含 Bybit 清算方向、OI 历史和资金费率标准化等修正，既说明持续维护，也证明“统一字段”仍可能出错。

**适用与接法。** 只读使用所需的公共市场方法，在边界处转成内部契约，同时保留原始响应或确有必要的扩展字段。接入方式是直接依赖或独立 Node/Python 适配进程，不要求前端直接依赖交易所对象。

**维护、许可、费用。** 可归为活跃演进，理由是可定位的实质修正，不是发版频率或 Star。[代码 MIT](https://raw.githubusercontent.com/ccxt/ccxt/master/LICENSE.txt)；上游历史、认证、费用与再分发条款独立。库不是免费完整历史库。多位贡献者可见，但完整集中度和目标适配器测试没有审计。

**限制与替代。** 统一 OHLCV 可能不足以支持柱级 Delta；衍生品单位、清算方向、频道恢复不能完全委托给统一层。Workers 兼容性要按所需方法、包体和运行时检查，不能从支持 JavaScript 推出全部可用。竞争方案是少量原生适配；若它们已经可靠，新增 CCXT 未必降维护成本。

**判断：值得对一个接口试验，不建议全面替换。** 接入与长期负担主要来自上游协议变化和回归样本，而不是首次函数调用。

### 5.3 Deribit：先得到可信期权截面，再考虑曲面

**已核验事实。** [get_order_book](https://docs.deribit.com/api-reference/market-data/public-get_order_book)区分 OI 单位：永续和反向期货为美元单位，期权和线性期货为基础币单位；[订阅说明](https://docs.deribit.com/articles/notifications)明确 raw 需要认证，普通聚合频道不能等同原始逐事件流。

**具体能力与最低方案。** 先收集合约定义、报价时间、到期、行权价、币种、指数、买卖价、mark、OI 和可得 IV，保存采样批次及每个合约的实际时间。由此回答期限结构、波动率变化、报价稀疏和 OI 分布问题。分批抓取形成的截面不能假定同时发生。

**维护、授权与运行。** 官方字段和采集建议可定位，实际限流、全历史覆盖与服务可靠性未验证。公共快照不要求引入交易执行权限；raw 认证、商业展示和再分发须另行确认。本轮未连接账号。可采用现有 HTTP 层或独立计算进程；无需先部署 QuantLib 或交易框架。

**限制与替代。** 无双边报价、宽点差、过期值和模型 mark 应降低质量等级。报价 IV、自己反解的 IV、Greeks 都不是无条件的“真实值”；模型、远期、计价单位、到期精度和日计数必须匹配。专用 py_vollib_vectorized 虽有计算能力，但导入可修改 py_vollib 行为、依赖链和近期维护仍需隔离验证，不能视为即插即用。见[其源码仓库与依赖说明](https://github.com/marcdemers/py_vollib_vectorized)。

**竞争方案：**有授权的历史期权数据，例如 Tardis，而不是用今天的截面倒推历史。**判断：快照契约值得采用；完整曲面与历史采购先试验。**

### 5.4 DuckDB＋Parquet：可迁移研究输入，而非默认新数据库

**已核验事实。** DuckDB 支持[Parquet 读取与写入](https://duckdb.org/docs/lts/data/parquet/overview.html)和[R2/S3 兼容访问](https://duckdb.org/docs/lts/guides/network_cloud_storage/cloudflare_r2_import.html)。[1.5.5 发布记录](https://github.com/duckdb/duckdb/releases)列出类型、聚合、内存及并发等修正，属于有实质维护证据的分析引擎。

**适用与接法。** 在需要重算较长历史、扫描文件和复现实验时，使用一个受控分析进程读取版本化文件，向现有系统输出聚合与证据包。进程可以按需或定时运行，不必一开始变成全天服务。原始数据量很小时，现有数据库的版本表或获准导出可能已经足够。

**许可、环境与费用。** [MIT](https://raw.githubusercontent.com/duckdb/duckdb/main/LICENSE)；本地使用没有数据库软件订阅费，但计算、磁盘、对象请求和备份有成本。可以选择 Python、Node 原生绑定或 CLI；不把原生绑定能否直接运行在 Workers 当成既成事实。

**限制与反证。** 嵌入式原生文件的典型读写模式是单写入进程，并非所有进程可随意并发写。当前文档也列出 Quack、DuckLake 等其他方案，不能说 DuckDB 永远不支持服务化或多进程；但为本项目引入额外目录库会改变复杂度。见[并发说明](https://duckdb.org/docs/current/connect/concurrency.html)。对象存储不是数据库事务层，上传多个文件也不等于原子发布一个完整数据集。

**替代与判断。** 竞争方案首先是优化并保留当前 D1/现有计算，而不是立即上 ClickHouse。持续并发重查询被证实后，才与 ClickHouse/QuestDB 对照。**推荐试验文件分析；不把迁库列为必做。**

### 5.5 FRED/ALFRED：历史可见性优先于指标数量

**已核验事实。** [实时区间说明](https://fred.stlouisfed.org/docs/api/fred/realtime_period.html)区分当前可见数据与历史时点数据；[使用条款](https://fred.stlouisfed.org/docs/api/terms_of_use.html)明确第三方序列的版权不会因经过 FRED 而消失。

**适用与接法。** 按选定序列保存观察日期、单位、频率、季调、版本日期、发布时间精度和取得时间，通过现有 HTTP 适配写入内部时点契约。先服务一个研究问题，不一次接入全部宏观序列。

**维护、费用与运行。** 官方服务与版本语义有直接证据，不等于实际可用性已测试。API 使用和 key、限流应按当前规则执行；本轮未申请或连接 key，也没有验证本项目调用额度。无需强行引入 Python 平台；调用和展示可以继续使用 JS。

**限制。** ALFRED 的版本日期不自动提供精确到秒的发布时间，也不提供完整的历史市场一致预期。用实际值减“现在查到的预测值”研究发布意外，可能已经泄漏信息。缺历史 vintage 时，只能限制研究用途，不能用最终值补造初值。

**替代与判断。** 原始发布机构的历史公告、发行与修订档案是有竞争力的替代，有时发布时间更明确，但适配更分散。**推荐时点方法；具体数据源按序列择一主源、必要时交叉核对。**

### 5.6 arch：为研究结论提供误差和选择偏差检验

**已核验事实。** 官方示例包含[时间序列 bootstrap](https://bashtage.github.io/arch/bootstrap/bootstrap_examples.html)和[SPA、StepM、MCS 等多重比较](https://bashtage.github.io/arch/multiple-comparison/multiple-comparison_examples.html)；源码可定位到[arch/bootstrap/multiple_comparison.py](https://raw.githubusercontent.com/bashtage/arch/main/arch/bootstrap/multiple_comparison.py)。

**适用与接法。** 在“某条件之后波动是否更大”“一个因子是否超出简单基线”这类问题中，用其计算区间与比较结果，输出小型结果表，不引入交易执行。独立研究进程调用即可，产品层只读取固定结果。

**维护与授权。** [8.0 变更](https://bashtage.github.io/arch/changes.html)包含构建系统、类型及 NumPy/pandas 兼容更新，并要求 Python 3.10 起。[许可原文](https://raw.githubusercontent.com/bashtage/arch/main/LICENSE.md)是带版权保留、二进制声明和不得背书条件的 BSD 式宽松许可。程序许可不授权输入数据；随包示例也不能代替所需 BTC 样本。核心作者角色清晰，长期响应速度未知。

**限制与替代。** block 长度、非平稳性、事件聚类和损失函数仍需研究者决定。p 值不是“预测正确概率”；SPA/MCS 不是直接给任何回测分数盖章。竞争方案是现有统计代码或 statsmodels 中适合该问题的方法；问题简单时不必新增依赖。

**判断：作为专用统计候选值得试验。** 比把系统变成自动交易平台更符合当前边界，但不会自动消除研究偏差。

### 5.7 exchange_calendars：解决跨资产的时间错配

**已核验事实。** [仓库](https://github.com/gerrymanoim/exchange_calendars)提供交易所日历；[XNYS 源码](https://raw.githubusercontent.com/gerrymanoim/exchange_calendars/master/exchange_calendars/exchange_calendar_xnys.py)可定位休市与特殊开闭市规则。[4.13.2 发布记录](https://github.com/gerrymanoim/exchange_calendars/releases)包含真实的 2026 日历修正，说明日历不是永远不变的常量。

**具体复用。** 为 BTC 与美股、ETF 等数据生成交易时段表，记录 session、时区、开闭市和是否正常交易。Python 生成后供 JS 查询，也可以只输出版本化日历文件，不增加常驻服务。

**许可与边界。** [Apache-2.0](https://raw.githubusercontent.com/gerrymanoim/exchange_calendars/master/LICENSE)。日历库不附送价格、复权数据、实时停牌信息或宏观发布日历。主分支运行环境和项目锁定版本仍需检查，不能只沿用旧 Python 环境。

**限制与替代。** 特殊休市、突发停牌和目标市场覆盖必须对照原始交易所公告。仅做 BTC 24×7 单市场研究时，其价值有限。竞争方案是保存少量目标交易所的官方日历快照，由现有代码读取；市场少、逻辑简单时可能更轻。

**判断：跨资产时点问题成立时采用或试验；不为纯 BTC 指标额外安装。**

### 5.8 Lightweight Charts 与 KLineChart：选研究任务，不选截图

### 5.9 Vercel AI SDK：有界工具调用，而不是研究可靠性本身

**已核验事实。** 本轮直接读取[generate-text.ts](https://raw.githubusercontent.com/vercel/ai/main/packages/ai/src/generate-text/generate-text.ts)，可定位工具、输出、超时、停止条件等控制入口；[ai@7.0.101 发布说明](https://github.com/vercel/ai/releases)有工具输出 JSON 序列化修正。部分官网文档页未成功访问，因此不声称完成全部接口审查。

**适用与接法。** 现有 JS/TS 模型层若缺工具参数约束、结构化结果或统一错误处理，可在调用边界局部依赖；现有层已经具备时，不为换 SDK 改写报告链。

**许可、环境与费用。** [Apache-2.0](https://raw.githubusercontent.com/vercel/ai/main/LICENSE)；SDK 本身不授予模型 API、数据或托管服务使用权。Workers/Node 的具体 provider、网络能力和依赖需锁版验证。费用主要由实际模型、工具与重试产生，不从 SDK 价格推算。

**限制与替代。** schema 只能检查结构，不能证明引用支持结论；停止轮数也不能代替每个工具的权限与成本预算。竞争方案是保留当前模型客户端，增加薄的类型、预算与校验层；当只有一个模型、一个固定报告流程时，这通常值得先比较。

**判断：推荐有界调用机制，SDK 采用与否待查仓库。** 不默认引入多代理、向量数据库或通用网页访问工具。

### 5.10 promptfoo：让报告修改可回归，而非再搭一个生产平台

**已核验事实。** [JavaScript 断言文档](https://www.promptfoo.dev/docs/configuration/expected-outputs/javascript/)支持布尔结果及带原因的评估结果，足以承载数值、引用、窗口和禁用字段的规则检查。[0.123.0 发布记录](https://github.com/promptfoo/promptfoo/releases)显示持续演进，并有 provider 行为变化，升级同样需要回归。

**接法与最小价值。** 放在隔离的开发/CI 评估环境，读取获准的固定证据包和报告输出，与当前模板比较。它不需要成为在线报告的必经服务。初期规则很少时，原有测试框架即可替代。

**许可、环境与费用。** [MIT](https://raw.githubusercontent.com/promptfoo/promptfoo/main/LICENSE)。查询时[主分支 package.json](https://raw.githubusercontent.com/promptfoo/promptfoo/main/package.json)声明 Node ≥22.22.0；这是该分支要求，不是本仓库升级指令。纯规则评估与调用付费模型评审是不同费用路径；云服务另约。官方提供[关闭遥测与更新检查的设置](https://www.promptfoo.dev/docs/configuration/telemetry/)，隔离环境仍应审查全部网络出口。

**限制。** 使用另一模型评分会增加成本和判断不确定性；引用存在不代表引用充分。对关键因果、风险和反证表述仍需人工抽检。固定测试集通过不代表所有未来报告无错。

**判断：值得小范围试验；报告质量规则优先于选择评估品牌。**

### 5.11 Tardis：历史数据采购选项，须把 SDK 与数据分开

**已核验事实。** [SDK 许可](https://raw.githubusercontent.com/tardis-dev/tardis-node/master/LICENSE)为 MPL-2.0。[套餐说明](https://docs.tardis.dev/faq/billing-and-subscriptions.md)区分 CSV 与原始回放接口，历史深度也有套餐和计费周期条件；不能把示例文件当作完整历史。

**重要授权分界。** [条款第 9 节](https://docs.tardis.dev/legal/terms-of-service)分别处理内部用途、衍生分发与 AI 使用。9.6 明确：只用其开源软件访问自行取得的交易所数据，并不会使这些独立数据自动受 Tardis 数据限制。反过来，购买 Tardis 数据也不自动取得任意外部 LLM、再分发或模型评测权。具体推理用途应确认，不能简单写成“一切推理都禁止”。

**接法、状态和代价。** Node 回放、标准化 CSV 或独立导入进程都可用；数据提供服务文档可核，实际覆盖、丢失记录、延迟和 SLA 未测试。软件可免费使用，数据、存储、导入和授权管理有成本。本轮没有形成符合目标市场、历史期和用途的完整报价，不沿用“全永续套餐”代表 BTC 最低成本。

**竞争方案。** 自有合法归档适合未来采集，不能补回从未保存的过去盘口；CoinAPI 等是采购对照，但必须逐数据产品比较事件粒度、覆盖与权利。**判断：只有某段不可回补历史对一个具体研究问题确有价值，才进入采购试验。**

## 6. 面向比特币分析的五项能力组合

本节全部为**条件性设计建议**，不是对仓库现状的断言。组件可以替换，验收针对研究结果。

### 6.1 U1：可复算的数据与证据快照

**用户问题与新增价值。** 如果今天打开旧报告，其数字会随上游修订或当前缓存变化；或者同一指标在页面、CSV 和 LLM 中不一致，就需要让每个结果绑定明确的数据版本、方法和截止点。新增价值是能够回答：“这份结论当时基于什么？后来变化来自数据、算法还是窗口？”

**最小方案与复用方式。** 不先建设数据湖。先选择一个现有指标，保存其获准留存的输入、标准化结果、方法参数和输出。数据少时使用现有版本表或文件；历史扫描需求成立时才加 Parquet/DuckDB。版本和溯源方法优先复用，不要求复制大型平台代码。

最低契约建议如下，字段名属于建议，不表示仓库已有这些字段：

| 对象 | 必须能表达的内容 | 关键边界 |
|---|---|---|
| 来源及 instrument | 交易所、市场类型、原始标识、基础/报价/结算币、乘数、有效区间 | 同名 BTC 合约不一定同单位；历史到期品种不能删除后视为从未存在 |
| 原始或获准留存记录 | 来源 ID/序列、原时间及单位、接收时间、原始载荷位置或许可允许的替代证据 | 取得数据并不证明它完整；不能保存的原文不擅自留存 |
| 标准化观察 | 价格、数量、单位、方向来源、统计覆盖、缺失/重复/修订状态 | 未知不是零；估计不能标成直接观测 |
| 数据集快照 | 来源集合、窗口、版本、行数、范围、校验和、完整性状态 | 校验和证明内容未变，不证明金融含义正确 |
| 指标与报告输入 | 方法版本、参数、窗口、累计起点、数据集 ID、质量、权利标签 | 参数变动属于新版本；不能悄悄覆盖历史结论 |

**时间模型。** 同时区分经济事件或观察时间、来源公布时间、系统接收时间、数据版本时间；保留时间精度与未知状态。统一 UTC 用于内部比较，但交易日历、时区和日线分桶仍须明确。超出 JS 安全整数范围的 ID 或高精度时间不得无损转换成普通 Number。

历史查询应至少区分三种模式：

| 模式 | 回答的问题 | 可使用的数据 |
|---|---|---|
| 当时市场可见 | 在截止点，市场理论上能知道什么？ | 有可信发布/历史版本证据、且当时已公开的数据 |
| 本系统当时已知 | 这份真实历史报告当时实际拿到了什么？ | 截止点前本系统已接收并留证的数据 |
| 以最新修订重算 | 今天用目前版本重新分析过去会怎样？ | 当前修订值，但明确不冒充历史实时结果 |

后来合法购得的历史数据可以支持第一种研究，前提是提供可信时点信息；不能据此声称本系统当时已收到。ALFRED vintage、数据库备份和报告留档分别解决不同问题，不能互相替代。

**数据链路。** 来源 → 现有采集/回补 → 原始或获准留存记录 → 标准化与质量判定 → 版本化存储 → 确定性计算 → 按快照查询的 API → 页面、导出、预警和报告。

**关联检查。** 查共享状态是否携带同一 instrument、窗口、单位、方法与快照；缓存键是否区分历史读取模式；导出是否重查了最新数据；LLM 是否混用了不同截止点；修订是否会覆盖旧报告。发布新快照时应有完整性标记，避免部分文件上传成功就被当作整批完成。

**代价与责任。** 主要是版本规则、额外留存、清理策略和回归样本。来源负责人维护口径与许可，计算负责人维护方法版本；单人项目也应在文档中区分这两类责任。保留范围由研究价值与权利决定，不默认永久保存全部逐笔。

**验收与不采用条件。** 同一输入和方法重算一致；修订前后可解释；重复、缺失和单位错误可见；页面、CSV、报告关键数字一致。若现有系统已经满足，保留它，只补缺失证据。无法保存必要输入且没有合法替代时，应降低“可复算”承诺，不为达标越过授权。

### 6.2 U2：分层的市场行为与衍生品分析

**用户问题与新增价值。** 如果使用者只能看到涨跌和指标，却分不清主动成交、杠杆变化、定价差异及数据缺口，可增加可拆解的市场行为面板。它可以说明“哪些观测与本次变化同时发生”，不能自动说明“谁在操控市场”或“下一步必涨”。

**最低数据分层。**

| 子能力 | 最低输入 | 能回答什么 | 不能宣称什么 |
|---|---|---|---|
| 柱级 Delta / 累计 Delta | 同覆盖的总量、主动买量、闭合柱 | 每柱主动成交差额及固定起点累计 | 真实资金净流入、柱内全部路径 |
| 成交足迹 | 保留价格、数量、主动方向的成交或聚合成交 | 在可用精度下，价格桶内的成交分布 | 普通 OHLCV 可恢复足迹；聚合成交等于逐事件时序 |
| 可见深度/盘口热力图 | 对应频道的快照、增量及恢复规则 | 接口可见的挂单深度变化 | 所有隐藏流动性、未公开订单意图 |
| 资金费率、OI、基差 | 合约规格、对应时点、费率周期、价格基准 | 杠杆和期限结构的不同侧面 | OI 增加就是等额资金流入 |
| 期权截面 | 合约定义、双边报价、指数、时间、质量 | 期限结构、偏斜与报价分布 | mark IV 就是随时可成交的 IV |

**复用与接入。** 原生字段作为正确性基准；多所接口确有重复成本再试 CCXT。先用 Binance 一个市场的闭合柱；Deribit 仅取有限期权快照。足迹和盘口分别获证，不先选全市场采集框架。

**三个必须保留的来源差异。**

其一，Coinbase Exchange `match.side` 表示 maker 一侧，而不是直接表示主动方向；Binance 的 `m` 也是 maker 相关字段。不能所有 `buy/sell` 字段共用同一映射。见[Coinbase matches](https://docs.cdp.coinbase.com/exchange/websocket-feed/channels)与[Binance 现货协议](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/web-socket-streams.md)。

其二，Binance 合约清算流每交易对在 1000 ms 窗口只给最新一条快照；Bybit 的 `allLiquidation` 文档描述每 500 ms 推送覆盖内的清算，其 `S=Buy` 表示多头被清算，价格字段是破产价格。这些是不同的协议语义，不是可以直接相加的同口径“真实全市场爆仓总额”。实际接收完整率仍未知。见[Binance 清算流](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/ws-streams/market)及[Bybit allLiquidation](https://bybit-exchange.github.io/docs/v5/websocket/public/all-liquidation)。

其三，[CoinGlass 热力图 API](https://docs.coinglass.com/reference/liquidation-aggregate-heatmap)说明结果根据市场数据与杠杆水平计算，且该端点只在特定付费计划提供。因此必须标为模型估计，不能与已发生清算流、真实成交足迹或可见挂单热力图混用。

**数据链路。** 市场原始字段/历史归档 → 按来源规范化 → 按交易与盘口分别标记质量 → 快照或文件存储 → 同口径 Delta、资金费率/OI/基差、期权计算 → API → 分来源面板与证据报告。

资金费率保存已结算/预测状态及实际结算间隔，不固定假设都是八小时。定期合约基差记录现货基准、到期时间和年化方式，永续不套用到期年化公式。跨所汇总先处理基础币量、合约张数、美元名义价值及报价币差异；现货与永续不默认合并。

**关联检查。** 实时柱更新和历史回补是否经过相同规则；当前未闭合柱是否覆盖已闭合历史；不同图表的价格桶和 CVD 起点是否一致；导出是否保留覆盖、来源和单位；LLM 是否把“观测成交差额”改写成“资金流入”；盘口断线是否污染本来完整的成交链。

**代价与验收。** 低频版本主要是字段、校验与界面成本；逐笔/L2 版本增加持续采集、断线恢复、历史缺口、对象操作和维护责任。验收应比较柱级计算与同窗口成交聚合，解释差异；注入方向、单位、重复和缺口错误；缺序列时盘口进入无效状态并恢复，而不是继续显示假精确。

**不采用条件。** 使用者不需要价格分档或盘口历史，则不采 L2；原始字段没有可靠主动方向，则不伪造精确 CVD；来源不能持续合法取得，则缩小覆盖；复杂曲面的主要误差来自脏报价，则停止增加定价模型。

### 6.3 U3：当时可见的事件与因子研究

**用户问题与新增价值。** 如果系统能写“ETF 流入、美元走弱与上涨有关”，却不能检查这一说法在历史上是否成立，就需要可复现的事件/因子研究。它增加的是条件统计、样本外对照与反证能力，不是自动交易。

**最小研究单元。** 先选一个问题，例如“某类已公布数据变化后，BTC 波动分布是否不同于对照样本”。固定事件定义、可见时间、研究窗口、基线、费用处理是否适用及样本外规则。最低界面是结果表、样本清单和证据链接，不需要完整回测终端。

**复用、数据与限制。**

| 输入方向 | 最小可信处理 | 需要明确的限制 |
|---|---|---|
| 宏观 | FRED/ALFRED 或原始发布机构；保存版本与发布精度 | 观察月份不是发布时间；缺历史一致预期就不做“意外程度”研究 |
| ETF | 发行人记录与汇总源交叉核对，保留到齐和修订状态 | AUM 变化不是净申购同义词；缺明细不是零；自动采集及商用权利未核全 |
| 稳定币 | 区分发行/赎回、流通、价格和跨链映射 | 供应增加不等于 BTC 买盘；同一资产跨链重复计数需排除 |
| 链上、矿工 | 保存区块高度/hash及计算方法；实体标签另存版本 | 地址归属、矿工卖出等含推断；全网算力本身也可能是统计估计 |
| CFTC 持仓 | 按实际发布日期而非持仓观察日加入信息集 | 一般周五公布前一周内周二的数据，节假日可改变安排 |
| 跨资产价格 | 目标市场日历、实际可见价格、最大陈旧时长 | 周末沿用的股票收盘价不是周末新成交价；复权口径单列 |
| 舆情与新闻 | 原始公告、获准摘要或新闻元数据；转载去重、事件时间与首次发现时间 | 转载数量不等于独立证据；全文、社媒和模型使用权另审 |

这些边界分别可由[发行人页面](https://www.ishares.com/us/products/333011/ishares-bitcoin-trust-etf)、[Circle 披露](https://www.circle.com/transparency)、[DefiLlama 数据定义](https://docs.llama.fi/analysts/data-definitions)、[Bitcoin Core 算力估计 RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/mining/getnetworkhashps/)、[CFTC 发布时间说明](https://www.cftc.gov/MarketReports/CommitmentsofTraders/index.htm)、[Glassnode PiT](https://docs.glassnode.com/data/point-in-time-metrics)和[GDELT 官方介绍](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/)交叉核验。它们支持来源定义，不证明某个因子有预测力。

**计算方法。** SQL/现有分析代码负责数据选择，必要时用 DuckDB 扫描文件、exchange_calendars 生成交易时段、arch 做适合的区间与多重比较。不是三者必须同时采用。保存全部已尝试参数，而不只保存胜出的版本。

研究验收必须区分以下问题：

| 风险 | 研究约束 |
|---|---|
| 前视与泄漏 | 历史特征只读取对应知识模式下截止点前可见值；缩放、阈值、模型拟合只用训练信息 |
| 重叠样本 | 未来收益窗口或标签重叠时，按真实重叠范围隔离训练与验证；不能只随机拆行 |
| 幸存者偏差 | 保存历史市场、合约、ETF 与数据源的生效区间，不按今天仍存在的对象筛过去 |
| 多重试验 | 记录问题、参数范围、尝试次数、淘汰结果；固定规则后再看独立样本 |
| 时间序列相关 | 区间估计考虑相关性、事件聚类和非平稳性，不对所有行直接做独立同分布抽样 |
| 状态识别 | 事后分段或全样本平滑状态只作描述；实时状态必须仅使用当时前缀重新计算 |
| 策略化误读 | 条件收益统计不是可成交收益；只有声称策略表现时，才必须建模费用、点差、滑点、资金费和信号/成交延迟 |
| 因果误读 | 事件后价格变化是关联证据，不自动证明事件导致变化；需要基线、负对照及其他解释 |

[ruptures 官方文档](https://centre-borelli.github.io/ruptures-docs/)明确定位为离线变点检测，适合事后分段，不适合不加处理地声称实时识别。[PBO 论文](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf)和[DSR 论文](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf)提供选择偏差方法，不能代替样本外结果，也不能当成“预测正确概率”计算器。

**数据链路。** 官方发布/获准供应商 → 观察、发布、接收、版本时间标准化 → 时点快照 → 预注册问题与确定性研究 → 固定结果 API → 事件表、区间统计、样本清单和报告。

**关联检查。** 当前页与历史页的知识模式、日历、复权和陈旧值处理必须一致；研究结果缓存含实验版本；导出保留被剔除样本及原因；LLM 不得把“最新值重算”描述为“当时已可判断”。

**实际代价。** 最大成本往往是历史版本、标签和发布时间的维护，而不是统计库。商业地址标签、ETF 汇总再分发、完整期权历史及新闻全文不纳入默认免费输入。

**验收与放弃。** 同一研究可复现；晚到与修订数据不进入错误时点；基线、负结果和不确定性可见。若有用结果只在反复调参后出现、样本不足或关键历史不可得，应保留描述功能、标记研究不成立或缩小范围，不包装成预测能力。

### 6.4 U4：有证据约束、可评估的 LLM 报告

**用户问题与新增价值。** 如果报告语言流畅，却无法核对数字、窗口或引用，问题不是再加一个代理，而是输入和输出缺少可验证契约。新增能力应是“这句话基于哪条数据、哪种方法、哪些反证”，并保留失败降级。

**最小方案。** 先保留现有模型调用。程序生成固定证据包，包含 cutoff、知识模式、快照 ID、指标值和单位、覆盖、方法、来源、可对外发送的字段。模型只负责解释、比较矛盾证据和提出假设；数值计算、权限、时点选择和关键校验由普通程序完成。

建议把结果分为：可核验事实、基于事实的解释、待检验假设、反证/替代解释、数据局限。每个关键事实或量化判断附 evidence ID；解释也应指向支撑它的事实，而不是给整篇报告挂几个网页链接。

**复用与接入。** 当前客户端＋薄校验层是第一对照；需要统一工具控制才试 AI SDK；已有测试框架与 promptfoo 二选一作为初期评估入口。都不要求引入在线多代理或向量数据库。

**数据链路。** 固定来源快照 → 确定性计算 → 权利与质量过滤 → 只读工具/证据包 → 模型生成 → 数值、引用、窗口和越权检查 → 保存原始报告与验证结果 → 页面、历史和获准导出。

**质量检查分四层。**

| 层次 | 检查目标 | 不能混淆的边界 |
|---|---|---|
| 结构 | 字段、类型、必须提供的证据 ID | JSON 合法不等于内容正确 |
| 数值与时点 | 数值、单位、窗口、方向、陈旧状态 | 引用了存在的数据不代表用了正确窗口 |
| 证据支持 | 引用实际支持该句；不把估计或关联写成观测、因果 | 有 URL 不等于论断得到支持 |
| 实际价值 | 相比确定性模板是否更有用，反证和不确定性是否恰当 | 文笔、长度和另一个模型的高分不能单独过关 |

**关联检查。** 工具统一走只读研究 API，不直接给任意 SQL、任意 URL、交易或账户权限。检索到的文章和帖子是数据，不是系统指令。共享上下文、缓存、报告历史和 CSV 使用同一快照。外发前做字段级权利检查；日志、评估样本和调试上传也属于数据使用路径。

**代价与验收。** 记录模型、模板、工具/方法版本、调用次数、费用、延迟、重试和降级原因。存档原始输出，不承诺重新请求模型会逐字一致；可复现的首先是输入和确定性事实。固定测试集要求关键数值与窗口校验通过、缺失不补造、受限数据不外发，语义支持由抽检补充。

**不采用条件。** 模板已经更可靠、模型没有可用增量，或者输入许可不允许外发，就缩小模型职责或使用模板。若主要故障来自证据错误，停止增加代理；多代理只有在独立任务、恢复或评审分工有实测净收益时再讨论。

### 6.5 U5：联动工作区与可解释预警

**用户问题与新增价值。** 如果使用者在多个页面反复选择相同时间、合约和指标，或收到无法解释的重复预警，增加共同研究上下文，比换一个更炫的终端更有价值。

**最低方案与复用。** 保留当前图表，补充同步时间窗口、事件标记、点击证据、绑定快照的研究笔记和可恢复链接。只有当前图表无法合理扩展时，才比较 Lightweight Charts 与 KLineChart。首次不引入完整可停靠工作台框架。

**数据链路。** 统一快照 API → 页面上下文与图表 → 事件/笔记证据关联；同一指标结果 → 确定性预警规则 → 预警状态与去重记录 → 页面预警及获准的通知渠道。

**预警不是一条简单的大于号。** 每条规则应说明输入、单位、方法版本、窗口、触发与解除条件、数据质量要求、冷却和重复合并方式。经济异常与数据中断分别告警。回放、回补和历史重算默认不发送真实通知；历史结果变化可以单列为修订事件。

滞回阈值和冷却用于减少边界反复触发，但参数应来自目标用途和回放检查，不能随意设成一个看起来专业的数字。阈值提示是研究入口，不是自动交易指令。

**关联检查。** 快速切换市场时旧请求不能覆盖新上下文；各面板的缺失点不能被隐式补零；导出、报告和笔记保留同一窗口与快照；保存的图形标注要表达价格/时间语义，不只依赖屏幕坐标。预警去重不得掩盖真正的新事件。

**实际代价。** 主要是前端状态、持久化少量上下文和预警状态；外部通知服务另有权限、费用和隐私要求。必要时增加图表组件，但不先重写 UI。

**验收与不采用条件。** 固定研究任务可以少走重复步骤，证据可回到原窗口，刷新后状态可恢复，页面/导出数值一致；注入迟到响应、缺数据、反复越阈值和历史回放，不能产生错页数据或重复真实通知。若只改善截图、不改善任务，保留现有组件。

## 7. 三种架构路线及条件化推荐

### 7.1 共同前提

路线选择依据是**实际保留粒度、历史扫描范围、计算形态、并发、新鲜度目标和维护能力**，不是项目年龄，也不是一条统一的“超过多少 GB 就迁移”规则。

一个数据量不大的查询也可能因扫描与关联方式很慢；大历史文件也可能因为按需批量分析而无需常驻数据库。先测完整路径，不只比较数据库执行时间。

### 7.2 路线比较

| 维度 | A：基于现有架构局部演进 | B：保留前端/API，增加专用数据或计算单元 | C：有触发条件的较大调整 |
|---|---|---|---|
| 适合任务 | 分钟/日频聚合、宏观、固定报告；现有路径能满足目标 | 长历史批量扫描、Python 专用统计，或持续逐笔/L2 | 在线数据服务成为主体，多用户并发或复杂计算持续超出现有边界 |
| 数据量表达 | 工作集和查询满足实际平台限制；不凭总行数决定 | 文件历史可按需分析；持续流另计峰值率与恢复要求 | 有真实增长与峰值记录，不凭未来想象建集群 |
| 新部署单元 | 可以为零；按缺口增加文件存储或任务步骤 | B1：按需/定时分析进程；B2：确需实时才增加常驻采集服务 | 可从单体后端＋任务进程开始，不等于微服务和 Kubernetes |
| 保留边界 | 保留当前页面、接口和计算，只补契约、版本与校验 | 新服务通过稳定的内部契约交付文件或结果，前端不直接绑定供应商 | 逐条数据链或查询路径切换，旧路径可比对、可回退 |
| 能力限制 | 重型计算、持续连接和长扫描需实际评估 | 多一个环境与恢复责任；文件和在线状态要协调 | 数据迁移、并行维护、接口兼容和运维成本最高 |
| 支持选择的证据 | 指标与报告通过正确性实验，实测响应、费用可接受 | 专用能力明确改善一个研究任务，成本和维护可承担 | A/B 优化仍不能满足目标，且边界摩擦长期超过调整成本 |
| 推翻选择的证据 | 确实需要无法合理承载的计算或采集 | 分区、索引、缓存已解决问题；无能力维护新进程；并无高频用途 | 主要问题其实是口径/缓存/缺证据；没有运维与迁移验收条件 |

**当前首选：从 A 开始核对，保留走向 B 的边界。** 只有持续微观结构或专用分析需求得到证明，B 才成为优先实施路线。C 不进入近期工作安排，也不与正在进行的仓库治理合并成大规模重构。

### 7.3 平台事实、配置限制与估算不能混写

| 项目 | 已核验的平台事实 | 对本系统只能得出的条件判断 |
|---|---|---|
| D1 容量与查询 | 付费单库 10 GB、免费单库 500 MB；单次 SQL 查询最长 30 秒；10 GB 单库上限不能继续上调 | 先检查实际表、索引、扫描和保留策略，不直接宣布 D1 不适合 |
| D1 读复制 | 每个实例的串行处理约束分别适用；读复制通过 Sessions API 使用，写仍到主实例 | 可改善部分读延迟和吞吐；不等于增加写能力，也不等于得到固定的金融数据快照 |
| Workers CPU | 付费计划 CPU 默认 30 秒，可配置到 300 秒；事件类型另有边界 | CPU 时间不是所有请求的墙钟寿命，不把默认配置当不可改变硬上限 |
| Workers 内存 | 128 MB 每 isolate，包含 JS 与 Wasm 分配，不是每请求各给 128 MB | 多面板和大对象共享内存的影响需测；不能仅凭单请求样本估计并发 |
| Durable Objects 出站 WebSocket | 能作为客户端；出站连接不能使用服务器端的休眠节费机制 | 需要验证生命周期、恢复和实际账单；既不能说“不能采行情”，也不能保证永久不断 |
| Queues/Workflows | Queues 至少一次投递；Workflows 有自身步骤、状态和资源限制 | 幂等、报告长期留档仍由应用设计；没有对应失败问题就不引入 |

原始依据：[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[D1 读复制](https://developers.cloudflare.com/d1/best-practices/read-replication/)、[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)、[DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)、[Queues 投递保证](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)、[Workflows 限制](https://developers.cloudflare.com/workflows/reference/limits/)。

尤其要区分：Sessions 的顺序一致性并不意味着整个报告生命周期中的多个查询自动冻结在同一个业务快照。U1 的数据版本约束仍有必要。

### 7.4 成本表达

查询时，[Workers 官方定价](https://developers.cloudflare.com/workers/platform/pricing/)包含最低 5 美元/月的付费订阅；[R2 Standard](https://developers.cloudflare.com/r2/pricing/)存储为 0.015 美元/GB·月，Class A 为 4.50 美元/百万次，Class B 为 0.36 美元/百万次，并有适用免费额度和计费取整。R2 直接出站不另收其数据传输费用，不代表关联计算与其他服务免费。

这些是**单价，不是本项目账单**。独立服务成本、所需数据套餐和模型费用未知。估算至少需要：实测事件率与编码后大小、保留期限、重放频率、对象数量、请求次数、峰值计算、模型调用与重试、备份以及人工维护。

不假设固定压缩比，不把每个 tick 上传成单独对象，也不把自托管等同免费。选 B 时必须明确谁负责磁盘、重启、补采、版本升级、备份和恢复。
