# 币安插件怎样补足四页数据工作台：研究与复用手册

研究日期：2026-09-27。范围：当前 Codex 会话可调用的币安工具、币安官方资料、GitHub 项目与社区讨论。状态：**研究已完成，接入建议未实施**。这是补充资料，不替代[当前开发方案](repository-development-plan-2026-09-27.md)，也不表示需要重做已经完成的采集。

## 1. 结论与适用边界

保留本系统作为连续采集、历史保存、四页展示和证据导出的主体。插件最有价值的用途是：**核对数据、补查具体问题、低成本试验新指标**。先证明它能发现错误或减少人工查数，再决定是否把某项能力做成网站功能。

- 当前会话发现 89 个币安工具，完成或复用了 5 项小规模公开数据查询。不能由此推断所有工具均可用、历史完整，或服务有特定可用性保证。
- 工具清单是会话能力快照；未核实当前连接器的软件包版本、内部部署方式及其与官方 Agent OS 的关系。插件目录搜索未返回条目，不能据此否定已可调用的工具。
- 本轮未安装新插件，未运行社区安装脚本，未读取账户、下单、导入数据库或调整采集频率。没有重新执行生产健康审计。
- 网站和插件都读取币安时，属于两条读取路径的交叉核对，不是两个独立市场来源。插件不能凭名称绕过本仓库的来源核验。
- Codex 仍用于用户主动发起的研究与开发；本建议不恢复退役的模型任务、CLI 队列或云端自动报告。

## 2. 先分清四种“币安插件”

| 对象 | 本轮确认的事实 | 对本仓库的价值与限制 |
| --- | --- | --- |
| 当前 Codex 会话中的 Binance 工具 | 89 个可调用工具，主要为公开市场查询；本轮看到的清单没有下单、账户余额、持续 WebSocket 或实际强平事件历史工具 | 可立即用于有界查询；不把未暴露的能力想象成已接通 |
| [币安官方 Skills Hub](https://github.com/binance/binance-skills-hub) | 官方仓库以 SKILL.md 等文件描述操作流程；部分流程调用 CLI 或需要凭据 | 借鉴参数、任务流程与数据语义；它不是当前连接器的实现证明，也不是装上就有完整采集系统 |
| [Binance Agent OS 官方公告](https://www.binance.com/en/square/post/360313703798060) | 官方 Binance Blog 介绍了面向代理的 MCP、Skills 等集成，范围包括市场、交易与账户能力 | 产品能力可能比当前会话更广；必须按实际工具和权限区分，不因研究需要扩大到账户或交易权限 |

## 4. 四页分别能得到什么

| 工作台 | 插件适合补足的工作 | 仍由现有系统或其他来源承担 |
| --- | --- | --- |
| 行情 | 指定已收盘窗口的 OHLCV 核对；区分现货、合约成交价、指数价与标记价；按交易规则检查精度 | 连续采集、长历史、跨周期一致性、缺口标记和页面状态 |
| 足迹/订单流 | 小窗口 aggTrades、主动买卖量与聚合结果的抽查 | 完整成交覆盖、断线续接、持续足迹计算；少量最近成交不能证明整段历史完整 |
| 强平 | 补看币安 ADL、保险基金相关公开状态，作为明确分栏的背景信息 | 实际强平事件采集、分所展示和覆盖率；ADL、订单簿和清算风险推算都不能伪装成已发生强平 |
| 衍生品 | OI、资金费、多空比例、基差相关价格、币安期权的按需查验与新指标试验 | 已有跨所数据、Deribit、宏观、稳定币等；币安插件不自动补齐这些来源 |

## 5. 推荐的七个复用流程

### A. 对同一窗口做数据核对：第一优先级

输入固定为交易所、产品、symbol、周期与 UTC 起止时间。优先选择已经收盘的 30 根 5 分钟 K 线；窗口使用明确的左闭右开约定。分别记录系统和插件的取数时间、请求参数、返回范围及原始结果。

按开盘时间逐根匹配，再比较 OHLCV、记录数量、首尾时间、重复和中间缺口。先核对现货/合约及价格类型，不对身份不同的数据算“误差”。数值字符串保留原件，容差依据实际精度或规范化规则设定，不统一拍一个百分比。

输出分为 PASS、FAIL、REVIEW、FLAKY：同口径且满足比较规则才 PASS；确认漏棒、重复或映射错误为 FAIL；时间/单位/来源不清为 REVIEW；重复观察不稳定为 FLAKY。零值与缺失值必须分开。当前 OI 和未收盘棒会随两次请求之间的市场变化而改变，不直接判采集错误。

价值：发现“接口成功、页面有数，但数不对”的问题。验收应包含一组已知正确结果、一组人为缺失和一组身份不匹配结果，而不是只证明请求返回 200。

### B. 用真实响应做字段映射回归

本次头部持仓比例工具返回 `longAccount` / `shortAccount`。字段名看起来像账户比例，实际业务含义要由所调用的“头部持仓比例”操作决定。[币安市场数据文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)和实际操作响应需要一起核对。

当前 `datasets.mjs` 已包含从这两个原始字段映射到持仓比例字段的兼容处理。本手册不把它再报成待修缺陷；建议把本次真实样本复用为回归输入，验证数值、单位、原始字段保留和错误空值传播，避免未来替换数据源时退化。其他接口也应采用相同办法，不能只用按实现反写的理想样本。

### C. 补查有明确起止时间的小缺口

先确认系统缺的是原始记录、规范化记录还是展示状态，再查询插件是否支持该产品、周期、时间参数和分页。仅有最近 N 条的接口不能承诺补到任意历史。

有结果时先做本地暂存和范围报告：请求窗、实际返回窗、重复数、缺口数、来源、单位、是否收盘。只有确认与规范数据集契约一致，后续实施任务才考虑接入现有回补入口，不把一次插件回复直接覆盖生产数据。

对于 K 线、成交等历史，[币安 Public Data](https://github.com/binance/binance-public-data)是独立于插件交互方式的归档补充入口。实现时核对具体产品和文件类型、下载校验、时间单位及更正记录；逐文件验证后再做业务连续性检查。[Issue #484](https://github.com/binance/binance-public-data/issues/484)报告了归档中断档、重复与校验文件同时存在的情况；这是未经本轮复现的用户报告，只用于提醒“文件校验正确”不等于“业务时间轴完整”。

### D. 用成交样本核对足迹，而不是拼一个假完整窗口

选择短而完整的已结束窗口，核对 aggTrades 的成交时间、价格、数量与主动方向，按本仓库同样的价格档位和时间桶聚合。实施前核对当前交易所字段定义；买方为 maker 通常对应卖方主动，不能只凭字段名把买卖方向反过来。

先证明采样覆盖整窗，再比较买量、卖量、delta 和桶边界。命中条数上限、分页缺段或窗口边缘不完整时，输出覆盖不足，不把少量成交外推成整小时/全天足迹。订单簿快照只能描述当时挂单，不能填充过去已成交的足迹。

### E. 四页证据导出 + 插件补查 + 人工研究记录

以已有工作台证据导出作为固定输入，让 Codex 先读身份、来源、观察时间、覆盖和缺口，再针对具体疑问调用插件。例如：“这个 OI 变化和价格上涨属于同一窗口吗？”优先比较证据，不先让模型编原因。

当前导出明确带有 `atomicSnapshot: false`，四页不是同一瞬间的数据库事务快照。分析需要保留各部分读取时间；补查结果标为“导出后追加查询”。回看历史时，后来查到的当前值不能塞回过去，造成事后信息混入。

借鉴社区 [TradeMemory](https://github.com/mnemox-ai/tradememory-protocol/blob/master/skills/binance-skills-hub/trade-memory/SKILL.md)记录决策背景的思路，先采用简单研究记录：问题 → 证据 → 假设 → 反证条件 → 后续观察。无需引入其框架、交易执行或新的持久化服务；该项目路径中的 Binance 字样也不代表官方认可。

### F. ADL、保险基金和币安期权：先回答一个新问题

ADL 可用于询问“当前去杠杆风险状态有没有变化”；期权可用于查看选定到期日、执行价和时间点的 IV、Greeks 与持仓分布；保险基金信息可作为交易所机制背景。先用按需查询验证是否为现有四页带来新的解释依据，再讨论周期采集和新增卡片。

必须保留交易所、合约、到期日、计价单位与观察时间。币安期权不能直接替换 Deribit；隐含波动率不能当作已实现波动率；仅凭公开 OI 和 Greeks 不能断言交易商净持仓方向或真实 gamma 敞口。ADL 不等于爆仓金额，也不是清算热力图。

### G. 排名、热点和社会讨论：作为研究线索

[官方 crypto-market-rank Skill](https://github.com/binance/binance-skills-hub/blob/main/skills/binance-web3/crypto-market-rank/SKILL.md)本次所读元数据版本为 3.0，包含社会热度、趋势、部分链上资金与交易者排名等分类，各操作覆盖范围不同。它可以启发“BTC 是否与市场广度一起变动”的研究，但不能据此认为当前 Codex 的四个概览工具拥有同样全部能力。

要记录排名覆盖的市场、时间窗和定义。搜索热度、社媒热度、涨幅与资金流是不同量；不要从“热门榜前几名”直接推出资金进入 BTC，更不要把插件生成的分析文案存入原始数值表。暂不为此扩大固定采集任务。

## 7. 未来接入时的数据收据

插件返回通常不足以直接满足本仓库的规范数据契约。建议先建立本地核对收据，最少包含以下字段；这是建议格式，尚未新增数据库表或生产 schema。

| 信息 | 用途与规则 |
| --- | --- |
| 工具身份与版本 | 保存完整工具名；版本查不到则空，不编造版本 |
| 输入与市场身份 | 参数、交易所、现货/U 本位/币本位/期权、symbol、价格类型、周期及单位 |
| 两类时间 | 上游观察时间与本次客户端取回时间分开，统一说明 UTC；历史复用样本未知调用时间留空 |
| 两类来源 | provider=Binance 与 transport=Codex Binance plugin 分开；上游主机未暴露则留空，不能自行填 fapi.binance.com 以通过核实规则 |
| 原始响应 | 保存公开返回结构与内容摘要/哈希；认证头、密钥、私人账户信息不进入资料快照 |
| 请求和覆盖窗口 | 请求起止、实际首尾、条数、分页、是否完整、是否收盘及保留限制 |
| 核对结果 | 系统证据身份、规范化版本、容差依据、逐项差异和 PASS/FAIL/REVIEW/FLAKY |
| 派生解释 | 与原始数值分开，标明假设、作者/模型生成属性和支持证据 |

除非另外核实端点来源，否则这些收据只能证明“某个工具在某次查询返回了这些内容”。它们不能自动升级成交易所官方主机直采记录，也不能证明过去持续采集没有中断。
