## 3. W1：历史来源、时间与覆盖

**用户可见结果：** 最新报价可以继续看；一段历史未核实来源或存在缺棒时，明确显示范围和限制，不把“最新写入成功”当作整段历史都经过验证。

已复现的起点：旧 `klines` 表无逐棒来源/收据字段，desk 用最新 `sync_status` 证明整个窗口，并把旧棒收据统一赋成最新写入时间。规范数据集已有缺口标记，但 desk 装配丢失该标记；500 根中间缺一根仍可返回质量通过。见审查记录 F1/F2。

实施方向与边界：

1. 使用下述增量契约区分产品身份、历史来源核验依据、观察/接收/存储时间、收盘证据、请求窗口覆盖和持续采集已知缺口。未知值保留未知，不把响应时间伪装成历史接收时间。
2. 规范观察与 live tape 进行有界合并：最新尾部负责展示新鲜价格，能核实的规范记录负责历史与确认语义。优先复用现有来源/时间字段；不能证明的旧历史标记未核实，不直接清洗、补标或整库替换。
3. 检查相邻棒时间连续性并保留服务端已知缺口；区分“本次尾部只返回 20 根”“研究窗口不足”“窗口内部缺棒”“窗口外仍有待补缺口”。禁止把正常尾部轮询当全历史损坏。
4. 报价可用与某个指标研究窗口合格分开。按实际计算所需连续窗口约束确认/结构结果；不因为一个旧缺口关闭全部最新报价，也不继续给断裂窗口输出已确认信号。
5. 检查查询边界和索引。统计真实 D1 `rows_read`/`rows_written`；覆盖检查不得把每秒 tail 请求变成每次扫描 6000 根。历史失效通知采用下述最小增量存储；其他索引按查询计划和扫描实测确定。

### W1 的接口与数据规则

本地接口版本已提升为 `2026-09-27.1`，保留现有字段。旧客户端仍可读取原形状，新客户端遇到缺少新证据的旧响应按未知处理；生产版本须单独核验。

| 对象 | 必须表达的语义 |
| --- | --- |
| 读取 | 内部 `readIntent=window/tail`；`window.from/to` 为 UTC 开盘时间毫秒的左闭右开范围。HTTP 保留现有 `interval`、`tail`，添加有界 `from/to` 供修订重读；非法/反向窗口返回 400。当前仅支持 BTCUSDT，其他产品不得静默返回 BTC |
| 读量 | full 最多保留现有 6000 根结果；tail 保留现有 2～200 根限制，主图继续 20 根。两条来源查询都在 SQL 层限定范围/条数，另查至多一根前驱用于交界检查；不再先通读 1000 条规范观察、完整 COUNT 后切片 |
| 返回范围 | `requestWindow`、`returnedRange`、`coverageScope=window/tail`；覆盖信息区分返回根数、已核实根数、窗内缺口、服务端已知缺口及截断。未计算的全库总数为 null，不把 tail 的 20 根写成全历史可用总数 |
| 每棒证据 | 保留 OHLCV 与现有时间字段，新增/传递 `origin`、`effectiveReceivedAt`、`sourceVerification=verified/unverified`；`closed/finality/closureBasis` 随被选中的整条记录走。未知来源、收据及收盘证据显式为 null/未核实 |
| 时间 | 规范 live 行的 `received_at` 可能是开盘时间存储身份；采用 `readDataset` 已提供的 `effectiveReceivedAt` 表达实际收据，并保留原身份用于追踪。`asOf` 是装配时间；当前采集状态标 `stateScope=current`，不能冒称 knownAt 当时的健康状态 |
| 可用性 | `pricePathAvailable` 只表示当前价格路径是否可用；每个分析方法另按自身需要的连续、来源可证、已收盘窗口决定资格。不能以顶层 quality=pass 或固定 128 根替代实际窗口检查；缺少方法窗口定义时不输出确认信号 |

合并键是产品＋周期＋开盘时间。先按 `readDataset` 现有已确认优先、有效收据次序选出规范版本；它存在时选择整条规范记录，原始行仅补没有规范证据的位置，并保留未核实标签。不得把规范行的来源/收据贴到数值不同的原始行上，也不得让未知原始行覆盖已确认行。尾部尚未进入规范集时允许显示其价格，但收盘证据仍未知；最多等待既有写入节奏，不为追求更快显示增加写频。核验来源还须匹配数据集的产品与真实源主机，不能仅判断字符串包含 `binance.com`。

特殊周期按分析窗口处理：3 日使用币安 USDⓈ-M 官方 `3d` K 线，开盘对齐为相对 Unix 三日网格偏移 1 天；错位的旧聚合棒不作为规范历史。规范保留至少覆盖指标窗口：5 分钟 900 根（研究窗 864），其余周期保留 600 根，分别覆盖 15 分钟 480、1 小时 336、4 小时 360、1 日 180、3 日 180、1 周 156。页面仍可显示更长的原始窗口，但只有连续已核实收盘棒进入确认分析。

`knownAt` 只筛选截至该时刻可见的真实收据/版本，不用今天的可变 live 行倒推过去；无法重建的点保留未知。当前四页仍使用实时读取，不在这轮顺带承诺历史时点重放产品。

### W1 的修订与查询验收

同一根棒的 OHLCV、来源证据、收盘状态或覆盖改变，都必须使内容版本变化；不要把响应时间放进内容摘要使每次空轮询都失效。tail 内容版本覆盖返回的整条值与证据；历史版本负责通知 tail 外变化，两者分开。

默认增加 BTC D1 小表 `desk_history_state`（已新增，按产品/周期一行），保存 `head_t` 和单调 `history_revision`；现有 DO recovery generation 只表示补缺任务代次，不能充当内容版本。固定以最新 20 个周期格点为失效边界，使用方 tail 至少 20 根才能依赖该保证；少于 20 根的兼容读取不能替代完整更新流，离线落后超过 20 根仍须 full。正常 tail 内价格刷新不递增历史版本。写入、删除或证据/缺口变化涉及 tail 外时，在同一 D1 batch 内按提交时数据进行 SQL 差异判断、版本递增和数据写入，差异判断须复用实际 upsert 的接纳条件，不能用事务外较早的 JS 查询判断。相同值的新收据不单独触发 full；来源/确认改变仍应触发。

覆盖原始表写入总口、直接历史扩展、`persistDataset`、WS/REST 规范写入、`cloudflare/finance/scheduler.mjs` 缺口登记，以及 `scripts/collect-finance-datasets.cjs` 的 SQL 导入生成器。原始表和规范表现有两个提交批次允许各自升版；任一成功的部分进展必须可见，失败批次不得空增版本，不能等整个补采最后成功才记版本。保留清理若只推进有效起点，可返回起点让客户端裁剪；其他会改变已加载证据的删除仍须失效通知。

状态行第一次创建时，`head_t` 必须按该产品/周期已有有效数据的最大开盘时间初始化，之后在事务内单调取最大值；不能从 0 或首个旧补采批次开始，否则会把第一次旧棒修正误当 tail。初始化版本仍可为 0，不回填逐棒来源。WB-03 增加“建表后首次 full，再首先写入一段旧历史补丁”的用例；事务失败测试使用真实 SQLite 事务或等价 D1 隔离环境，不能用逐条自动提交的 mock 宣称批次回滚已验证。

full 读取在同一 batch 取得数据与对应历史版本。客户端只有完整窗口成功更新后才确认该版本；tail 发现更新时将重读合并为一个待办，不把新版本提前记为已消费。第一版只在历史版本变化时有界重读当前已加载窗口（不扩到全库）；重读期间又有新版本则再收敛一次。失败保留“待更新”状态，受现有退避约束，禁止每秒重试 full。对象重建不丢版本，旧响应不能覆盖更新版本。

1. 暂停期间先完成拟发布阶段及其相邻消费者的本地/隔离验收。W1 可独立交付给下一开发阶段，不必等待全部 W4 才验收；生产发布必须具备完整兼容边界。
2. **部署前**更新受影响前端资源 `?v=`，运行 `npm run build` 和相关浏览器验收；冻结源码/配置/迁移/资源指纹，记录旧 Worker 与 Pages 恢复点。`deploy:pages` 会重新生成静态产物，发布期间不得混入并发修改；最终核验实际上传与生产返回内容，不能只看旧 dist。
3. 只有需要真实联调且用户明确要求“开起来/恢复云端”时，先读取当前恢复记录与远程状态，核对正式版本、三个 D1、两个 DO、Cron/域名，再执行 `npm run cloud:resume` 恢复已保存版本。不要用业务 `wrangler deploy` 绕过暂停，也不要把恢复旧版当部署新版。
4. 增量 SQL 经隔离验证后，核对 BTC 数据库、语句和恢复点再执行；新 schema 须兼容仍在运行的旧版本。然后部署 BTC Worker → 其他确实改变的 Worker → `npm run deploy:pages`。不部署未改的快照/舆情 Worker；Pages 脚本含 production/preview 各保留最新 8 条的清理，记录所需回退部署是否仍保留。
5. 核对生产 `index.html` 版本和 JS 指纹及受影响 hash；运行 `verify:api`，再按改变的行为核验 desk、7 周期/缺口、真实页面和来源时间。复查云端开关的恢复基线与新正式版本对应；不能让下次暂停/恢复又切回老代码。失败先恢复已记录的兼容版本，保留新表与数据，不自动删库/删表。
6. 记录有明确起止的同分布采样：请求、CPU、D1 读写、延迟和活跃 DO；验证未增加无界扫描/写放大。单次成功和费用模拟不证明整月账单或长期稳定。
7. 在本文件相应 W 项更新实现、离线、浏览器、生产四类证据及精确下一步。若仍暂停，清楚记录“本地通过、生产待验”，不能写成已上线。Git 备份按用户明确指令执行。
