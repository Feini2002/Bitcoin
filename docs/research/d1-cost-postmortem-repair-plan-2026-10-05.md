## 1. 决策摘要

这次异常主要是系统工程问题，不能归咎于用户多点页面，也不是 Cloudflare 把“新数据条数”算错。系统把历史状态检查放进高频采集事务；该 SQL 在实际 D1 上采用了高扫描执行路径，而此前验收没有覆盖这条路径的真实行读取成本。

**关键修正：状态已存在时，问题不一定是 MAX 子查询仍被求值。** 本次取得的线上 INSERT 执行计划显示：历史存在性判断被展开成历史索引循环，状态存在时跳往循环的下一行，最终不插入任何记录，却仍遍历历史。Python所带SQLite 3.50.4先检查状态并退出；继续审查在本机Node所带SQLite 3.53.1重现了与线上相同的关键循环形态。不是“所有SQLite都正常、只有CF异常”。线上确切引擎版本仍未知。此前“每次初始化都计算历史最大值”的描述由本文替代。

**推荐分两阶段：**

1. 保持原数据语义，先用明确短路的条件保护两类初始化查询；不改 schema、不删历史、不降低采集频率。完成真实 D1 完整事务验收后，才把它视为可发布的止损修复。
2. 再按实测剩余消耗，处理非 K 线的重复最新值计算、无消费者的状态维护、版本选择查询和清理成本；建立整条采集及读取链路的成本验收。不能只修最显眼的 SQL 就宣称整个系统成本合格。

**本次继续审查新增一项可复现的准确性问题：** 原始行情与规范数据不是同一笔事务。合成故障下，原始值已更新为101，规范写入失败，图表仍显示旧值100且标记采集未过期。它不是已证实的历史生产事故，也不是本次96.152亿初始化读取的替代原因；但必须纳入恢复前的正确性条件，不能用“单个 batch 会回滚”掩盖。

不建议现在迁库、购买更高套餐、清库、直接关掉正确性检查，或把成本转移到 VPS。它们不能代替查明和消除无效工作。

风险：文档修改为 L1；后续方案含持久数据与生产基础设施，实施按 L3 核验。风险等级不代表本轮获得上线或恢复授权。

## 2. 第一性原理：系统到底需要付钱做什么

系统的价值是：保留能追溯的市场事实，用符合时间和来源口径的数据支持图表及研究。数据库的工作量应与新增事实、真实修订、用户请求范围有关，而不是与“已经保存了多久”不断相乘。

### 2.1 四种数据不能混为一谈

| 对象 | 必要行为 | 不必要或危险的行为 |
| --- | --- | --- |
| 形成中的 K 线 | 接受较新的更新，保留收盘状态及来源边界 | 每次更新重查整个历史；把未收盘当最终事实 |
| 已收盘 K 线、真实修订 | 幂等写入，必要时使历史缓存失效 | 因值相同就删掉所有不同取得时点的证据 |
| 宏观参考期、盘口等不同数据集 | 依据本类键、时间单位和版本规则保存 | 把任意字符串键强制转为统一毫秒时间 |
| 最新时间、缓存修订号、采集状态 | 用小状态行维护派生信息 | 为维护一行状态反复遍历全部历史 |

稳定状态下一批新数据的数据库工作，应近似受输入行数及其相关版本数约束；查询 N 根窗口应受 N 和相关版本数约束。冷初始化、历史修订和回补可以做更多工作，但必须有明确范围、次数和预算，不能混进每 5 秒运行的常态路径。

### 2.2 计费公式与正确度约束

- 总扫描量 = 各类操作的调用次数 × 每次真实扫描行数；必须分别降低不必要的频次和单次扫描，不能只看请求数。
- 已写行包括插入、更新、删除和索引维护。它不等于独立新事实数，更不等于报告数或投资收益。
- 判断状态已存在原则上只需主键查找；写入 0 行仍可能扫描大量行。
- SQL 中把便宜条件写在 AND 左侧，不保证执行器按程序员想象的顺序执行；EXPLAIN 出现索引也不代表只访问少量索引项。
- 降费不能破坏 knownAt、observedAt/receivedAt/storedAt、形成中/已收盘、来源/产品隔离、迟到修订、事务回滚及缓存失效语义。

Cloudflare Paid 当前包含每账期 250 亿读取行，超出部分每百万行 0.001 美元；写入另有额度和单价。额度按订阅账期、账号共用，不能把北京时间自然日或单库额度直接当账单。来源见第 11 节。

## 4. 根因链：为什么会放大到每天几十亿行

### 4.1 实际执行路径

交易所 WS → VPS 出口 → KlineLiveComponent 合并待写更新 → 原始 klines 落库与同步状态 → 规范观测落库 → 历史状态和修订维护。

另外，Cron 有界补尾、REST 断线恢复、5 秒级 premium/OI/book 快照、低频规范数据采集，也会进入相关状态维护逻辑。VPS 是出口，不保存这里的 D1 历史；本地 Agent 和浏览器是消费者，不是这些持续任务的唯一启动条件。

当前七个 K 线周期、每周期最快 5 秒一次，理论常态上界为 7 × 86,400 ÷ 5 = 120,960 次/日；收盘、回补、失败重试和去重会改变实际数值。这与原始 K 线初始化约 12 万次/日的量级吻合，但不是精确归因日志。

### 4.2 主根因：廉价判断被高成本循环包住

原意是“状态不存在且有历史时，只初始化一次”。实际 D1 计划先进入数据集历史索引，在每个候选上判断状态是否存在；发现已存在后跳到 Next，而不是跳出整个查询。因此，**逻辑上的不修改，并没有实现执行上的不遍历。**

远程规范 INSERT 的字节码关键位置：3–10 打开并定位历史索引，11–25 计算状态存在性，26 在存在时跳到 67，67 为历史索引 Next，再回 9；MAX 子查询在 34–60，暖态无需进入。这解释“零写入、大读取”，也解释此前仅优化 head UPDATE 为输入最新值为什么没有消除费用。

候选使用 CASE：状态已存在直接返回 false；只有缺失时才检查历史是否存在。线上计划先读状态，绕过外层历史循环；SQLite 的 CASE 具有明确短路语义。修复依赖这一语义和实际 D1 计数，不依赖 AND 条件书写顺序。

### 4.3 放大器与过程缺陷

1. 高频路径复用通用历史维护，原始和规范两套数据均执行检查；数据职责不同，但派生状态工作重复。
2. 非 K 线仍用 MAX(CAST(observation_key AS INTEGER)) 更新 head；同一条 UPDATE 可能为比较和赋值扫描两次。它是主热点修复后仍然显著的成本。
3. 图表、研究的版本选择与保留清理还有范围放大，不能只看 LIMIT、返回行或是否使用索引。
4. 之前的测试把 K 线 head 更新 `after[1]` 与图表尾部作为成本对象，漏掉 `after[0]` 初始化和整个写事务。SQLite 3.50.4与线上执行差异进一步遮蔽了问题；本机3.53.1已能重现计划形态，因此后续必须记录实际测试引擎和目标语句，不能笼统写“SQLite验证过”。
5. 验收强调页面时延、HTTP 200、build 和数据推进，没有对 24 小时无人访问采集成本设验收，也没有把保留历史增大十倍作为整链路成本测试。
6. 现有 `desk` 仅汇总部分请求的 rows_read；高频写入的返回 meta 大多丢弃。无法及时把每日账单增长定位到操作类别和有效变更。

这不是用户先前允许高频采集的责任。高频要求解释调用频率；它没有授权每个无变化检查遍历历史。工程实现和验收必须显式承担成本正确性。

### 4.4 第二轮发现：通用状态承担了不属于它的职责

读取所有 `desk_history_state` 的实际消费者后，当前外部返回 head/revision 的业务入口集中于 `desk.mjs` 的当前行情图；历史 knownAt 明确返回 null。其他数据集也创建和更新同一类状态，目前可见消费主要是维护逻辑自身，并不是每个研究岗位都需要这些 head。

- 线上 FRED、SOFR、规则、网络费率等状态 head_t 为 2026。原因是日期/ISO 字符串键经过整数 CAST 只取到年份；它不是正确的毫秒最新时间。
- crypto-breadth 的键来自秒级 updated_at，其状态为秒值；K 线为毫秒。现有泛化字段没有统一的时间域。
- 源码实际计算出的现货 1h 和永续 1h 状态键都是 `BTCUSDT + 1h`。这是共享状态身份冲突，不等于两张行情事实表已经混写，也不能据此宣布历史报告已错误。
- `persistLiveKlineBar` 等返回值表示处理数量，部分路径固定返回 1；不能直接拿来统计“实际新增有效事实”。后续指标必须区分接受、修改、覆盖和重放。

这些问题直接影响本次“取消重复状态工作”的范围与正确性，须写进 P2；但不是主初始化扫描已被定位的替代解释。不能为了让数字看起来一致，给所有无消费者的 head 再补一套日期解析和迁移系统。

### 4.5 继续审查：两次提交不能当作一笔事务

`kline-live-collector.mjs`的`persistOne`当前依次完成raw批事务、`sync_status`成功标记、每行canonical批事务。`binance-klines-worker.js`的raw持久化又按100行拆批；REST恢复也先写raw再写canonical。因此D1单次batch的回滚保证不覆盖整个调用链。

本轮[离线探针结果](d1-cost-review-2026-10-05/adversarial-local-result.json)使用当前真实采集方法、持久化SQL和图表入口，数据库适配器为Node 24.18.0内置SQLite 3.53.1，未联网：

1. 同一形成中K线初值100；注入下一次canonical事务失败后，raw为101、canonical仍为100、sync成功为1；采集器自身成功计数没有增加。
2. 真实图表组装先放raw、再以canonical覆盖同开盘时间，因此该合成场景返回100，`collectionStale=false`。
3. 用相同取得时间重试后两份数据收敛为101，规范表仍一行；raw批事务先失败时则没有执行后续步骤。说明已有部分幂等能力有效，但不能证明崩溃重启、收盘或多批回补都可靠。

不能只把成功标记移到函数末尾就宣称解决：之前的成功标记仍可能在90秒新鲜窗口内，进程也可能在两次提交之间中断。缺口是跨投影提交及可见性合同，修复见P2c。原始与规范事实职责仍保留，不以删除一份数据解决。

## 6. 分阶段实施方案

### P0：冻结基线与补齐成本归因

- 先记录实际暂停状态、业务恢复版本、D1 结构、查询指纹、账期和时区；不重置恢复文件。
- 保存本案两天指标、SQL 归组、精确只读对照和本地反证。后续成本比较使用同一输入、保留量、调用频率；不能拿“页面关闭”与“多页面同时打开”直接比较。
- 对完整采集事务逐条收集 `rows_read/rows_written/changes`，另按事务加总；同时计输入、接受、重复、迟到拒绝、真实修订、收盘棒及失败。changes 仍不是独立事实量，需要业务分类。
- 指标优先在调用点内存汇总和有界结构化日志输出；不为每条 SQL 再往 D1 写一条审计记录。低基数维度用操作类别、数据集、入口来源，不记录凭据或整段市场材料。
- `cloud-control.cjs`的暂停验收会对部分表执行MAX/GROUP BY。它适合有界开关核验，不能直接每几秒重复调用充当免费监控；观测、造数、核对和清理本身的读写也计入各自预算。
- P0 产出是可比较基线，不是额外后台系统或新的模型任务。

度量要求：每条语句固定操作名，不把整段 SQL/receipt ID 当日志维度；每个完成 batch 只加总一次。记录异常及按分钟汇总的正常计数，日志自身也限量。失败、超时或重试若未返回完整 meta，成本记为未知并单列，不能按0计；采样结果标明估算，不用它声称精确硬限额。多 Worker 实例的内存计数只是局部观测，不能冒充账号全局余额；每日真实用量以 D1 平台统计校对，延迟入账与新发生消耗分开。云端关停后执行的诊断查询也单独归类。

### P1：不改语义的止损修复

- 修改 canonical/raw 两个初始化谓词为明确 CASE 短路：状态存在立即跳过，仅缺失时判断历史并计算原基线。
- 保留原事务位置、参数、初始化 head 和 revision 规则；不使用进程内“初始化过”标记作为正确性的唯一依据。
- 不把原 guard 拆成无保护的应用层“先 SELECT 再 INSERT”，防止并发冷启动冲突；不把 INSERT IGNORE 当成不求值历史子查询的保证。
- 同时检查 gap、read baseline、bump 内同类 EXISTS 形状。只有精确证据表明高成本或合同要求一致时修改；baseline 本次暖态计划已先跳出，不能笼统说所有初始化都坏。
- 单次初始化首次扫历史仍可接受，但要单列成本且只在状态缺失时发生。冷态不应以本批较旧输入覆盖已有更晚历史 head。
- schema/索引保持不变，不需远程数据迁移。热查询优化不能以先删状态行重建作为步骤。

### P2：处理剩余成本与正确性

- 按 P1 后的操作成本排序，先验证通用 head UPDATE、历史版本读取、bump 判定及保留清理。
- **默认推荐 P2a：把图表缓存修订状态收窄到现有消费者真正需要的永续 K 线身份。** 原始 klines 与对应永续规范集共同维护该身份是有意的；现货、宏观、premium/OI/book 等不应因为经过通用存储函数就维护图表状态。实施前核对源码、所有 API 响应和导出合同；若发现真实消费者则停止该类别移除，单独给出类型化方案，不能静默改变接口。
- 停止非消费者维护时保留现有状态行，不删表、不重建事实历史；删除的是未来的无效工作。预计无需 schema 迁移，但必须据实际实现再次确认。相关“任意数据集都必须生成 history SQL”的旧测试要改成业务契约测试，不能为了旧实现断言保留无用逻辑。
- 收窄判断必须同时覆盖canonical前置bump/后置init与head、scheduler的gap维护和本地bootstrap导入；raw及图表baseline继续限定为其永续身份。仅删通用head UPDATE仍会留下初始化和bump读写，不算完成。历史遗留行保留不代表后续继续维护。
- 现货/永续状态分工调整时，单独核对既有 `BTCUSDT + 1h` head 是否受混用影响。若需要校正，只能按永续 raw/canonical 实际历史重建派生基线，保留已有 revision 并显式失效缓存；不得清零 revision 或抹掉历史。该步骤属于未来远程数据操作，不在 P1 或本轮中执行。
- 对剩余确需 head 的系列，用本次成功接受的数据维护单调最新值，只比较同一种时间单位。不得把所有输入行的最大时间当成已提交数据；乱序、拒绝和事务失败不能推进派生状态。冷初始化仍需考虑已有历史比本批输入更新的情况。
- **暂不做 P2b：新增通用跨产品状态表。** 只有确认实际消费者不能用收窄方案满足时，才设计带产品/数据集身份、明确时间域的新状态；迁移成本、兼容和回退另列。原始与规范双写是两个数据合同，不能直接合并删除。
- 版本查询坚持有界选 observation key、再选择截止时间可见的正确版本；不能用“全表 LIMIT 20”或只留最新版本替代历史语义。
- 保留清理按有界批次和实际到期分片执行；不改变用户历史保留要求，不对全库每分钟反复排序。
- 对“同 receipt、同内容”和“新 receipt、同内容”分别处理。前者幂等；后者可能是必要的新观察/取得证据，不能统一用内容哈希丢弃。

P2 不是先增加全库表达式索引。CASE 已用现有状态主键将暖态检查降到 1 行；额外索引会增加写入和存储。只有剩余查询的实际行计数证明有收益时，才提出局部索引及受控迁移。

**P2c：封闭已复现的部分提交缺口，独立于P1提交。** 推荐先针对同一D1内的一条WS更新或一个有界REST分片，复用SQL构造器，把raw、canonical及其head/revision与对应成功标记组成同一batch；不引入分布式锁、新队列或通用审计表。读取验收不得出现“旧canonical覆盖新raw却宣称本次成功”。

- 所有接纳/拒绝条件须落实在该事务内；不能只把现有两个异步函数塞入Promise.all。保留source、receipt、closed、已收盘修订和knownAt规则，不能强迫双投影接受本应拒绝的旧输入。
- 一个分片只有全部必要写入成功才可确认；6000根回补仍拆成平台允许的有界分片，不能拼成无上限事务。跨分片不承诺全量原子回滚，复用已有gap/generation及覆盖核对，最后完整成功才推进覆盖游标。进程中断后重放须幂等。
- 实施前核对单batch语句数/参数/体积限制及写行增量。若合并会违反真实接纳合同或平台上限，保留独立批次，但必须明确持久化未完成范围、失败时取消“已完成”资格、重启后核对两投影再补齐；这是更高写入成本的备选，需要重新评审，不能以调整成功标记顺序替代。
- 测试要覆盖当前已复现场景以及提交间崩溃、第二分片失败、WS收盘与较旧REST交错、旧成功标记仍新鲜、重启后丢失内存pending。未完成这些检查前，P1可作为独立补丁交付，不能宣称准确性和恢复条件全部满足。

### P3：成本与正确性联合验收

- 分开三个变量：H为无关历史键数，V为本次相关键的版本数，B为本批输入量。H放大100倍时固定V/B；V放大时只在固定少量相关键上生成版本，不要求真实相关版本成本恒定。不能把80,000键×100版本全组合默认为云端夹具。
- 离线先测H=800/8,000/80,000、固定V；另测V=1/10/100、固定20个相关键。云端改用可负担的H=10/100/1,000，V轴在少量键单独验证；计划/计数差异出现再决定有证据的扩样，不把小样本冒充80,000行真实D1验收。
- 记录单语句和完整 batch 两种计数，不能仅验证被替换的一句。
- 先离线全覆盖，再独立 D1 验证环境执行完整事务；若本机 workerd 仍不可用，测试环境的创建、写入、预算和销毁需在后续实施授权范围内明确。不得借生产原 INSERT“应当不写”之名测试。
- 成本和结果分别断言。不能通过降低新鲜度、漏写、空结果或把错误吞掉通过成本测试。
- 云端造数、索引维护、旧/新对照、故障重试、清理共用一次预算。先用很小的造数批次量出实际写入放大，再预估下一步并预留清理；不能等大批造完才检查超额。固定夹具复用并保存每步账本，不默认重建全组合。

### P4：发布与有界恢复

- 当前 `cloud:resume` 会恢复保存的旧业务版本，旧版本包含本次缺陷。不能把“本地修好”后直接 resume 当成部署修复。
- 先验证新的业务版本及回退路径，再通过受控流程登记候选恢复点；保持维护版、入口和 Cron 关闭。当前保存的业务版为 `e42aa488-463f-4505-9096-d9bcebe3eef3`，维护版为 `9180e712-a75f-411b-8f14-02e68ec90663`；这里只是本次已核对的基线，执行时重新读回。
- **现有脚本没有暂停期间替换业务恢复版本的完整流程，此能力是实施工作，不是现成命令。** 推荐保留原 restore 快照，新增最小的已验证候选版本记录；由开关脚本登记，不手工改 JSON。登记校验候选绑定和 DO 类/命名空间相同、无迁移、实际代码与验收版本对应，且活跃版本仍为维护版。既有原版本留作追溯，恢复时只使用明确登记的修复版。
- 同步修改 status、dry-run、resume、pause 对候选版本的识别及中断续做；候选上传失败/回执丢失先按已返回版本 ID 查状态，不重复上传或启动。暂停状态下不得用普通 `wrangler deploy` 激活业务版；Worker 版本上传也需核对不会应用迁移或更改触发器。
- 官方支持上传而不部署；触发器另行管理，DO类生命周期改变不能走这种上传。上传前后都须读回维护版、关闭的workers.dev/Version URLs、入口和Cron。**Version URL使用该版本已有绑定资源，不是隔离测试库**，暂停期间不得打开它执行带生产D1/DO绑定的候选探测。[官方部署说明](https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/)、[Version URLs](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/)。
- 预检回退维护版不仅要“ID存在”，还要可重新部署；官方只允许部署最近100个上传版本。失去可部署回退点时先补合格维护候选，不进入试运行，不用旧业务版顶替。
- 用户明确恢复后才启用；先有界观察采集事务、接口、真实写入和成本，再决定继续。恢复失败或成本异常退回无采集维护版本，不回退到会继续烧费的旧业务版本。
- 原舆情和 market-snapshot Cron 为空，恢复不能添上历史日报计划；不得影响同账号其他系统或取消共用订阅。

恢复观察分三种证据，不用同一张“健康截图”代替：

1. 配置：版本、绑定、Cron、域名、旧采集器退役符合新恢复记录。
2. 数据：形成更新、收盘、gap、raw/canonical、revision和研究有界读取符合合同。暂停缺失的不可回放盘口/强平仍标缺失。
3. 成本：先 2 分钟核对高频初始化计数，再至少观察 15 分钟热点采集；小时、日级等低频任务另外回放验证，并纳入一个完整自然日的后台和指定交互用量。规模无关性由固定输入下的100倍历史测试证明，不用两分钟观察推断。尚无24小时证据时，只报告阶段验收，不能承诺下月零费。

建议首2分钟100万、15分钟累计200万读取行作为**提前停止触发线**，不是绝对总额。出现热初始化>8行、数据错误、到期或计量链路失联也结束试运行；未返回meta的在途操作和冷回补另列预先限定的预算，不能当0或无限豁免。

继续审查撤回“维持小流量即可控制后台费”的模糊假设：BTC采集集中在`LIQUIDATION_COLLECTOR/BTCUSDT`固定DO。官方按DO实例分配版本；本项目不能把1%请求分流理解为1%的七周期采集成本。隔离D1/DO合成验证先完成；生产首次试运行使用明确修复版和有界时长，不拿版本百分比当采集限速器。[DO部署语义](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/)

实施必须补齐三个可执行条件：

1. 试运行带固定绝对截止时间，Worker计划入口、DO连接/报警/重试和其他采集入口均遵守，重启不得重新计时或自动延期。到期不接纳新采集，清理本次连接与报警；这项试运行能力当前尚未实现。外部监督仍负责执行完整暂停并读回，不把本地终端退出等同云端停止。status/dry-run须能识别候选截止已过期；阶段通过后仍需按后续授权登记适用配置，不能静默解除截止或回到旧版。
2. 停止动作分开记录“触发停止、关闭入口/切维护、写入稳定确认”。现有暂停至少包含5次间隔30秒观察，脚本8分钟硬截止是排错收口，**不是云端8分钟内必停的保证**；已提交操作不能撤销。没有完整停止确认就保留pausing，报告未知剩余消耗，不宣称触发线未被超过。
3. 试运行总预算需覆盖已返回计量、最大在途批次、计量延迟及停止期间增量、诊断预留。启动前给出有依据的这些数值及可接受总额；目前只有触发线，没有足够证据推导总额，故不能把200万当硬上限直接放量。停止观察也不能每几秒重新扫历史来计量。

现有脚本没有账号级实时扣费熔断。上述是针对本次采集故障的有界试运行条件，不新建常驻监控平台；跨实例/入口计量和停止条件未闭合时，停留在隔离验证，不恢复生产来“边跑边看”。

## 7. 验收矩阵

下列均为后续实施要求；本轮完成项仅限第 3.3 节明确列出的诊断。

| 编号 | 场景 | 正确性断言 | 成本断言 |
| --- | --- | --- | --- |
| C01 | 状态已存在，历史扩大 100 倍 | 状态及数据不变 | 初始化近常数成本；实测目标每次不超过 8 读取行 |
| C02 | 空库、只有历史无状态、仅 receipt | 不凭空生成 head；历史存在时保留正确基线 | 冷成本单列，第二次退回暖态 |
| C03 | 形成→收盘→迟到形成／旧 REST | 最终收盘及较新版本不被覆盖 | 被拒绝输入不得重扫全历史 |
| C04 | 尾部外真实修订、同值重放 | 真实修订使缓存失效；重复不误增 revision | 与受影响键及版本数相关 |
| C05 | 单batch失败、两写者竞争、raw/canonical间中断、第二分片失败 | 同batch一起回滚；跨批部分提交不冒充完整成功，重启可补齐；旧canonical不掩盖更新失败 | 重试成本单列，既有成功标记不能掩盖失败 |
| C06 | 现货/永续同 symbol/interval | 状态及缓存身份不串用 | 无跨产品额外维护 |
| C07 | 宏观迟到修订、A→B→A、knownAt；日期键/秒/毫秒/非时间键 | 原始取得时点和历史可见版本保持；未知时间仍未知 | 无消费者不维护图表 head；不新增全历史转换 |
| C08 | 5 秒采集 + Cron + REST 恢复 | 不漏收盘、gap 如实、有界补洞 | 完整事务总成本达标 |
| C09 | 20 根尾部／6,000 根窗口／多面板 | 结果与优化前可信基准等价 | 固定窗口不随无关历史增长；隐藏页停止消费 |
| C10 | 过期清理、旧缓存返回 | 保留规则不变，已删历史不复活 | 每批上限且不会热路径反复排序 |
| C11 | 无页面、无模型任务的长时采集 | 新鲜度和真实采集持续符合合同 | 单独量化后台基线，不混入页面成本 |
| C12 | 候选上传、Version URL、试运行到期、计量失联及暂停中断 | 维护版仍有效；不通过共享绑定预览唤醒生产；旧采集器不重启 | DO固定实例不能按请求比例估算；记录停止延迟/在途消耗，不承诺绝对费用上限 |

P1 等价性反例必须单独覆盖：空状态+空历史、无状态+更晚历史、已有状态+历史已清理、仅 receipt、多个版本、非数字/日期键、多个周期；保留旧基线取值，即使它暂有类型问题也不在止损补丁里悄悄重定义。P2 再针对有证据的无用状态和身份问题消除来源。

并发验收要复用真实 D1 `batch` 的同事务边界：两个首次写者、同 key 不同 receipt、较旧输入后到、写入中途真实约束失败。必须比较写入前后的 bar、head、revision；另测多batch提交间中断及读者在中间时刻看到什么。SQLite单连接或Promise同时返回不能冒充D1并发验收，revision只作单调失效标识，不当作独立修订事件数量。无需另建分布式锁、审计状态机或全面数据迁移。

复用命令：`npm run lint`、`node tests/integration/verify-finance-incremental.cjs`、`node tests/integration/verify-desk-migration.cjs`及其 `--workerd` 版本、`npm run verify:finance`、`npm run verify:evidence`、`npm run verify:cloud-control`，最终 `npm run build`。前端受影响才运行对应浏览器回归。所有异步命令通过项目有界监督器、每轮观察不超过 30 秒；线上 smoke、diagnose 和生产图表访问留到明确恢复之后。

本次文档交付不跑全量 build，它不能替代方案论证；真实研究和线上 smoke 也不执行，以免唤醒暂停业务。本轮只核验方案数字、引用、证据文件、资料导航和 SQL 诊断；上段命令是未来实现的验收清单。

## 8. 成本与产出目标

- P1 的真实暖态只读样本下降超过 99.9%，**不等于全系统账单下降超过 99.9%**。调用分布、冷态、其他查询、Workers/DO/存储另计。
- 两类初始化曾占两日读取的约 87.7%，是优先修复依据，不是已兑现节省。即使理想消除其绝大部分，两日仍约有 13.448 亿其他读取行，日均约 6.724 亿；不能因此宣布成本问题已经彻底解决。
- 后续同时报告：每日真实读取/写入、每百万输入/接受更新成本、真实修订数、最终收盘棒数、请求窗口完整率、研究成功/有限/失败轮次。模型调用成本与 D1 成本分开。
- “有用”以是否满足图表或研究的数据契约、是否形成可核验新证据判断，不能用报告篇数承诺投资收益。

### 8.1 拟定量化门槛

这些是方案建议的工程目标，尚未通过实测，也不是替用户选定新采集频率。若原有准确性与新鲜度无法同时满足，报告具体成本/功能取舍，不能悄悄放宽门槛或降低数据要求。

| 层级 | 门槛 | 理由与检查方式 |
| --- | --- | --- |
| 热初始化 | 暖态每次 ≤8 读取行；100倍无关历史增长后仍满足 | 真实只读样本为1行；留小量索引开销，不承诺每平台恰好1行 |
| 单键常态写事务 | 固定输入及该键版本数，历史增长100倍时总读取增量 ≤ max(32行,原量10%) | 必须核对整笔事务，冷启动与实际历史修订分开计 |
| P1匹配负载 | 暖态目标类别减少至少99%；未修改类别无无法解释的回升；全链路按该负载实际类别权重核算 | 撤回无条件80%：若目标原占50%，类别下降99%也只能使总量下降49.5% |
| P2目标日 | 24小时原频率后台采集 + 1小时主图及4子面板 + 预先固定的研究取证回放，总读取 ≤1亿行；单列匹配旧版降幅 | 约30亿/月为工程目标；撤回无条件95%，不同负载不能套用历史两日分母 |
| 写入与正确性 | 相同接受输入下写行原则上不增加超过5%；增幅需逐项解释；最终数据合同全通过 | 防止把读费简单转成更多索引/日志写费 |
| 云端测试预算 | 整次申请预算读取1000万、写入10万行，包含造数/索引/对照/失败/清理；每步执行前预留下一批与收尾额度 | 返回计数只用于停止后续步骤，不能撤销已发生计费；范围未知的大步骤不执行 |

参考负载需要固定事件列表、字段、receipt顺序、版本密度、冷/暖比例、面板配置、并发度、错误与重试次数，优先使用确定性合成输入或本地已有原件回放。研究回放只取证，不启动模型；报告产出和 D1 成本不能用模型随机性混在一起比较。原版高成本对照只跑有界合成样本，不在生产复开一天用于“测基线”。

总降幅计算用同一负载下各类别旧成本权重×各类别实测降幅，分开暖态、冷态、重试和维护；任何缺失项保留未知。第3节87.7%只是特定两日组成。v4规模矩阵若解释为80,000键×100版本，单canonical就有800万逻辑行，未计索引已是10万写行预算的80倍；已由P3的分轴、小样本、执行前预算取代。

### 8.2 费用推导与限制

- 两天 109.6 亿行若全部处于超额区，读取边际费用约 10.96 美元；它不是这两天实际独立账单，免费额度消耗、账号共享和入账时间必须另核对。
- 理想移除上述初始化成本后的 6.724 亿行/日，30天约201.72亿行；再加其他查询增长及账号项目，不应拿“暂低于250亿”当完成标准。
- 1亿行/日目标按30天约30亿行，仍需单列写行、Workers请求/CPU、DO、存储和基础订阅，不能宣称整账号免费。
- 现有数据不证明 Cloudflare 误收；不以费用投诉替代修复，也不以账户计费延迟误判已经暂停的采集又恢复。

### 10.1 方案完成与实施完成分开

- 累计完成：六轮复盘修订；此前现场SQL机制与候选暖态只读验证、12项初步等价检查；本次增加60项跨两版SQLite复核、真实代码本地故障注入和预算反例、来源及恢复限制核验。
- 仍是未来工作：实际代码修复、完整D1事务及并发验收、拟定成本门槛达标、暂停状态下准备候选业务版、授权恢复及24小时成本验收。
- 工作顺序为 P0 → P1 → P3对P1验收 → P2 → P3完整验收 → P4。主热点可以先形成独立止损补丁，但达到放量恢复条件前保持暂停；不为追求一次大改而把简单止损和复杂语义修改绑成不可回退整体。
- 完成定义：数据/缓存/研究合同通过、热路径不再随无关历史增长、整体成本满足约定负载目标、失败可回到维护版，并明确实际账单范围；不是“build成功”或“某一条SQL很快”。
